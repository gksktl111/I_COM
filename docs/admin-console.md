## 접속과 관리자 계정

일상적인 계정 등록·관리는 **관리자 계정 메뉴(`/admin/accounts`)**에서 한다. 로그인한 관리자가 새 이메일과 비밀번호·확인을 입력하면 Supabase Auth에 관리자 역할과 함께 생성하며 즉시 로그인할 수 있다. 별도 초대 메일이나 설정 파일이 필요하지 않다. 관리자 목록에서 비밀번호를 변경할 수 있고, 본인 비밀번호 변경 시 로컬 세션을 종료한 뒤 다시 로그인한다. 비밀번호 원문을 조회·반환·로그·파일 저장하지 않는다. 일반 사용자 계정의 승격이나 비밀번호 변경, 관리자 삭제·권한 회수는 이 화면에 포함하지 않는다. 모든 기존 관리자는 동일한 계정 관리 권한을 갖는다.

- 로그인: `/admin/login`, 대시보드: `/admin`.
- Supabase 이메일·비밀번호 인증과 서버가 관리하는 `app_metadata.role = "admin"`을 함께 확인한다.
- 이메일 확인이 완료되지 않은 계정, 일반 사용자, 익명 사용자, 이용 제한 계정은 거부한다. 사용자가 수정할 수 있는 `user_metadata`는 권한 판단에 사용하지 않는다.
- 각 페이지·데이터 조회·서버 액션에서 권한을 다시 확인한다. 레이아웃 숨김만으로 보호하지 않는다.
- 인증 서버의 `/auth/v1/user`를 매 요청 조회한다. JWT를 로컬에서 해석한 역할을 신뢰하지 않는다. 토큰 만료·권한 제거·인증 서버 장애 시 로그인으로 이동한다.
- 접근 토큰은 HttpOnly / SameSite=Strict / `/admin` 경로 쿠키에 저장한다. 프로덕션은 Secure 쿠키이므로 HTTPS가 필요하다. 만료는 토큰 수명 또는 1시간 중 짧은 값이며 자동 연장하지 않는다.
- 로그아웃은 동일 출처 POST만 받고 Supabase 세션 종료를 요청한 뒤 쿠키를 제거한다. 외부 서비스 장애 시에도 로컬 쿠키를 제거한다. 이미 유출된 JWT의 즉시 무효화를 보장하는 별도 세션 저장소는 구현하지 않았다.
- 서버 키는 `SUPABASE_SECRET_KEY`, 프로젝트는 `SUPABASE_URL`. 브라우저에 키나 원본 API 오류를 전달하지 않는다.

아래 스크립트는 최초 관리자 계정이 전혀 없는 환경의 초기 설정용이다. 기존 계정 승격·비밀번호 초기화는 이 스크립트에서 하지 않는다. 관리자 로그인 이후에는 위 관리자 계정 메뉴를 사용한다.

```bash
node --experimental-strip-types scripts/admin/create-admin.ts --email 실제관리자이메일 --origin http://localhost:3002
```

비밀번호를 생성하거나 저장하지 않는다. Supabase 초대 계정과 일회용 설정 링크를 만들고 `.local/admin/계정ID-setup.html`에 파일 권한 600으로 보관한다. 이메일은 발송하지 않는다. 해당 파일을 브라우저에서 열어 `/admin/setup`으로 이동하면 본인이 비밀번호를 설정한다. 링크 토큰은 URL fragment로 전달해 서버 요청 URL에 남기지 않고, 새로고침과 재시도를 위해 설정이 성공할 때까지 유지한다. 제출할 때 fragment를 읽어 전달하고, 비밀번호 설정 성공 후 주소 표시줄에서 제거한다. 초대 확인 후 서버가 관리자 권한을 재검증하고 최대 10분의 HttpOnly 설정 쿠키로 저장 실패 재시도를 지원한다. 비밀번호 설정 후 쿠키를 지우고 다시 로그인하도록 한다. 파일은 Git에 포함하지 않으며 링크를 공유하지 않는다. 초기 구현 당시 지정된 첫 관리자 계정의 관리자 역할·비밀번호 미설정 상태를 실제 DB에서 확인했다. 이는 당시 초기 설정 기록이며 현재 계정 상태를 뜻하지 않는다.

인증 기준: [Supabase getUser](https://supabase.com/docs/reference/javascript/auth-getuser), [사용자 메타데이터](https://supabase.com/docs/guides/auth/users).

## 구현 범위

| 메뉴 | 동작 |
| --- | --- |
| 대시보드 | 실제 정책 수, 품질 상태, 출처별 저장량, 최근 실행 조회. 사용자 수는 현재 조회 페이지 범위를 명시 |
| 관리자 계정 | 관리자 전용 목록, 이메일·비밀번호 등록, 기존 관리자 비밀번호 변경. 중복 이메일은 기존 계정을 변경하지 않고 거부 |
| 사용자 관리 | 전체 인증 계정 기준 검색·필터·정렬·페이지 이동, 마스킹 이메일과 계정 상세. 제재·계정 삭제는 미구현 |
| 정책 관리 | 출처·정책명 검색, 페이지 이동, 정책 상세 모달, 공식 링크, 품질 상태별 이력 조회와 다음 커서 |
| 정책 수집 | 출처·검색어 설정, 실행 목록, 발견·성공·실패·대기 건수, 중단 사유, 호출 예약량, 이어서 수집 |
| 커뮤니티 / 신고 | 신고·게시글·댓글·금칙어 탭, 필터·목록·상세·조치 영역. 저장·신고 백엔드 미연결로 집계는 `—`, 조치는 비활성화, 검색은 미연동 안내 |
| 공지 / 알림 | DB에 초안 작성·수정·보관, 동시 수정 충돌 방지. 사용자 게시·외부 발송은 미연결 |

공지 초안은 `admin_notices`에 저장한다. RLS 활성화, 일반 역할 접근 차단, 서버 역할에 조회·추가·수정만 허용한다. `20260908063708_admin_notices.sql`을 개발 DB에 적용하고 마이그레이션 이력·DB 타입을 갱신했다.

## 수집 실행

웹 실행은 `POLICY_SYNC_ENABLED=true`와 해당 출처 API 키가 있어야 한다. 한 번의 요청은 최대 5개 정책 / 10회 API 호출 / 일일 예약 상한 100회로 제한한다. 요청 종료 후 저장된 실행 ID로 재개한다. 웹 요청에 맞춘 작은 배치이며 수천 건을 한 HTTP 요청이나 예약 작업으로 처리하지 않는다. 전체 범위는 검색어를 비워 지정한다. 호출 예산·중단·재개·목록 변경 계약은 [자동 수집 운영 문서](policy/work/collection-runbook.md)를 따른다.

수집 액션은 Node 서버에서 실행되며 배포 플랫폼에 충분한 실행 시간이 필요하다(`maxDuration=300`은 플랫폼 지원 시 적용). 프로세스가 중단되면 잠금 만료 후 이력에서 재개한다. 대규모 정기 수집은 별도 작업 실행기 연결이 필요하다. 관리자 UI 검증에서는 새 수집을 실행하지 않았다.

## 사용자 조회 계약

- 로그인 채널 필터는 카카오·네이버·구글만 제공한다. 이메일·사용자 ID 부분 검색, 정상·이용 제한 상태, 최근 로그인 7/30/90일·기록 없음, 가입/로그인 정렬, 15/30/50개 표시를 지원한다. 인증 대기 UI나 지표는 없다. 이는 위 관리자 인증의 서버 이메일 확인 검사를 제거한다는 뜻이 아니다.
- 서버에서 전체 Auth 목록을 확보하고 필터·정렬 후 페이지를 나눈다. 페이지 이동은 조건을 보존하며 새 필터 적용은 첫 페이지로 돌아간다. Auth API는 1,000개씩 최대 100페이지·전체 30초 한도로 조회하며 중복 ID·후속 페이지 오류를 검사한다. 불완전한 목록은 전체 결과처럼 표시하지 않고 실패 처리한다.
- 원문 이메일 검색은 서버에서만 수행하고 목록·상세에는 마스킹 값을 반환한다. 토큰·전화번호·사용자 메타데이터를 전달하지 않는다. 채널 정보가 없는 계정은 미확인으로 표시한다.
- 전체 등록·최근 30일 가입·최근 30일 로그인·이용 제한 지표는 전체 계정 기준이다. 최근 로그인은 서비스 이용 이벤트나 MAU가 아니다.
- 자녀·거주지·가구 특성·관심 분야는 사용자별 저장 계약이 없어 상세에서 미수집으로 표시하며 필터로 제공하지 않는다.

## 화면 구성

[Stitch 아이콤 프로젝트](https://stitch.withgoogle.com/projects/11573763693905046904)의 운영 현황 개정안 `4fbedbe2d7b0433aaca3e30e9f2015be`를 공통 기준으로 삼았다. 시안별 식별자와 순차 변경 기록은 [UI 이력](archive/admin-ui-history-20260909.md)에 보관한다.

- 보호된 layout의 `AdminShell`이 공통 헤더·사이드바·본문을 한 번 렌더링한다. `AdminHeader`·`AdminSidebar`가 메뉴 정의를 공유하고 `admin-chrome.css`가 공통 외곽 스타일을 담당한다. 품질 화면은 데이터 품질 메뉴를 활성화한다.
- 헤더는 현재 위치, 서버 `VERCEL_ENV`/`NODE_ENV`에 따른 환경, 공지·알림 링크, 실제 관리자 역할·이메일을 표시한다. 허구 신규 알림 점이나 총괄 관리자 역할을 만들지 않는다. 계정 메뉴에 관리자 계정·서비스 바로가기·POST 로그아웃을 제공하고 Escape·외부 클릭·초점 이탈로 닫는다.
- 사이드바의 통계·감사 로그·설정은 준비 중이다. 모바일 메뉴는 접기·펼치기와 이동 후 닫기·Escape를 지원한다. 좁은 화면에서는 이메일·환경 배지를 숨기고 계정 메뉴에서 이메일을 확인한다. 넓은 표는 내부 스크롤을 사용한다.
- 정책 상세·수집 제외 근거·관리자 비밀번호 변경은 공통 Dialog를 사용한다. 정책·수집 상세를 열어도 조회 URL은 유지한다. 제외 근거는 저장된 발췌이며 전체 원문으로 가장하지 않는다. 비밀번호 모달을 닫으면 입력을 초기화한다. 계정 목록에 이메일 확인 열은 없다.
- 공지·알림은 초안 목록과 작성 폼을 분리한다. 초안은 수정 펼침, 보관 본문은 짧은 미리보기와 전체 보기로 제공한다.
- 커뮤니티는 네 집계 영역, 네 탭, 검색·기간 필터, 목록과 상세 패널 순서다. 신고 상세는 접수 사유·원문·작성자·조치 순서를 유지한다. 게시글·댓글 탭은 신고 종결 대신 공개 복원 문구를 사용한다. 가상 신고 사례·건수는 없으며 공개 `/community`와 별개다.

## 검증 기록과 재현 범위

아래는 2026-09-08~09 작업 시점의 확인 결과다. 문서 통합 시 제품 코드·원격 DB를 다시 검증하지 않았다. 단계별 상세 결과는 [보관 이력](archive/admin-ui-history-20260909.md)을 참고한다.

| 검증 종류 | 확인 범위와 한계 |
| --- | --- |
| 서버 회귀 테스트 | 초기 관리자 서버 8개 파일·29건, 후속 사용자 조회 회귀 9건 통과 기록. 인증·쿠키·권한·계정·공지 충돌·수집 재개 등을 포함하며 서로 다른 실행 시점의 수치를 최신 단일 실행으로 합산하지 않는다 |
| 정적 검사·빌드 | UI 작업 단계별 ESLint·TypeScript·webpack 프로덕션 빌드 통과. 최종 공통 헤더·사이드바 단계도 통과 기록 |
| 합성 UI | 별도 로컬 복사본에서 합성 서버 응답으로 8개 화면을 320/390/768/1280px에 렌더링. 전체 가로 넘침, 활성 메뉴, 모달·계정 메뉴·모바일 메뉴의 키보드/닫기 동작 확인. 사용자·커뮤니티 단계는 1600px도 포함 |

합성 렌더링은 제품 인증 우회 경로를 추가하지 않고 별도 `/tmp/icom-admin-preview` 복사본에서 수행했다. 스크립트·캡처(`/tmp/icom-admin-screens`)는 저장소에 없는 임시 산출물이어서 다른 환경에서 그대로 재현할 수 없다. 초기 임시 관리자 생성·로그인 정보 보관은 자동 승인 검토에서 거절되어 수행하지 않았다. 해당 사실을 실제 로그인 검증 성공으로 해석하지 않는다.

저장소에서 실행 가능한 기본 확인 명령:

```bash
node --experimental-strip-types --test src/features/admin/server/*.test.ts
npm run build -- --webpack
```

미연결 기능의 구현 순서와 운영 검증 할 일은 [후속 작업](next-steps.md)에서 관리한다.
