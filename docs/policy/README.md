# 정책 데이터 개발 현황과 다음 작업

기준일: 2026-09-08 · 작업 브랜치: `feat/policy-ingestion`

**Gov24 실제 정책 8개의 수집·표시 정제·개발 DB 저장과 데이터 적합성 검증까지 완료했다.** 검색용 조건 규칙, 다른 API 수집, 서비스 UI 연결, 배포·자동 수집은 아직 완료되지 않았다.

## 1. 현재 개발 상태

| 영역 | 완료한 내용 | 남은 범위 |
| --- | --- | --- |
| Gov24 조회 | 목록·상세·지원조건 조회, 식별·페이지 완전성 검사, 호출 예산·제한 재시도·비밀값 제거 | 전체 정책 수집, 실제 계정 한도·갱신 특성 확인 |
| 정제 | 텍스트·HTML·빈 값·URL·날짜 처리, 필드 출처, 원본·표시·조건 해시와 정제 버전 | 검색용 분류·조건 규칙의 구조화와 검수 |
| 개발 DB | 원본 스냅샷·현재 표시·실행 이력 저장, 원자적 반영·중복 방지·실패 보존 | 다중 API 출처·검수 규칙 스키마 설계·적용 |
| 실행 제어 | 임대 잠금·세대 검증, 재개, dry-run, 저장 원본 재정제 | 배포 진입점·예약·운영 관측 |
| 실제 검증 | 8개 최초·반복 저장, DB 무변경 dry-run, 동시 실행 1개 허용, 권한 검증 | 전체 데이터·현행 정책·장기 자동 실행 보장 아님 |
| 검색 데이터 적합성 | 8개 × 14개 표시 필드 대조: 112개 공백 외 차이 없음, 여섯 조건별 부족 항목 기록 | 비교 준비 완료 0개; 공식 근거·규칙 검수 필요 |
| 검색·입력 설계 | FR-06~10, 임신 여부, 2단계 입력, 공통 논리 계약, Stitch 대조 | 입력 모델·분류 사전·비교 기능·UI 구현 |
| 복지로 확장 | 중앙·지자체 공식 Swagger 보관, 필드 매핑 초안 | API별 활용 승인·키, 목록 요청 명세, 인증된 실제 표본 |

현재 원격 DB는 승인된 `policy-dev` 프로젝트(`visumyadkxleiqtxokqg`)다. 적용 마이그레이션은 `20260907181933_policy_ingestion.sql`이며 **이미 적용돼 있으므로 재적용하지 않는다.** 기존 프로젝트 공통 함수의 advisor 경고와 새 수집 테이블 검사 결과는 검증 문서에 구분해 기록했다.

## 2. 문서 읽는 순서

1. [검색 요구사항](./policy-search-requirements.md): 무엇을 입력받고 어떤 정책을 어떻게 보여줄지.
2. [입력 화면 요구사항](./policy-input-design-brief.md): 1단계 기본 정보·관심 정책 → 2단계 관련 상세 정보. 공유 질문 재사용, 모름·건너뛰기 처리.
3. [저장 데이터 적합성 검증](./policy-data-fitness.md): 현재 8개 원본·저장값 대조와 검색에 부족한 의미.
4. [공통 논리 데이터 계약](./policy-common-data-contract.md): 다른 API도 따라야 할 출처·표시·분류·규칙·검수 기준. 아직 DB 구현 계약이 아님.
5. [다음 API 연결 준비](./policy-api-expansion.md): 복지로 공식 링크·명세·매핑·키 준비.
6. [실행 안내](./policy-sync-runbook.md), [저장 계약](./policy-db-schema.md), [실행 검증 결과](./policy-sync-validation.md): 구현된 수집 기능의 사용·검증 근거.
7. [Stitch 화면 대조](./policy-stitch-data-mapping.md): 참고 디자인과 필요한 데이터의 차이. 데이터 정확성을 우선하여 디자인에 반영.

기존 한국어 구현 계획서·구조화 설계서는 설계 배경이다. 그 문서의 과거 미착수 체크리스트를 현재 상태로 오인하지 않는다. 실제 구현 계약은 [Gov24 수집 계약](./policy-data-contract.md)과 저장 계약을 기준으로 한다.

## 3. 다음 작업 순서

### A. 키 대기 중 진행할 작업

1. **복지로 목록 요청 명세·코드표 확보:** 현재 저장 Swagger의 요청 정의는 선택된 상세 기능 중심이다. 목록 필수값·검색 필터·페이지 조건을 공식 자료로 확인한다. 응답 필드 선언을 실제 반복 건수 보장으로 해석하지 않는다.
2. **공통 매핑 구체화:** 출처 식별·원본·표시·분류·조건 후보의 논리 계약을 출처별 매핑표로 구체화한다. 문자열 코드·누락·시행 기간·신청 기간의 의미를 유지한다.
3. **Gov24 규칙 후보 검수 준비:** 8개 정책에서 근거 문장·대상 인물·적용 범위·단위·경계·기준일·미해결 항목을 구조화한 초안을 만든다. 미확인 기준을 추정해 채우거나 검수 완료로 표시하지 않는다.
4. **공식 근거 보완:** 지역 적용·연령 경계·소득 산정 기준·급여 문구 충돌·신청 URL을 확인한다. 사용자 추가 입력으로 해결할 문제와 정책 원문 부족을 구분한다.

완료 기준: 다음 API 표본을 동일한 기준으로 검증할 수 있는 매핑표와, 현재 정책별 검수 가능한 후보·미해결 목록이 있다.

### B. 복지로 활용 승인·키 준비 후

1. 중앙부처·지자체 API 각각의 목록 1페이지로 인증·오류 envelope·XML 형태를 확인한다.
2. 육아 관련 소규모 표본의 상세를 수집한다. 원문 XML, 조회 근거, 반복 요소, 누락·빈 태그, ID·페이지·날짜·코드를 검증한다.
3. 실제 표본으로 정제 어댑터와 필요한 회귀 검증을 작성한다. 필드명만 보고 Gov24 규칙을 복사하지 않는다.
4. 공통 매핑·표시 적합성·공식 출처를 검증하고, 다중 출처 저장 구조를 설계·마이그레이션한다. 동일 정책의 교차 출처 연결은 검수 후 수행한다.
5. 작은 범위 저장·재실행·실패 복구를 확인한 뒤 수집 대상을 확대한다.

완료 기준: 출처별 실제 표본·매핑·정제·저장·재실행 근거가 있고, 표시/공개/비교 가능 범위를 각각 보고한다.

### C. 검색과 UI 구현

- 관심 정책 분류와 두 단계 입력 데이터 모델을 확정한다. 지역 코드, 인물 관계, 자녀별 생년월일, 소득 기준, 답변 정밀도·미입력을 구분한다.
- 검수된 규칙으로 PASS/FAIL/UNKNOWN과 MATCH/NO_MATCH/NEEDS_CHECK를 구현한다. 연령 경계·동일 자녀·AND/OR·하위 서비스·노후 규칙을 검증한다.
- 실제 저장 데이터로 입력 → 후보 조회 → 비교 이유 → 상세·공식 출처 연결을 검증한다.
- Stitch 스타일을 바탕으로 입력·결과·상세·모바일 UI를 구현한다. 샘플 정책·금액·건수를 실제 데이터로 취급하지 않는다.

### D. 배포·자동 수집

배포 플랫폼·요금제·공개 URL과 계정 호출 예산을 확인한 뒤 예약 방식을 정한다. 예약 진입점 인증, 실행 잠금·실패 기록을 연결하고 실제 12시간 간격 2회 성공을 확인한다. 현재는 예약 등록·배포된 수집 경로가 없다.

## 4. 필요한 사용자 준비

- 복지로 중앙부처·지자체 API 각각 활용 신청 후, 승인된 키를 `.env.local`의 `BOKJIRO_CENTRAL_API_KEY`, `BOKJIRO_LOCAL_API_KEY`에 저장한다. 변수 이름만 `.env.example`에 준비돼 있으며 아직 복지로 CLI는 없다.
- 최초 서비스 지역을 확정한다. 현재 8개 검증 표본에는 전국 범위 후보·서울시·서울 중구가 있고, 디자인의 종로구 예시는 운영 지역 확정이 아니다.
- 예약 구현 단계에서 배포 플랫폼·요금제·공개 URL을 제공한다.

키는 대화·문서·Git에 넣지 않는다. Supabase 관리용 액세스 토큰과 데이터 API 서버 키는 역할이 다르며, 관리용 토큰은 배포 수집기에 필요하지 않다.

## 5. 검증 및 환경 제한

- 정책 테스트 7개 파일 통과 기록을 확보했다. 원본 반복 수집, 정제, 서비스, SQL 원자성·잠금·복구, 실제 fixture 통합 검증을 포함한다.
- 원격 개발 DB 최초·반복 실행은 각각 8개 성공, 반복 시 원본 스냅샷 중복 증가 없음. dry-run은 6개 테이블의 전체 행 지문 불변을 확인했다.
- 저장 데이터 감사 스크립트는 정제 재실행 8/8 일치, 해시 8/8 일치, 112개 필드의 공백 외 차이 0을 확인했다.
- TypeScript와 관련 ESLint 검사 통과. 이번 문서·키 준비 변경으로 기존 성공한 수집 테스트를 반복하지 않는다.
- 전체 빌드는 이전 실행에서 Turbopack의 프로세스/포트 생성 권한 오류(`Operation not permitted`)로 완료되지 못했다. 코드 변경으로 우회하지 않았으며 빌드 성공으로 보고하지 않는다. 환경이 달라진 배포/CI에서 다시 확인해야 한다.

실행 명령·상세 run ID·권한 결과는 실행 안내와 검증 결과 문서에 있다. 공개 정책 수, 신청 가능 여부, 추천 정확도, 자동 운영 완료는 위 성공 기록으로 보장하지 않는다.
