# 정책 데이터 개발 현황과 다음 작업

**현재 우선순위:** 활성화된 정책 1,000건을 확보한다. 서비스 범위에는 부부·부모뿐 아니라 아동·청소년 본인 지원도 포함한다. 추가 수집을 잠시 멈추고 2,277건을 v3로 재평가해 활성 842·검토 845·제외 590건을 확인했다. 원문·평가 이력을 보존하고 호출 제한 출처는 제외한다. [진행 기록](./policy-bulk-20260908.md)과 [최신 관련성 기준](./policy-relevance.md)을 우선한다. 아래 215건 등 표본 수치는 과거 기록이다.

기준일: 2026-09-08 · 작업 브랜치: `feat/policy-ingestion`

**자동 ID 탐색·페이지별 수집·정제·중단/재개와 품질 이력 저장 구조를 구현하고 개발 DB에 적용했다.** 복지로 중앙 “양육” 검색 40개를 자동 처리했고, 기존 Gov24 8개·복지로 지자체 2개에도 품질 평가를 추가했다. 이후 전체 범위 1차 수집 당시 출처별 레코드는 **215개**였고, 연속 수집 후 현재는 **1,247개**다. [수집 확대 결과와 재개 ID](./policy-expansion-20260908.md)를 참고한다. 고유 정책 수와는 다르다.

**최신 실행·품질 조회 방법은 [자동 수집·품질 운영 계약](./policy-automatic-quality.md)을 먼저 읽는다.** 관리자 인증·화면과 수집 재개 연결은 구현했다([관리자 운영 안내](../admin-console.md)). 예약 배포는 후속 작업이다. 이전 12개 표본 감사와 v2 재처리 기록은 [복지로 실행 안내](./policy-bokjiro-runbook.md)에 보존한다.

**서비스 관련성 재평가:** v3로 아동 본인 지원 경로를 보완했다. 검토 대기 105건과 제외 4건을 관련으로 회수하고 성인 전용 오분류 3건을 제외했다. 관리자 기본 목록은 활성 후보이며 검토·제외는 별도 조회한다. [관련성 기준과 검증](./policy-relevance.md)을 참고한다.

## 2. 문서 읽는 순서

현재 실행·품질 저장 계약은 [자동 수집·품질 운영 계약](./policy-automatic-quality.md)을 우선한다. 아래 문서는 검색 요구사항과 표본 감사 배경이다.

1. [검색 요구사항](./policy-search-requirements.md): 무엇을 입력받고 어떤 정책을 어떻게 보여줄지.
2. [입력 화면 요구사항](./policy-input-design-brief.md): 1단계 기본 정보·관심 정책 → 2단계 관련 상세 정보. 공유 질문 재사용, 모름·건너뛰기 처리.
3. [Gov24 저장 데이터 적합성 검증](./policy-data-fitness.md), [복지로 표본 적합성 검토](./policy-bokjiro-fitness.md): 원본·저장값 대조, 검색에 부족한 의미와 출처 충돌.
4. [공통 논리 데이터 계약](./policy-common-data-contract.md): 다른 API도 따라야 할 출처·표시·분류·규칙·검수 기준. 아직 DB 구현 계약이 아님.
5. [다음 API 연결 준비](./policy-api-expansion.md): 복지로 공식 링크·명세·매핑·키 준비.
6. [실행 안내](./policy-sync-runbook.md), [저장 계약](./policy-db-schema.md), [실행 검증 결과](./policy-sync-validation.md): 구현된 수집 기능의 사용·검증 근거.
7. [Stitch 화면 대조](./policy-stitch-data-mapping.md): 참고 디자인과 필요한 데이터의 차이. 데이터 정확성을 우선하여 디자인에 반영.

기존 한국어 구현 계획서·구조화 설계서는 설계 배경이다. 그 문서의 과거 미착수 체크리스트를 현재 상태로 오인하지 않는다. 실제 구현 계약은 [Gov24 수집 계약](./policy-data-contract.md)과 저장 계약을 기준으로 한다.

## 3. 다음 작업 순서

1. **정책 후보 확보:** 명확히 무관한 새 정책만 제외하고, 관련·검토 필요 정책과 원문을 최대한 수집한다. 기존 세 출처 실행의 진행 위치를 보존했으며, 재개 시 강화된 v2 기준을 적용한다. 조건 해석·자격 판정은 수집의 선행 조건으로 요구하지 않는다.
2. **품질 문제 처리 흐름:** ERROR는 정제 오류 수정·재처리, 공통 SOURCE_MISSING은 출처/매핑 수준의 보완, 충돌·변경은 근거 검수로 나눈다. REVIEW 정책 수를 개별 수동 정제 작업 수로 해석하지 않는다.
3. **범위·호출량 확대와 예약:** 현재 전체 범위 1차 배치를 진행했고 총 215개가 저장됐다. 전체 출처를 다 수집한 것이 아니다. 포털 계정 한도·대상 범위·배포 플랫폼을 확인하고 자동 실행기를 연결한다. 12시간 간격 실제 2회 성공은 아직 검증하지 않았다.
4. **검색 비교·입력·UI:** 지역·인물·기간·소득·하위 서비스의 검수된 규칙과 미확인 처리를 구현한다. 수집/품질 PASS를 자격 MATCH로 바꾸지 않는다. 공식 근거 보완·동일 정책 연결·조건 충돌 검수는 남아 있다.

## 4. 필요한 사용자 준비

- 복지로 중앙부처·지자체 키 설정과 인증 확인은 완료됐다. `policy:sync:bokjiro` CLI로 실행할 수 있다.
- 최초 서비스 지역을 확정한다. 현재 8개 검증 표본에는 전국 범위 후보·서울시·서울 중구가 있고, 디자인의 종로구 예시는 운영 지역 확정이 아니다.
- 예약 구현 단계에서 배포 플랫폼·요금제·공개 URL을 제공한다.

키는 대화·문서·Git에 넣지 않는다. Supabase 관리용 액세스 토큰과 데이터 API 서버 키는 역할이 다르며, 관리용 토큰은 배포 수집기에 필요하지 않다.

## 5. 검증 및 환경 제한

- 자동화 추가 후 정책 테스트 15개 파일 범위를 확인했다. 1001개 목록 체크포인트, 실제 XML 통합·재개·품질 오류 격리·원자적 저장·관리자 커서/권한 검증을 포함한다. 세부 명령과 실제 원격 결과는 [운영 계약](./policy-automatic-quality.md)과 [검증 JSON](../fixtures/policy-automatic/validation.json)에 기록했다.

- 기존 정책 테스트 10개 파일 통과 기록을 확보했다. 원본 반복 수집, 정제, 서비스, SQL 원자성·잠금·복구, 실제 fixture 통합 검증을 포함한다.
- 원격 개발 DB 최초·반복 실행은 각각 8개 성공, 반복 시 원본 스냅샷 중복 증가 없음. dry-run은 6개 테이블의 전체 행 지문 불변을 확인했다.
- 저장 데이터 감사 스크립트는 정제 재실행 8/8 일치, 해시 8/8 일치, 112개 필드의 공백 외 차이 0을 확인했다.
- 복지로 v2 변경 후 정책 테스트 10개 파일·TypeScript·전체 lint 통과. 원격 재처리 4개는 API 0회로 성공했고, 원본·표시·적용 스냅샷 불변 및 전체 v2 정제 재실행 일치를 확인했다. [v2 검증](../fixtures/bokjiro/fitness/reprocess-v2-audit.json), [DB 실행 결과](../fixtures/bokjiro/fitness/reprocess-v2-database.json)를 참조한다.
- 전체 빌드는 이번 일반·권한 실행 모두 Turbopack의 프로세스/포트 생성 권한 오류(`Operation not permitted`)로 완료되지 못했다. 코드 변경으로 우회하지 않았으며 빌드 성공으로 보고하지 않는다. 환경이 달라진 배포/CI에서 다시 확인해야 한다.

실행 명령·상세 run ID·권한 결과는 실행 안내와 검증 결과 문서에 있다. 공개 정책 수, 신청 가능 여부, 추천 정확도, 자동 운영 완료는 위 성공 기록으로 보장하지 않는다.
