# 정책 검색·추천 요구사항과 데이터 적합성 기준

작성일: 2026-09-08 · 상태: 사용자 FR-06~FR-10을 구체화한 검토 초안

이 문서는 사용자 조건에 따른 정책 검색의 동작과, 그 동작에 필요한 수집·정제 데이터의 기준을 정의한다. Gov24뿐 아니라 이후 연결할 API에도 같은 의미 기준을 적용한다. 아래 세부 처리·정렬 방식은 제안이며 구현 완료를 뜻하지 않는다.

## 1. 목적과 문서 관계

사용자가 거주 지역과 가족·자녀·임신·소득 조건을 입력하면 관련 정책과 관련 이유, 추가로 확인할 조건, 공식 출처를 제공한다. 결과는 입력 정보와 확인된 정책 기준의 비교이며 실제 신청 승인이나 수급 자격의 확정이 아니다.

- 본 문서: 검색 요구사항, 필요한 데이터, 데이터 적합성 판정의 기준.
- [공통 데이터 계약](./policy-common-data-contract.md): API별 매핑에 적용할 논리 구조와 수용 기준.
- [다음 API 연결 준비](./policy-api-expansion.md): 복지로 공식 명세·매핑·미확인 사항.
- [수집 데이터 계약](./policy-data-contract.md): 현재 Gov24 수집·표시 정제의 구현 계약.
- [기존 구조화 설계서](./행정안전부%20API%20기반%20정책%20데이터%20정제·구조화%20설계서.md): 규칙 버전·조건 그룹 등의 설계 배경.
- [저장 계약](./policy-db-schema.md): 현재 구현된 저장 구조와 범위.
- [실제 8개 정책 적합성 검증](./policy-data-fitness.md): 저장 원본·표시 데이터 대조와 공통 계약 보완안.
- [입력 화면 요구사항](./policy-input-design-brief.md): 실제 정책 근거로 필요한 기본·후속 질문과 디자인 반영 기준.
- [Stitch 화면 데이터 매핑](./policy-stitch-data-mapping.md): 입력·결과·상세 화면과 데이터 요구사항의 차이.

현재 8개 정책의 원본과 표시 데이터는 저장돼 있다. 검색용 지역·가족·자녀·임신·소득 규칙의 구조화, 검수, 조건 비교와 검색 연결은 아직 완료되지 않았다. 수집 성공이나 표시 정제 성공을 검색 데이터 적합성 통과로 간주하지 않는다. 이 문서는 특정 정책의 자격 조건을 새로 확정하지 않는다.

## 2. 공통 원칙

1. 원본, 표시 정보, 검색 분류, 조건 비교 규칙을 구분한다. 키워드나 분류 태그만으로 자격을 판단하지 않는다.
2. 모든 정제 값과 비교 규칙은 출처·원본 필드·스냅샷으로 추적할 수 있어야 한다. 비교 규칙에는 근거 문장과 검수 상태도 필요하다.
3. 정보 없음, 미입력, 명시적 비해당, 명시적 제한 없음을 구분한다. null을 false·0·전국 적용·제한 없음으로 바꾸지 않는다.
4. 지역·연령·금액·기간·예외·AND/OR 의미를 추측하여 채우지 않는다. 원문으로 해결되지 않는 사항은 추가 확인 대상으로 남긴다.
5. 사용자 검색은 내부 데이터로 수행한다. 사용자의 검색 요청마다 외부 정책 API를 수집하지 않는다.
6. 표시 가능 여부와 조건 비교 가능 여부는 별도로 관리한다. 설명을 표시할 수 있는 정책도 조건 비교에는 정보가 부족할 수 있다.

## 3. FR-06 — 사용자 조건 입력

입력 흐름은 1단계 기본 정보·관심 정책 선택, 2단계 맞춤 상세 정보 입력으로 구성한다. 지역·가족 상황·관심 분야로 질문 범위를 정하고, 관련 정책에 공통으로 필요한 상세 정보는 중복 없이 한 번만 받는다. 관심 분야는 복수 선택과 전체/잘 모르겠어요를 지원하며 자격 조건과 구분한다. 결과 화면에서는 추가로 필요한 정보만 다시 질문한다.

사용자는 다음 조건을 입력·수정하여 다시 검색할 수 있다. 최초에는 모든 항목의 입력을 강제하지 않고, 누락된 조건이 필요한 정책에서 추가 입력을 안내한다. 실제 정책 조건과 확보 가능한 데이터에 따라 항목을 조정한다.

| 입력 | 제안하는 내부 표현 | 검증·처리 기준 |
| --- | --- | --- |
| 거주 지역 | 시도·시군구 지역 ID | 지역 계층의 조합을 검증한다. 시설 검색용 GPS와 구분한다. 정책이 요구하는 주민등록지·실거주지 등의 기준을 표시한다. |
| 가족 형태 | 복수 특성 코드 또는 미입력 | 한부모·조손·다문화 등 특성은 중첩될 수 있다. 미선택과 명시적 비해당을 구분한다. 법적 인정 기준이 필요한 경우 별도 확인한다. |
| 자녀 수 | 0 이상의 정수 또는 미입력 | 0명과 미입력을 구분한다. 입력한 자녀 목록과 모순되면 정정을 요청한다. 정책별 산정 대상 자녀 수와 단순 총자녀 수를 구분한다. |
| 자녀 연령 | 자녀별 생년월일 또는 연령 범위 | 정확한 월령 비교는 생년월일과 기준일로 계산한다. 연령대만 입력하면 범위 내 판정이 달라질 수 있는 조건을 확정하지 않는다. |
| 임신 여부 | 예 / 아니요 / 미입력 | 명시적인 아니요와 미입력을 구분한다. 누구의 임신 여부인지 입력 대상과 정책의 비교 대상을 일치시킨다. |
| 소득 구간 | 산정 기준·적용 연도·구간의 상하한 또는 미입력 | 기준 중위소득 비율, 소득인정액, 건강보험료 등 서로 다른 기준을 구분한다. 필요한 경우 가구원 수도 받는다. 월급을 다른 소득 기준으로 자동 변환하지 않는다. |

소득 입력 구간 전체가 기준에 들어가면 통과, 전체가 벗어나면 불일치로 비교할 수 있다. 경계에 걸치거나 정책과 산정 기준·연도가 다르면 추가 확인이 필요하다. 구간의 경계 포함 여부를 명시한다.

임신 여부는 기본 입력 항목으로 제공한다. 임신 주수·출산 예정일, 거주 시작일, 출생·입양일, 장애 등 추가 항목은 해당 정책의 실제 조건을 근거로 필요한 경우에만 요청한다. 최초 입력 항목 확장은 데이터 적합성 검토 결과에 남긴다. 맞춤 입력은 기본적으로 검색 요청 범위에서 사용하고 영구 저장은 별도 요구사항으로 다룬다.

## 4. FR-07 — 조건 기반 정책 필터링

### 4.1 비교에 필요한 정책 데이터

아래 항목은 논리적 데이터 요구사항이며 특정 DB 테이블이나 컬럼을 확정하지 않는다.

| 조건 | 정책에 필요한 구조화 정보 | 금지되는 추정 |
| --- | --- | --- |
| 지역 | 전국/특정 지역/미확인, 적용 지역 ID와 계층, 하위 지역 포함 여부, 거주 기준, 필요 시 거주 기간·기준일 | 제공 기관 소재지를 적용 지역으로 복사, 지역 누락을 전국으로 처리 |
| 가족 형태 | 대상 특성, 포함·제외 기준, 결합 관계, 인정 기준과 근거 | 한부모/조손 결합 코드를 각각의 확정 자격으로 분해 |
| 자녀 수 | 기준 수, 비교 연산자, 산정 대상 자녀의 범위와 기준일 | 다자녀 태그를 일괄적으로 2명 이상 규칙으로 변환 |
| 자녀 연령 | 비교 대상, 단위, 상·하한과 경계 포함 여부, 계산 기준일, 동일 자녀에 적용할 조건 묶음 | 부모 나이를 자녀 나이로 사용, 일수를 30으로 나눠 월령 계산 |
| 임신 여부 | 임신 대상자, 임신 여부 조건, 필요 시 임신 주수·출산 예정일·판정 기준일, 근거 문장 | 임신 여부만으로 출산·입양·산후 조건까지 충족한다고 처리, 미입력을 비임신으로 변환 |
| 소득 | 산정 기준, 기준 연도, 상·하한과 경계, 단위, 가구 규모 등 필요한 전제 | 금액·비율 혼용, 소득 기준이 다른 사용자 값을 직접 비교 |
| 추가 조건 | 조건별 비교 가능 여부, 원문 근거, 미해결 기준 | 구조화하지 못한 예외·중복 수혜 제한을 삭제하고 완전한 규칙으로 표시 |

모든 규칙은 원본 스냅샷, 검수 상태·시점, 유효 기간, 비교 범위의 완전성 정보를 갖는다. `COMPLETE`는 검수 범위에서 필요한 기준을 모두 표현했다는 뜻이다. 확인하지 못한 필수 기준이 있으면 `PARTIAL` 또는 `UNKNOWN`으로 둔다.

### 4.2 비교 순서와 판정

1. 표시·출처 기준을 충족한 정책에서 후보를 찾는다. 주제·태그는 관련성 탐색에 활용할 수 있지만 태그 누락만으로 탈락시키지 않는다.
2. 현재 원본과 연결된 검수 규칙이 유효한지 확인한다. 미검수·노후화·충돌한 규칙으로 확정 판정하지 않는다.
3. 지역과 사용자 조건을 비교하고 각 조건에 `PASS / FAIL / UNKNOWN`과 근거를 부여한다.
4. 조건 관계를 반영하여 정책 결과를 결정한다. 그룹 내부 AND, 대체 가능한 그룹 사이 OR를 기본으로 한다. 지역 등 공통 필수 조건은 별도로 결합한다. 빈 그룹과 누락 규칙은 통과가 아니다.
5. 신청 접수 상태와 관련성 정렬을 별도로 적용한다.

AND는 FAIL이 하나라도 있으면 FAIL, 그 외 UNKNOWN이 있으면 UNKNOWN이다. OR는 PASS가 하나라도 있으면 PASS, 그 외 UNKNOWN이 있으면 UNKNOWN이다. 자녀 조건 여러 개가 같은 자녀를 요구하면 한 자녀가 모두 충족해야 한다. 서로 다른 자녀의 통과 결과를 합치지 않는다.

| 결과 | 기준 | 사용자 안내 |
| --- | --- | --- |
| `MATCH` | 유효한 검수 규칙과 완전한 비교 범위에서 필수 조건을 통과 | 입력한 조건에 부합 |
| `NO_MATCH` | 유효하고 검수된 규칙에서 모든 대체 경로를 고려해 필수 조건 불일치가 확정 | 입력한 조건과 불일치, 이유 제공 |
| `NEEDS_CHECK` | 확정 불일치가 없으나 미입력·미검수·미해결 기준·규칙 변경 등으로 판단 불가 | 추가 확인 필요, 필요한 정보 제공 |

일부 조건이 UNKNOWN이어도 유효한 공통 필수 조건의 명확한 FAIL로 모든 경로가 불가능하면 NO_MATCH가 될 수 있다. 한 대체 경로의 실패만으로 전체 정책을 제외하지 않는다. 규칙 전체가 무효한 경우 과거 규칙의 FAIL도 사용하지 않는다.

### 4.3 결과 포함과 관련성 정렬

초기 제안은 MATCH를 먼저, NEEDS_CHECK를 별도 구분해 함께 제공하고 NO_MATCH는 기본 추천에서 제외하는 것이다. 불일치 결과를 확인하는 선택 기능에서는 제외 이유를 제공한다. 정책 조건이나 사용자 입력이 부족하다는 이유만으로 후보를 조용히 누락하지 않는다.

같은 판정 안에서는 확인된 사용자 관심·가족 특성과 정책 분류의 관련성을 활용하고, 동률은 정책명·내부 ID 등 일정한 기준으로 정렬한다. 상세 점수·가중치는 실제 표본 평가 후 결정한다. 미확인 조건을 일치 점수로 계산하거나 점수를 수급 가능 확률로 표시하지 않는다.

결과가 없으면 ‘현재 수집 범위에서 조건에 맞는 정책을 찾지 못함’으로 안내한다. 현재 데이터가 전체 정책을 포함한다거나 사용자가 받을 정책이 전혀 없다고 표현하지 않는다.

## 5. FR-08 — 추천 정책 목록

카드 또는 리스트에 다음 정보를 제공한다. 표현 방식은 UI 설계에서 결정한다.

| 표시 정보 | 필요한 데이터와 처리 |
| --- | --- |
| 정책명 | 공식 정책명, 필수 |
| 정책 요약 | 출처 있는 요약. 내부 작성 요약은 원문과 구분하며 조건·예외를 왜곡하지 않음 |
| 주요 지원 대상 | 지원대상 표시문. 상세 원문으로 이어질 수 있어야 함 |
| 주요 지원 내용 | 금액·단위·주기·지급 대상·예외를 보존한 설명 |
| 신청 기간 또는 관련 일정 | 신청기한 원문과 확인된 일정. 사업 기간·지원 기간·신청 기간을 구분 |
| 정책 제공 기관 | 소관 기관명. 접수·문의 기관과 구분 |

정책별 판정, 관련 이유, 추가 확인 사항도 함께 제공한다. 원문에서 확보하지 못한 정보는 ‘정보 확인 필요’로 표시하고 다른 필드에서 추측해 채우지 않는다. 목록 축약 시 금액의 단위나 부정·예외 표현이 잘리지 않도록 한다.

접수 상태는 `OPEN / CLOSED / UNKNOWN`으로 자격 비교 결과와 분리한다. 검증된 신청 기간과 기준 시각으로 확인 가능한 경우에만 OPEN/CLOSED를 부여한다. 상시·예산 소진·공고 확인 등의 문구만으로 현재 접수 가능을 단정하지 않는다. 종료된 정책은 상태를 표시하고 보기 옵션으로 구분한다.

## 6. FR-09 — 정책 상세

| 표시 정보 | 데이터 기준 |
| --- | --- |
| 정책명 | 목록과 같은 정책 ID·표시 버전의 이름 |
| 지원 대상 | 대상 설명 원문을 정제한 전체 텍스트 |
| 지원 조건 | 선정기준·예외·추가 조건 원문, 비교 결과와 미해결 사항 |
| 지원 내용 | 금액·단위·횟수·주기·서비스 내용을 보존 |
| 신청 방법 | 온라인·방문 등 절차와 원문 링크, 임의 절차 생성 금지 |
| 필요 서류 또는 준비사항 | 원문 내용. 누락을 ‘서류 없음’으로 해석하지 않음 |
| 담당 기관 | 소관·접수·문의 기관의 역할 구분, 제공되는 경우 연락처 |
| 공식 출처 | 출처명·원본 링크·확인 시점 |

표시 정보와 비교 규칙이 서로 다른 원본 버전일 때는 확정 판정을 중단하고 재검수 상태를 표시한다. 조건에 부합하더라도 접수 상태와 추가 확인 사항을 독립적으로 볼 수 있어야 한다.

## 7. FR-10 — 공식 출처 연결

- 각 공개 정책은 사용자가 직접 확인할 수 있는 해당 정책의 공식 원본 링크를 갖는다. 공식 출처를 확보하지 못하면 수집 원본은 보관하되 추천 공개 대상에서는 보류한다.
- 출처 링크와 온라인 신청 링크는 별개다. 신청 링크를 출처라고 일괄 취급하지 않는다.
- URL의 http/https 문법 검증, 공식 출처 여부 확인, 링크 접근 가능성 확인은 별도 상태로 관리한다. 문법상 유효함을 공식성·접속 성공·신청 가능으로 해석하지 않는다.
- 잘렸거나 복수인 URL은 추측해 수정하지 않는다. 다른 공식 출처로 보완할 경우 확인 근거와 출처를 기록한다. 일시적인 접속 실패는 확인 시점과 함께 기록하고 수동 확인 대상으로 둔다.
- AI 설명과 내부 요약은 보조 정보이며 공식 원문을 대체하지 않는다. 사용자가 최종 조건과 신청 절차를 공식 출처에서 확인하도록 연결한다.

## 8. API 공통 수집·정제 기준

각 API의 필드를 공통 의미로 매핑하되 제공하지 않는 정보를 강제 생성하지 않는다.

| 단계 | 필수 기준 |
| --- | --- |
| 식별 | 제공자·외부 ID·API 버전을 보존. 다른 제공자의 같은 ID는 다른 출처로 취급 |
| 원본 | 연결 가능한 목록·상세·조건 응답과 수집 시점·완전성·오류를 보관 |
| 표시 정제 | HTML·공백 정리 전후에 대상·숫자·단위·부정·예외·조건 관계가 유지됨 |
| 필드 매핑 | 원본 경로, 내부 의미·타입·단위, 빈 값 의미, 변환 방식과 버전 기록 |
| 분류 | 코드 사전의 출처·버전·검증 상태 보관. 미지 코드는 원본 보존 후 미확인 처리 |
| 비교 규칙 | 근거 문장, 비교 대상, 연산자, 단위, 기준일, 조건 관계, 검수 상태 확보 |
| 변경 | 원본 변경 시 영향을 받는 규칙을 재검수. 의미 영향이 불분명한 변경도 재검수 대상 |
| 출처 충돌 | API별 원본과 차이를 보존. 최신 날짜나 같은 제목만으로 자동 덮어쓰기·병합 금지 |

서로 다른 API가 동일 정책을 제공하는 경우 출처 식별자와 공통 정책 식별자를 분리할 수 있어야 한다. 동일 정책 여부, 적용 연도·지역·사업 차이, 필드별 우선 출처를 검수한 뒤 연결한다. 충돌하는 조건을 섞어 새로운 자격 규칙을 만들지 않는다.

## 9. 검색 구현 전 데이터 적합성 검증

### 9.1 검증 방법

실제 저장된 정책과 그 적용 원본 스냅샷을 읽어 FR-06~FR-10 요구 항목별로 대조한다. 원본에 정보가 있는지, 표시 정제에 의미 손실이 없는지, 비교 가능한 구조가 있는지, 근거와 검수가 연결되는지를 각각 확인한다. 검색 엔진 구현이나 UI 연결은 이 검증의 선행 조건이 아니다.

다음 형식의 정책별 보고서를 작성한다.

| 기록 항목 | 내용 |
| --- | --- |
| 식별·버전 | 제공자, 외부 ID, 원본 스냅샷, 정제 버전, 검토 시점 |
| 요구사항 | FR 번호와 세부 항목: 지역·연령·신청기간 등 |
| 원본 근거 | 원본 필드·경로와 필요한 근거 문장 |
| 현재 저장값 | 정제 결과와 현재 구조화 상태 |
| 판정 | 사용 가능 / 추가 구조화 필요 / 원본 정보 부족 / 정제 오류 |
| 영향 | 표시 가능 여부, 비교 가능 여부, 잘못된 포함·제외 가능성 |
| 조치 | 매핑 수정, 규칙 구조화·검수, 다른 공식 자료 확보 등 |

‘사용 가능’은 해당 용도의 의미·타입·근거가 충족된 경우다. 텍스트로만 존재하는 연령 기준은 표시에는 사용 가능해도 조건 비교에는 추가 구조화가 필요하다. 원본에 없는 정보와 정제 과정에서 잃어버린 정보를 반드시 구분한다.

### 9.2 필수 검증 사례

- 원문의 부정문·예외·금액 단위·기간·목록 관계가 정제 후 유지되는가.
- 전국·시도·시군구 적용과 기관 소재지를 구분하는가.
- 가족 특성의 복수 선택과 결합 코드의 의미를 보존하는가.
- 자녀 수의 산정 범위, 연령 대상·단위·경계·기준일을 식별할 수 있는가.
- 임신 여부의 예·아니요·미입력을 구분하고, 정책의 대상자와 임신·출산·산후 조건을 구별할 수 있는가.
- 소득 산정 기준·연도·가구 규모와 구간 경계를 식별할 수 있는가.
- 조건 누락·명시적 비해당·제한 없음을 구별하는가.
- 지원 기간과 신청 기간, 자격 비교와 접수 상태를 구별하는가.
- 원본 링크가 해당 정책의 공식 출처로 연결되는지 별도 확인할 수 있는가.
- 규칙 근거가 현재 표시 원본과 연결되며 변경·충돌을 감지할 수 있는가.

이 사례는 데이터가 필요한 의미를 표현할 수 있는지 점검하는 기준이다. 실제 조건 비교 엔진의 경계값·AND/OR 동작 테스트는 이후 구현 단계에서 별도로 수행한다.

### 9.3 완료 기준

1. 현재 저장된 8개 정책 모두에 대해 필수 표시 항목과 지역·가족·자녀·임신·소득 조건의 판정표가 있다.
2. 의미 손실·오매핑 등 정제 오류는 수정하거나 해당 정책의 사용을 보류한다.
3. 추가 구조화 항목과 원본 부족 항목마다 처리 방식이 정해져 있다. 정보 부족을 임의의 통과·탈락 값으로 채우지 않는다.
4. 표시 가능한 정책과 조건 비교 가능한 정책의 범위를 각각 명시한다. 확인되지 않은 정책을 비교 가능으로 집계하지 않는다.
5. API를 추가할 때 공통 필드 매핑표와 실제 표본 검증을 작성하고, 출처별 미지원 항목·충돌·예외를 기록한다.

8개 표본 통과는 전체 정책이나 다른 API의 적합성을 보장하지 않는다. 새 출처·새 필드 형식·새 조건 유형을 도입하면 해당 범위의 검증을 추가한다.

## 10. 다음 단계와 미결정 사항

저장된 8개 정책의 데이터 적합성 대조는 완료했으며, 결과와 미해결 항목은 위 검증 보고서에 기록했다. 표시 기반은 확보했으나 검수된 검색 규칙은 아직 없다. 보고서의 공통 계약 보완안과 Stitch 화면 매핑을 적용하여 다른 API의 표본 매핑·정제를 설계한다. 검색 비교 기능 구현은 확인된 데이터 범위와 미확인 처리 방식을 바탕으로 진행한다.

아직 결정하거나 검증해야 할 사항은 다음과 같다.

- 최초 서비스 지역과 지역 코드 사전.
- 가족 형태 선택지, 소득 구간·산정 기준, 추가 입력 항목.
- 정책별 조건 근거의 검수 담당과 공개 절차.
- 다른 API의 우선순위, 동일 정책 연결과 출처 충돌 해결 기준.
- 관련성 정렬의 세부 가중치와 공개 데이터의 재확인 주기.

이 항목들은 현재 확정된 구현이나 검증 결과로 취급하지 않는다.
