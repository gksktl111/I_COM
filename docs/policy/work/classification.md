# 정책 관련성·분야 라벨·검수 운영

관련성 후보 선별 → 여섯 분야 분류 → 원문 검수 저장의 세 단계를 구분한다. 관련성 버전은 `policy-relevance-3`, 분류 사전의 논리 초안은 `interest-taxonomy-v2-draft`, 구현된 평가 버전은 `interest-taxonomy-2/rules-1`이다. `ACTIVE`, `VERIFIED`, 공개 승인, 자격 비교 가능 상태는 서로 대체하지 않는다.

이 문서의 명령은 저장소 루트에서 실행한다. 날짜별 재분류·1,000건 AI 보조 검수·독립 표본 조정·마이그레이션·검증 결과는 [구현·검증 이력](../records/classification-and-operations-history.md)에 보존한다. 당시 건수는 현재 DB 집계나 인간 검수·최종 정확도 증명이 아니다. 공개 조회와 질문의 현재 동작은 최신 추천·UI 문서를 따른다.

## 1단계: 서비스 관련성 후보 선별

### 분류 기준

서비스 범위는 부부·부모의 지원뿐 아니라 아동·청소년 본인 대상 정책을 포함한다. 부모·가족 단어가 없어도 실제 아동 대상과 지원 내용이 확인되면 관련 후보로 분류한다. 소득·거주지·신청 자격의 충족 여부는 이 분류에서 판정하지 않는다.

분야는 임신·출산, 양육·보육, 아동 돌봄, 아동 의료·건강, 아동 교육, 가족 지원, 신혼·자녀가구 주거의 7개이며 복수 분류를 지원한다.

v3는 아동 상담·의료·급식·장학·문화·체육·생활 지원, 초중고 약칭과 명시적 아동 연령 경로를 인식한다. 법령 인용이나 수급 자격 명칭만으로 아동을 추정하지 않으며, 실제 아동 대상 문장에 법·수급·차상위라는 단어가 있다는 이유만으로 근거 전체를 버리지 않는다. 기존 관련성에서는 문화·체육·일상생활을 아동 돌봄에, 상담·심리·위생을 아동 의료·건강에 포함한다. 이 넓은 관련성 분류를 여섯 분야 라벨로 자동 변환하지 않는다. 아동 제외 괄호 문구·일반 대학생·성인 자녀·산업/기업 지원·임산물·장례 안치료는 긍정 근거가 아니다.

이 7개 관련성 분야는 맞춤 정책 UI의 6개 관심 분야와 별도다. UI에는 아동 교육을 독립 선택지로 제공하며, 후속 검수 라벨의 제안 코드는 `child_education`이다. [라벨링 기준](classification.md)의 연결표는 재검수 출발점이며 기존 평가·저장 데이터를 자동 변환하지 않는다. 현재 UI 조회의 키워드 탐색을 검수 라벨 기반 조회로 해석하지 않는다.

- 직접적인 사업명 또는 지원 대상과 실제 지원 내용의 교차 근거를 사용한다.
- 요약·목적의 배경 설명, 구비서류, 선정기준의 부수적 언급만으로 관련을 확정하지 않는다. 제외 문구와 제외 목록도 긍정 근거로 사용하지 않는다.
- `창업 보육실`은 육아 보육이 아니다. `자녀`라는 관계 표현만으로 아동 연령을 추정하지 않는다. 보호종료 청년의 과거 아동 경력도 현재 아동 대상의 증거로 사용하지 않는다.
- 일반 주거·생활비·의료 지원은 일괄 제외하지 않는다. 명시적인 신혼부부 지원 경로가 있는 복합 주거 사업은 관련 후보가 될 수 있다.
- 기업·창업·소상공인 금융, 산업·수출·광업, 농림축수산 생산시설·경영, 노인·보훈, 장례, 대학·대학원 학비, 일반 성인 취업·자립 정책은 사업명과 실제 지원 대상에 명시된 범위 밖 근거로 제외한다.
- 농어업인 보육·임산부 지원, 사업주 육아휴직 지원금처럼 신청 주체가 성인이어도 실제 가족 지원 경로가 있으면 보존한다.
- `임산물`을 임신·출산으로, 장례의 `안치료`를 의료의 `치료`로 인식하지 않는다. 아동 진료·입원과 초중고 교육·통학 근거는 관련 판정에 반영한다.

### 저장과 수집 연결

`policies.relevance`와 `relevance_assessed_at`은 현재 표시 데이터의 평가다. `policy_relevance_observations`는 원본 스냅샷·정제 버전·표시 해시·평가 버전에 묶인 이력이다. 저장 원본이나 정제 결과를 수정하지 않고 별도 평가를 추가한다.

`catalog_status`는 관련성 평가에서 DB가 자동 계산한다. 무관 정책을 별도 플래그로 활성화할 수 없으며, 원본 변경으로 평가가 무효화되면 자동으로 검토 대기로 돌아간다. 서버 전용 `policy_active_candidates` 뷰는 활성 후보만 반환한다. 기존 원본·정제 내용·평가 이력은 보존한다.

모든 실제 수집기의 공통 `createRepository()`가 `apply`에 평가 결과를 추가한다. DB에서는 정책 반영과 평가 이력을 같은 트랜잭션에 저장한다. 과거 스냅샷에 대한 늦은 재평가는 거절하며, 원본 또는 정제 결과가 바뀌면 이전 현재 평가는 해제한다. 같은 버전·같은 입력에 다른 평가를 덮어쓰지 않으므로 분류 규칙을 바꿀 때 평가 버전과 DB 허용 버전도 함께 올려야 한다.

신규 정책 수집에는 제외 단계를 적용했다. 자동 수집은 최신 목록의 정책명만으로 무관함이 명확하면 상세 API 호출과 정책 신규 저장을 생략한다. 목록만으로 애매하면 상세 원문을 확인하고, 상세 평가가 무관이면 신규 정책 목록에 반영하지 않는다. 검토 필요는 자동 제외하지 않고 저장해 보류한다. 공통 저장 경로도 무관한 새 정책의 반영을 차단하므로 선택형 수집에 적용된다.

목록 단계 제외는 이미 저장된 목록 페이지를, 상세 단계 제외는 수집된 원본 스냅샷을 보존한다. `policy_sync_items.scope_relevance`·`scope_phase`와 처리 이력에 제외 근거를 기록하며 재개 시 같은 제외 항목을 반복 처리하지 않는다. 처리 완료를 위한 내부 항목 상태는 SUCCESS지만 실행 요약과 관리자 표시는 저장 성공과 제외를 나눠 집계한다.

기존 정책은 삭제하거나 제목만으로 갱신 여부를 결정하지 않는다. 자동 CLI의 새 `new-only` 실행에서는 같은 출처+외부 ID의 저장 정책을 `skippedExisting`로 집계하고 상세 호출·정책·원본·평가·라벨 갱신을 생략한다. 명시적 `refresh`, 모드 없는 과거 실행의 재개, 기존 갱신 수집 경로에서는 전체 상세를 확인해 관련성을 재평가한다. 기존 무관 정책과 원본·평가 이력은 감사용으로 보존한다. 관리자 활성 필터는 공개 승인이 아니며 공개 조회 연결 시 관련·검토·무관 상태를 구분해야 한다.


### 관리자와 재평가

`/admin/policies`에서 전체 기준 관련성 건수, 상태·분야 필터, 정책별 분류 이유·근거 필드·원문 문장·평가 시각·버전을 확인한다. 긴 근거는 화면에서만 줄이고 안내하며 저장 이력은 보존한다. 기술 품질 이력과 서비스 관련성은 별도다. 관리자 로그인 검증과 서버 전용 DB 권한을 유지한다. `/admin/collection`에는 실행별 저장 성공·제외 건수와 최근 제외 30건의 정책 ID·출처·목록/상세 단계·근거를 표시한다. 수동 판정 변경 기능은 이번 범위에 포함하지 않는다.

```bash
# DB 읽기와 로컬 보고서만 작성
node --experimental-strip-types scripts/policy/relevance.ts
# 현재 스냅샷을 다시 읽고 평가 이력 저장
POLICY_SYNC_ENABLED=true node --experimental-strip-types scripts/policy/relevance.ts --apply
```

로컬 감사 보고서는 `.local/policy-sync/relevance-report.json`에 비공개 권한으로 저장한다. 재실행은 이미 저장된 동일 버전 평가를 중복 추가하지 않는다.

## 2단계: 여섯 분야 사전과 검수 기준

### 1. 목적과 적용 범위

분류 작업은 실제 지원 목적의 분야·세부 유형, 지원 대상·경로, 자격 규칙의 검수를 구분한다. 입력·공개 조회의 구현 상태는 [질문 사전](question-bank.md)과 [추천 구현 계획](recommendation-plan.md)를 따른다.

1. 실제 지원 목적에 맞는 **분야·세부 유형**을 검수해 다른 분야의 정책이 섞이는 문제를 줄인다.
2. **지원 대상과 적용 범위**를 구분해 아동·청소년 본인과 가족을 위한 정책을 찾는다.
3. 근거와 조건 관계를 검수한 **자격 규칙**을 입력값에 연결한다. 분류 라벨만으로 신청 가능 여부를 판정하지 않는다.

사용자는 한 분야를 선택하고, 정책에는 복수 분야를 부여할 수 있다. 예를 들어 임산부 진료비 지원은 임신·출산과 의료·건강의 실제 지원 경로를 모두 가질 수 있다. 결과를 줄이기 위해 정책마다 분야 하나를 강제하지 않는다.

서비스 범위는 임신·출산 가구뿐 아니라 일반 아동·청소년 본인, 자녀를 양육하는 보호자와 가구를 포함한다. 장애·저소득·한부모 등의 특성은 선택적인 대상 조건이지 모든 정책의 기본 요건이 아니다. ‘아동’, ‘청소년’, ‘자녀’의 연령을 하나의 임의 상한으로 통일하지 않고 원문의 정의를 보존한다.

#### 기존 문서와의 관계

- 서비스 관련성은 위 1단계의 기존 7개 분야 평가다. 활성 후보라는 사실은 6개 분야 라벨 검수 완료를 뜻하지 않는다.
- [공통 논리 데이터 계약](data-model.md): 원본 근거, 대상 인물, 조건 관계, 정보 상태, 버전과 검수 원칙을 따른다.
- [검색 요구사항](data-model.md): 자격 비교와 공식 출처 표시 원칙을 따른다.
- [질문 사전](question-bank.md): 1단계 관심 분야·거주지, 2단계 분야별 상세 정보와 연결한다. 과거 문서의 입력 순서보다 현재 UI 문서를 우선한다.

이 문서는 현재 6개 카테고리의 분류 사전과 검수 기준을 구체화한다. 기존 수집·관련성 평가·공개 승인 상태를 덮어쓰는 문서가 아니다.

### 2. 분류 단위와 공통 판정 원칙

#### 분류 단위

기본 단위는 하나의 정책이다. 다만 통합 신청 서비스나 복합 사업은 **실제 지원 경로별 하위 서비스**를 분류 단위로 나눈다. 분야·대상·조건은 같은 경로에 묶어 저장한다.

예를 들어 한 통합 사업에 ‘임산부 건강검진’과 ‘다자녀 주거 지원’이 함께 있어도 임산부의 연령 조건을 주거 지원 경로에 적용하지 않는다. 결과 카드가 정책 단위라면 해당 분야에 해당하는 하위 서비스를 이유로 표시하고 같은 정책을 중복 노출하지 않는다.

#### 근거 우선순위

1. 현재 적용 중인 원문의 지원내용·지원대상·선정기준에서 실제 급여나 서비스를 확인한다.
2. 사업 목적과 공식 제목으로 의미를 보완한다.
3. 제공자 분류 코드와 키워드는 자동 분류 후보를 만드는 보조 근거로 사용한다.

제목만으로 내용이 충분히 특정되지 않으면 검토 대상으로 남긴다. 서류 목록, 정책 배경, 제외 대상, 부정문, 기관명에 나온 단어만으로 라벨을 확정하지 않는다. 원문이 충돌하면 최신 수집일만으로 한쪽을 선택하지 않는다.

각 분야 라벨에는 그 분야의 실제 지원 목적을 입증하는 근거가 필요하다. 보조 분야도 주 분야와 동일한 근거 수준을 요구한다. 대상자가 부모라는 이유만으로 양육·보육을, 현금 지급이라는 이유만으로 주거·생활지원을 추가하지 않는다.

### 3. 상위 카테고리 기준

코드는 라벨링 식별자이며 화면 문구와 분리해 버전 관리한다. 아동 교육의 라벨 코드는 `child_education`이며 현재 UI 선택값은 `아동 교육`이다. 저장 구현의 평가 버전은 `interest-taxonomy-2/rules-1`이다. UI 카테고리 추가만으로 저장 정책에 검수 라벨이 부여되지는 않는다.

| 임신·출산 / `pregnancy_birth`     | 임신 준비·임신·출산·산후 회복이라는 사건을 직접 지원                                | 일반 자녀 양육, 서류의 출생증명서, ‘임산물’                                     | 출생 자체에 대한 일회성 지원은 여기, 이후 지속적인 양육 지원은 양육·보육        |
| 양육·보육 / `parenting_childcare` | 아동의 양육, 어린이집·유치원 기본 이용과 보호자의 양육 역할을 직접 지원                    | 기업 창업보육, 단지 부모가 신청하는 일반 사업                                   | 어린이집·유치원 기본 이용은 여기, 보호 공백 해소는 돌봄, 아동·청소년 교육비·학습은 아동 교육        |
| 돌봄 / `care`                     | 아동의 일상 보호·돌봄 공백 해소를 위해 사람·시간·장소·서비스 비용을 지원            | ‘돌봄’이라는 홍보 문구, 노인 전용 돌봄, 단순 강좌                               | 방과 후 보호·돌봄은 여기, 학습비·교육비만 지원하면 아동 교육                    |
| 아동 교육 / `child_education`    | 아동·청소년의 교육 참여, 교육비·학용품·통학·학습을 직접 지원                      | 성인 전용 학비·취업 교육, 보호자 양육 교육, 단순 아동 언급                      | 어린이집·유치원 기본 이용은 양육·보육, 방과 후 보호 공백 해소는 돌봄           |
| 의료·건강 / `health`              | 아동·청소년 또는 서비스 범위 내 임산부 등의 검진·예방·진료·치료·재활·건강 비용 지원 | 병원 소재지, 장례의 안치료, 성인 전용 사업                                      | 임산부 치료비는 임신·출산과 복수 분류 가능. 치료 근거 없는 일반 체험활동은 제외 |
| 주거·생활지원 / `housing_living`  | 서비스 범위 내 가구·아동의 주거 안정, 생계, 식생활, 필수 생활비를 직접 지원         | 모든 현금 급여, 일반 사업자 금융, 가족·아동 지원 경로가 확인되지 않은 주택 사업 | 보육료는 양육·보육, 교육비는 아동 교육, 진료비는 의료·건강. 급여의 지급 형태보다 목적을 우선        |

#### 서비스 범위가 넓은 정책

일반 생계·주거·의료 사업을 일괄 제외하지 않는다. 아동·가족이 실제 포함되는 지원 경로가 원문에 확인되면 `general_inclusive` 대상으로 분류할 수 있다. 단순히 아동 제외 문구가 없다는 이유만으로 포함을 확정하지 않는다. 반대로 ‘부모’, ‘가족’ 단어가 없어도 아동 본인 지원 근거가 있으면 포함한다.

성인 전용, 노인 전용, 기업 전용 등 명시적으로 범위 밖인 경로는 제외한다. 신청자가 사업주여도 실제 지원이 육아휴직 등 가족 지원인 경우 신청 주체와 수혜자를 구분해 검토한다.

### 4. 세부 유형 사전

한 하위 서비스가 여러 실질적 지원을 제공하면 세부 유형도 복수 부여할 수 있다. `other`는 목적이 분명하지만 사전에 없는 유형이며 근거와 사전 확장 요청을 필수로 남긴다. 정보 부족을 `other`로 채우지 않는다.

| 상위 분야     | 세부 유형 코드                                                                           | 의미                                                                          |
| ------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 임신·출산     | `preconception`, `infertility`                                                           | 임신 준비·사전 지원, 난임 관련 지원                                           |
| 임신·출산     | `prenatal`, `birth_grant`, `postpartum`                                                  | 임신 중 지원, 출산 사건에 대한 급여, 산후 회복·조리 지원                      |
| 양육·보육     | `child_allowance`, `childcare_fee`                                                       | 양육비·수당, 어린이집·유치원의 기본 보육·교육 이용 비용                           |
| 양육·보육     | `childcare_access`, `parenting_service`                                                  | 보육시설 이용·접근, 양육 상담·교육·휴직 등 보호자의 양육 지원                 |
| 아동 교육     | `education_participation`, `learning_support`                                            | 아동·청소년 교육비·학용품·통학 등 참여 지원, 학습 지원                        |
| 돌봄          | `home_visit`, `center`, `afterschool`, `emergency`                                       | 방문 돌봄, 시설·센터 돌봄, 방과 후 돌봄, 긴급·일시 돌봄                       |
| 의료·건강     | `checkup`, `vaccination`, `treatment`, `medical_cost`, `rehabilitation`, `mental_health` | 검진, 예방접종, 진료·치료, 의료비, 재활, 정신건강 지원                        |
| 주거·생활지원 | `housing_access`, `housing_cost`, `moving`, `utilities`, `livelihood`, `food`            | 주택 공급·접근, 임대료 등 주거비, 이사, 공과금·에너지, 생계비, 급식·식품 지원 |

‘평일·야간·주말’은 돌봄의 세부 유형이 아니라 서비스 제공 시간 속성이다. ‘가정 양육·어린이집·유치원·학교’는 아동의 이용 상태이며 정책의 지원 유형과 별도로 기록한다. 질병명·장애 여부·소득은 분야 자체가 아니라 대상 또는 조건이다.

현재 6개 카테고리에 명확히 들어가지 않는 서비스 관련 정책은 `OUT_OF_TAXONOMY`로 보존하고 사전 검토 대상으로 둔다. 양육·보육이나 주거·생활지원에 편의상 몰아넣지 않는다.

### 5. 기존 7개 관련성 분야와의 연결

아래는 재검수의 출발점이며 자동 일대일 변환 규칙이 아니다.

| 기존 관련성 분야   | 우선 검토할 현재 카테고리       | 확인 사항                                                                            |
| ------------------ | ------------------------------- | ------------------------------------------------------------------------------------ |
| 임신·출산          | 임신·출산                       | 실제 지원 내용에 따라 의료·건강 등 복수 분야 검토                                    |
| 양육·보육          | 양육·보육                       | 단순 아동 언급과 직접 양육 지원 구분                                                 |
| 아동 돌봄          | 돌봄                            | 교육 강좌와 보호·돌봄 서비스 구분. 기존 문화·체육·일상생활 지원은 목적별 재분류      |
| 아동 의료·건강     | 의료·건강                       | 아동 대상 경로와 치료·예방 목적 확인                                                 |
| 아동 교육          | 아동 교육                       | 초중고 등 아동·청소년 지원 보존. 성인 전용 학비는 해당하지 않음                      |
| 가족 지원          | 실제 목적에 따라 분기           | 양육 상담, 정신건강, 생계 등으로 재검수. 관계 개선 등 사전 밖 목적은 OUT_OF_TAXONOMY |
| 신혼·자녀가구 주거 | 주거·생활지원                   | 신혼·자녀가구의 실제 지원 경로 확인                                                  |

기존 아동 돌봄에 포함된 관람료·문화·체육 활동 지원은 보호·돌봄 서비스로 자동 변환하지 않는다. 명확한 아동·청소년 교육 참여 목적이면 아동 교육, 생계 목적이면 주거·생활지원으로 검토한다. 순수 문화·체육 지원처럼 현 사전에 맞지 않으면 OUT_OF_TAXONOMY로 보존하며, 서비스 무관으로 판정하지 않는다.

기존 관련성 판단의 원본·버전·이력은 그대로 보존한다. `ACTIVE` 등 수집 후보 상태, 6개 분야 검수 상태, 공개 가능 상태, 조건 비교 가능 상태를 별개로 취급한다.

### 6. 라벨링 기록 규격

이 절은 논리 규격이다. 구현은 `assessment.categories`, `assessment.labels[]`의 분야·세부 유형·경로·원문 인용, `targets`, `reason`을 저장한다. 별도 `subcategories[]`나 `primary_category`, 구조화한 자격 규칙·인물별 관계·공개 승인 필드는 아직 구현하지 않았다. 자동 제안과 검수 이력은 분리하며 현재 유효한 원본·평가 버전과 일치하는 기록만 현재 라벨 뷰에 나타난다.

#### 분야·대상 기록

| 항목      | 기록 내용                                                                                                                                                                |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 식별      | 정책 ID, 출처·외부 ID, 하위 서비스 ID 또는 정책 전체 범위                                                                                                                |
| 기준 원본 | 적용 스냅샷 ID·해시, 정제 버전, 원문 적용 연도·시점                                                                                                                      |
| 분야      | `categories[]`, `subcategories[]`와 각 상위 분야 연결. 대표 목적이 확인되면 `primary_category` 하나                                                                      |
| 대상      | `child`, `adolescent`, `pregnant_person`, `preconception_person`, `parent_guardian`, `newlywed_household`, `child_household`, `general_inclusive` 등 근거 있는 복수 대상 |
| 역할      | 신청자·수혜자·대리인·가구 구분. 역할별 대상 연결                                                                                                                         |
| 근거      | 원본 필드 경로, 문장, 공식 출처 링크, 어느 라벨을 지지하는지                                                                                                             |
| 판단      | 분류 상태, 판단 이유, 미해결 사유, 자동 제안 여부·사용한 규칙/모델 버전                                                                                                  |
| 검수      | 검수자, 검수 시각, 사전 버전, 적용 원본 버전, 변경 이유                                                                                                                  |

VERIFIED 분류에는 근거가 있는 categories가 하나 이상 필요하다. OUT_OF_TAXONOMY, OUT_OF_SCOPE 및 근거 부족 NEEDS_REVIEW는 분야 배열이 비어 있을 수 있으며 사유를 필수로 남긴다. 미확정 후보 라벨은 확정 라벨과 별도로 기록한다. 대표 목적을 하나로 정할 근거가 없으면 primary_category는 비워 둘 수 있고, 이것만으로 근거가 명확한 복수 분야의 검수를 막지 않는다.

주 분야는 정책의 대표적인 지원 목적이다. 독립적인 복수 목적의 우선순위가 불명확하면 임의로 정하지 않고 검수한다. 검색은 주 분야뿐 아니라 검수된 모든 해당 분야를 사용한다. 원문의 정책·하위 서비스별 연결 없이 라벨을 평면적으로 합치지 않는다.

#### 분류 상태

| 상태              | 의미                                                   | 분야 검색 적용                          |
| ----------------- | ------------------------------------------------------ | --------------------------------------- |
| `PROPOSED`        | 자동·수동 초안, 검수 전                                | 검수 작업 목록에만 사용                 |
| `VERIFIED`        | 현재 원본의 해당 분류 범위를 검수 완료                 | 공개 요건도 통과한 경우 적용            |
| `NEEDS_REVIEW`    | 근거 부족·충돌·해석 보류                               | 확정 분야 결과에 자동 포함하지 않음     |
| `STALE`           | 원본 또는 사전 변경으로 기존 검수의 유효성 재확인 필요 | 영향받는 라벨의 검색 적용 중단          |
| `OUT_OF_TAXONOMY` | 서비스 관련성이 있으나 현행 6개 분류로 표현 불가       | 별도 검토·사전 확장 대상으로 보존       |
| `OUT_OF_SCOPE`    | 실제 지원 경로가 서비스 범위 밖                        | 해당 범위 검색에서 제외, 원본·이력 보존 |

자동 분류의 신뢰도 점수는 검수 상태를 대체하지 않는다. 상태는 정책 전체와 하위 서비스 중 어느 범위에 적용하는지 함께 기록한다. 한 경로의 보류·제외를 다른 검수 완료 경로로 전파하지 않는다.

구현된 `VERIFIED`는 원문 의미 검수 결과의 상태이며 `review_kind`로 `HUMAN`과 `AI_ASSISTED`를 구분한다. `STALE`은 별도 저장 상태가 아니라 스냅샷·전체 정제값 해시·정제 및 평가 버전 불일치에 따른 현재 뷰 제외다. 아래 조회 적용 규칙은 제안 기준이며 공개 연결 여부는 별도로 확인한다.

### 7. 자격 조건 구조화와 현재 질문의 연결

분야 라벨 검수와 조건 규칙 검수는 별도다. 아래 입력값이 있다는 이유로 비교 가능한 규칙이 생기지는 않는다.

| 현재 입력                | 정책에 필요한 의미                                   | 초기 적용 원칙                                                                  |
| ------------------------ | ---------------------------------------------------- | ------------------------------------------------------------------------------- |
| 관심 분야 하나           | 검수된 categories와 하위 서비스                      | 일치 분야의 후보 조회                                                           |
| 시도·시군구              | 적용 지역, 주민등록/실거주 기준, 기준일·거주기간     | 기관 소재지를 지역 조건으로 사용하지 않음. 주소 표기와 지역 코드 버전 연결 필요 |
| 가족 상황·출산 예정 시기 | 대상 사건, 임신·출산·산후 구분, 주수·사건 기준일     | ‘3개월 이내’ 같은 거친 구간을 정확한 예정일·임신 주수로 변환하지 않음           |
| 자녀 생년월일·출생월     | 어느 자녀의 연령인지, 만 나이/월령, 비교 기준일·경계 | 출생월만으로 경계 판단이 불가능하면 확인 필요                                   |
| 총자녀 수·전체 입력 여부 | 총자녀 수, 대상 자녀 수, 출생순위 중 정확한 속성     | 등록된 자녀 목록 길이로 다자녀·출생순위를 추정하지 않음                         |
| 보육·교육 이용 현황 (양육·보육·아동 교육 공통) | 시설·학교 이용/미이용 조건, 대상 자녀·기준일              | 동일 자녀에게 연령·이용 조건을 함께 적용                                        |
| 돌봄 시간·유형           | 실제 제공 시간·방식·이용 조건                        | 선호와 불일치는 관련도 정렬에 우선 사용. 자격 탈락으로 바꾸지 않음              |
| 의료·건강 지원 유형      | 실제 지원 목적과 검수된 세부 유형                    | 목적 일치로 후보를 좁힘. 미입력 진단·질환 조건은 확인 필요                      |
| 주거 형태·생활 지원 목적 | 현 주거 형태, 무주택·주택 소유 조건, 지원 목적       | 월세 거주를 가구 전체 무주택으로 추정하지 않음                                  |
| 가구 특성·소득·복지 여부 | 대상 가구, 산정 방식·연도·규모, 필수/대체 경로       | 중위소득 구간·모름·해당 없음 구분. 월급·가구 형태로 자동 환산 금지              |

정보 상태는 공통 계약의 `KNOWN`, `EXPLICIT_NO_RESTRICTION`, `EXPLICIT_NOT_APPLICABLE`, `MISSING`, `UNRESOLVED`를 따른다. 빈 값은 제한 없음, 아니요, 0으로 채우지 않는다.

검수된 조건에는 대상 인물·범위, 연산자·단위·경계·기준일, 근거, 공통 필수 AND, 대체 OR, 제외·예외와 완전성이 필요하다. 한 대체 경로가 불일치해도 다른 경로가 미확인이면 정책 전체를 제외하지 않는다.

아동 교육은 기존 자녀별 보육·교육 이용 현황, 자녀 정보와 가구 특성 질문을 재사용한다. 이 답변을 교육비·학습 지원의 자격 판정이나 검수된 세부 유형으로 자동 변환하지 않는다.

현재 화면에서 묻지 않는 조건은 추가 확인 사항으로 남긴다. 카테고리별 상세 질문 목록은 정책의 검수된 조건을 축적한 뒤 보완하며, 현재 질문에 맞추려고 원문의 조건을 생략하지 않는다.

### 8. 조회·정렬 적용 정책

아래는 라벨 기준서에서 제안한 검색 적용 기준이다. 수집·라벨 저장 자동화의 실행 계약이나 공개 검색 구현 완료를 뜻하지 않는다. 최신 추천 설계·공개 검토 문서와 함께 적용 범위를 확인한다.

#### 1차: 분야 분류 적용

- 현재 활성 후보·공개 요건을 만족하고 선택 분야에 **유효한 VERIFIED 라벨**이 있는 정책만 해당 분야의 기본 결과로 조회한다.
- 분야가 미확정인 정책을 ‘정보가 부족하니 포함’이라는 이유로 모든 카테고리에 넣지 않는다. 원본은 보존하고 별도 검수 대기 건수로 관리한다.
- 분야는 확정됐지만 자격 정보가 부족한 정책은 결과에 남기고 ‘추가 확인 필요’로 표시한다. 분야 미확정과 자격 미확정을 구분한다.
- 결과가 적거나 없더라도 넓은 키워드 검색으로 자동 확장하지 않는다. 선택 분야 변경과 검수 범위 안내를 제공한다.
- 전체 대상 데이터에 필터를 적용한 뒤 중복 제거·건수 계산·페이지 나누기를 수행한다. 먼저 불러온 일부 목록만 필터링한 건수를 전체 결과 수로 표시하지 않는다.

#### 2차: 세부 목적·조건 적용

- 세부 지원 목적이 확인되면 일치 정책을 우선 정렬한다. 미확인 유형은 ‘추가 확인 필요’로 분리하고 자동 탈락시키지 않는다.
- 검수된 조건으로 모든 대체 경로의 불일치가 확정될 때만 기본 결과에서 제외할 수 있다. 제외 근거를 내부 기록으로 남긴다.
- 입력 누락·모름, 거친 날짜/소득 구간, 원문 충돌·예외 미해결은 `NEEDS_CHECK`다.
- 모든 필수 조건과 예외를 비교할 수 있는 범위에서만 `MATCH`를 허용한다. 이 상태도 공식 신청 승인이나 지급 보장을 뜻하지 않는다.
- 접수 마감과 자격 불일치는 별도 상태다. 접수 상태가 미확인이면 ‘접수 중’으로 표시하지 않는다.

임의 점수나 모델 신뢰도만으로 숨기지 않는다. 초기 정렬은 ‘세부 목적 일치 → 확인이 필요한 정책’처럼 설명 가능한 그룹을 우선하고, 수치 가중치는 실제 표본 평가 뒤 별도 결정한다.

### 9. 검수 절차와 변경 관리

1. **표본 구성:** 기존 관련·검토·제외 후보에서 원본이 있는 표본을 선정한다. 6개 분야, 아동 본인 지원, 복수 분야, 복합 서비스, 부정문·동음이의어, 근거 부족 사례를 포함한다.
2. **자동 초안:** 분야·세부 유형·대상·근거 문장·보류 이유를 제안한다. 키워드만 출력하거나 근거 없는 빈 항목을 채우지 않는다.
3. **독립 검수:** 검수자가 원문과 제안을 대조한다. 초기 기준 표본은 두 검수자가 독립 판정하고, 불일치는 조정 담당자가 사유와 최종 기준을 기록한다.
4. **규칙 조정:** 합의된 경계 사례로 사전을 수정한다. 기준 변경에 사용한 표본과 최종 품질 평가 표본은 분리한다.
5. **일괄 라벨링:** 확정 사전으로 확대하되 검수 완료 범위만 검색 적용 후보로 둔다. 자동 초안의 대량 생성을 검수 완료로 집계하지 않는다.
6. **조회 전 대조:** 현재 조회 결과와 라벨 기반 결과를 비교하고, 새로 포함·제외되는 정책 및 이유를 검토한다.
7. **원본 갱신:** 스냅샷이나 의미 관련 필드가 달라지면 영향을 받는 라벨·규칙을 재검수한다. 영향 판단이 불가하면 STALE 처리한다.

검수 책임은 분류 작성자, 원문 검수자, 불일치 조정 담당자, 조회 적용 담당자로 나눈다. 실제 담당자는 착수 전에 지정한다. 자동 처리와 수동 수정 모두 버전·근거·사유를 남기고 과거 이력을 덮어쓰지 않는다.

사전 버전을 바꾸면 영향받는 분류와 기존 결과를 다시 평가한다. 문제가 생기면 이전 사전·검색 적용 버전으로 되돌릴 수 있어야 한다. 단, 변경된 원본에 무효한 옛 검수를 다시 유효하게 만들지는 않는다.

### 11. 1차 완료 기준과 평가

다음 수치는 **착수용 제안 목표**이며 실제 달성 수치가 아니다. 실제 분포와 검수 비용을 확인한 뒤 적용 버전에 기록해 확정한다.



- 기준 정립 표본은 최소 100건으로 시작하고, 각 카테고리의 긍정 사례를 최소 15건 확보한다. 복수 분야 표본의 중복 집계 여부를 함께 기록한다.
- 위 표본에 더해 오탐 위험·부정문·범위 밖 사례 최소 25건을 검수한다. 표본 크기가 작으면 비율만으로 전체 품질을 단정하지 않는다.
- 튜닝에 쓰지 않은 별도 평가 표본에서 분야별 정밀도·재현율과 혼동 사례를 보고한다. 초기 목표는 각각 95%·90%이며, 분모·실제 건수와 함께 평가한다.
- 정밀도는 ‘그 분야로 분류한 것 중 정답’, 재현율은 ‘정답 분야 정책 중 찾아낸 것’이다. 재현율 평가는 자동 분류 음성·검토·미분류를 포함해야 하며, 현재 결과에 나온 정책만 검수하지 않는다.
- 아동 본인 지원 누락, 임산물·창업보육 오탐, 양육·보육·돌봄·아동 교육 경계 혼동, 경로 간 조건 혼합 등 명시된 회귀 사례는 평가 표본에서 모두 통과해야 한다.
- 검색 적용할 VERIFIED 라벨은 근거·원본·사전 버전·검수 이력이 모두 연결되어야 한다. 분야별 전체 대상 수, 검수 완료 수, 미확정 수, 공개·검색 적용 가능 수를 별도로 보고한다.
- 표본 목표 통과만으로 미검수 전체 데이터를 공개하거나 조건 비교를 활성화하지 않는다. 부족한 분야는 적용 범위를 제한하고 그 범위를 기록한다.

조건 비교 도입은 별도 완료 기준을 둔다. 날짜·연령·소득 경계, 같은 자녀 결합, AND/OR·예외, 정보 부족, 접수 상태, 원본 변경의 사례를 검증한 뒤 비교 가능 범위만 공개한다.

## 3단계: 라벨 저장·검수 실행과 충돌 처리

### 1. 구현 범위

구현 파일은 [마이그레이션](../../../supabase/migrations/20260908120844_policy_interest_labeling.sql), [실행 CLI](../../../scripts/policy/label.ts), [검수 계획 검증](../../../src/features/policy/server/labeling-plan.ts)이다. 분야·경계는 위 분류 사전을 따른다.

| 객체 | 역할 |
| --- | --- |
| `policy_label_observations` | 원본 스냅샷·정제 버전·표시 해시·전체 정제값 해시·평가 버전에 묶인 자동 제안 이력 |
| `policy_label_reviews` | 제안에 연결된 원문 검수 결과, 이전 검수 ID, 재실행 키, 검수자·종류·사유·시각 |
| `policy_current_labels` | 현재 `ACTIVE` 정책과 모든 유효성 값이 일치하는 제안 및 최신 검수 결과 |
| `policy_assign_labels` / `policy_label_backfill` | 단일 정책 또는 최대 100건씩 기존 활성 후보의 자동 제안 생성 |
| `policy_review_labels` | 원본·버전·검수 충돌·정확 인용을 검사한 후 검수 이력 추가 |
| `policy_label_on_activation` | 정책 INSERT 또는 관련성·정제값·적용 스냅샷 UPDATE 시 `RELATED` 정책에 자동 제안 생성 |

자동화는 DB 트리거에 연결되므로 활성화·원본 갱신에 별도 예약 작업이 필요하지 않다. 마이그레이션 이전 활성 후보에는 명시적 backfill이 필요하다. 대상 DB의 마이그레이션 적용 여부를 먼저 확인한다.

규칙은 현재 33개, 명명된 세부 유형은 27개다. 규칙은 지원내용과 대상·제목 근거를 연결해 `PROPOSED`, `NEEDS_REVIEW`, `OUT_OF_TAXONOMY` 중 하나를 만든다. 자동 규칙만으로 `VERIFIED`를 만들지 않는다. 규칙의 초안 건수는 최종 검수 결과와 별개이며 현재 원본·규칙으로 다시 집계한다.

### 2. 저장과 검수 계약

`assessment`에는 `version`, `status`, `categories`, `labels`, `targets`, `reason`이 들어간다. 각 `labels[]`는 `category`, `subcategory`, 지원 경로 설명인 `path`, 원문 `evidence[]`를 갖는다. 자동 제안에는 적용 `rule`도 포함한다. `categories`는 라벨에 나타난 분야와 일치해야 한다.

검수 결과는 `VERIFIED`, `NEEDS_REVIEW`, `OUT_OF_TAXONOMY`, `OUT_OF_SCOPE`를 허용한다. `VERIFIED`에는 하나 이상의 라벨이 필요하고, 사전 밖·범위 밖 결과에는 라벨을 두지 않는다. 각 라벨에 `benefit_text` 근거가 반드시 필요하다. 인용은 현재 정제 표시값의 정확한 부분문자열이어야 하며 DB는 `name`, `target_text`, `benefit_text`, `purpose_text`, `criteria_text`만 허용한다.

`review_kind`는 `HUMAN` 또는 `AI_ASSISTED`를 저장할 수 있다. 현재 CLI는 항상 `AI_ASSISTED`로 기록한다. AI 보조 검수를 인간 검수로 표시하지 않는다. 인용 일치는 원문 연결을 보증하는 검사이며 의미 판단의 정확도 보증은 아니다.

정책의 현재 스냅샷, 정제 버전, 표시 해시, **전체 `normalized` JSON의 해시**, 평가 버전이 모두 일치해야 현재 라벨이 유효하다. 전체 정제값 해시는 DB 내부 `md5(normalized::text)` 비교에 사용하며 인증용 값이 아니다. 조건 원문 등 표시 해시 외 값이 바뀌어도 옛 검수가 현재 라벨로 재사용되지 않는다. 과거 이력은 보존하며 `STALE` 행을 덮어쓰는 방식 대신 현재 뷰에서 제외한다.

두 테이블은 RLS를 켜고 `anon`·`authenticated` 접근을 차단한다. `service_role`에는 조회·추가만 부여하며 수정·삭제 권한은 부여하지 않는다. 뷰·RPC도 서버 전용이며 함수는 `SECURITY INVOKER`다. 운영은 검수 RPC로 새 이력을 추가하고 기존 이력을 수정하지 않는다.

### 3. 실행 순서

환경 파일 `.env.local`에 서버용 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`를 설정한다. 키를 문서·로그·브라우저에 넣지 않는다. 쓰기에는 `POLICY_SYNC_ENABLED=true`도 필요하다. URL은 자격증명·추가 포트 없는 HTTPS `*.supabase.co` 주소만 허용한다.

1. 대상 DB의 `20260908120844_policy_interest_labeling.sql` 적용 이력과 객체를 확인한다. 개발 DB에 적용 완료한 이력을 재적용하지 않는다.
2. 기존 활성 후보에 자동 제안을 생성한다. 같은 입력·평가 버전의 제안은 중복 생성하지 않는다.
3. 현재 스냅샷과 전체 정제값에 묶인 검수 bundle을 준비하고, 미리보기로 원본·계획 일치를 확인한다.
4. 검수를 저장하고 전체 활성 후보의 현재 라벨 누락과 결과 건수를 대조한다.

```bash
# 읽기 보고서: DB 쓰기 없음, 로컬 보고서 작성
npm run policy:label

# 기존 ACTIVE 후보의 자동 제안 backfill 후 보고서
POLICY_SYNC_ENABLED=true npm run policy:label -- --apply

# 검수 bundle의 원본·버전·계획 일치 검사: 검수 저장 없음
npm run policy:label -- --reviews .local/policy-labeling/review-bundle.json

# 준비한 검수 결과 저장
POLICY_SYNC_ENABLED=true npm run policy:label -- --reviews .local/policy-labeling/review-bundle.json --apply
```

`--reviews --apply`는 backfill을 함께 실행하지 않는다. 해당 원본의 현재 자동 제안이 먼저 있어야 한다. 읽기 보고서도 `policy_current_labels`를 사용하므로 마이그레이션이 없는 원격 DB에서는 실행할 수 없다.

bundle은 `{ reviewRun, items }` 형식이다. 각 item은 `sourceId`, `snapshotId`, 전체 `normalized`, `reviewer`, `reason`, `assessment`를 포함한다. 검수자가 기록한 부분 결과 배열을 그대로 CLI에 넣지 않는다. `.local/policy-labeling/review-bundle.json`은 로컬 준비 파일이며 다른 환경에 자동 존재하지 않는다. 적용 시 원본 유효성을 다시 검사한다.

CLI는 활성 후보와 현재 라벨을 500건씩 조회한다. 기본 보고서는 `.local/policy-labeling/report.json`이며 `--output`으로 파일 경로를 바꿀 수 있다. 보고서에는 전체 활성 수, 현재 라벨 수, 상태·분야별 수, 누락 ID와 라벨이 들어간다. 디렉터리·새 파일은 각각 `0700`·`0600`으로 생성한다. `applied`는 CLI의 `--apply` 여부이며 원격 마이그레이션 적용이나 인간 검수 완료를 뜻하지 않는다.

### 4. 재실행과 충돌 처리

첫 검수 쓰기 전에 CLI는 프로젝트 호스트와 `reviewRun`으로 구분한 `.local/policy-labeling/plan-<hash>.json`을 배타적으로 생성한다. 이 계획은 bundle 바이트 해시, 제안 ID, **처음 읽은 이전 검수 ID**를 고정한다. 재실행이 다른 검수자의 새 결과를 자동으로 기준 삼아 덮어쓰지 않는다.

각 검수는 `<reviewRun>:<sourceId>`를 재실행 키로 사용한다. 이미 같은 내용으로 저장했다면 기존 검수 ID를 반환한다. 같은 키로 다른 내용·검수자·사유를 보내면 거절한다. 정책 단위로 잠그고 이전 검수 ID를 검사하므로 새로운 검수가 먼저 저장된 경우 충돌한다. CLI 전체는 한 트랜잭션이 아니므로 중도 실패 전 일부 항목은 저장될 수 있다. 같은 bundle·계획을 보존한 채 재실행하면 완료 항목을 중복 저장하지 않는다.

| 오류·상황 | 처리 |
| --- | --- |
| `writes-disabled` | 승인된 쓰기 환경의 `POLICY_SYNC_ENABLED` 설정 확인 |
| `invalid-database-environment`, `database-http-*` | 대상 프로젝트·서버 키·마이그레이션·RPC 접근 상태 확인. 키나 응답 원문을 공개하지 않음 |
| `stale-review-source`, `stale-review-plan`, DB `STALE_LABEL_REVIEW` | 원본·정제값·평가 버전 변경 또는 현재 제안 부재 확인 후 영향 경로 재검수 |
| `review-plan-conflict`, DB `LABEL_REVIEW_KEY_CONFLICT` | 같은 실행 키의 bundle 변경 여부 확인. 기존 계획을 삭제해 충돌을 우회하지 않음 |
| DB `LABEL_REVIEW_CONFLICT` | 다른 검수 변경과 대조·조정 후 새 검수 실행을 준비 |
| `duplicate-review-source` | bundle 내 중복 정책 ID 제거 후 검수 범위 재확인 |
| `INVALID_LABEL_EVIDENCE`, `INVALID_LABEL_CATEGORY` | 인용·분야·세부 유형을 현재 원문 및 규칙과 대조 |
| `active-policies-missing-labels` | 작성된 보고서의 누락 ID 확인. 실행 중 활성 후보 변경이나 backfill 누락을 조사 |

CLI는 원격 오류 본문 대신 HTTP 상태 오류를 출력한다. DB 예외를 확인할 때도 서버 운영 경로에서 확인한다. 규칙 변경은 평가 버전을 올려 이전 제안·검수의 유효성을 분리해야 한다. 새 버전 backfill과 재검수 없이 이전 결과를 다시 현재 결과로 간주하지 않는다.
