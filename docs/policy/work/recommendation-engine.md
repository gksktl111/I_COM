# 정책 추천 엔진 기술 계약

갱신: 2026-09-11 · 범위: 정책 처리·순수 계산·서버 전달·검증 계약

이 문서는 구현 담당자의 기술 기준이다. 목표 흐름·현재 상태·작업 우선순위는 [추천 구현 계획](recommendation-plan.md), 질문 문구·선택지는 [질문 사전](question-bank.md)을 따른다. 여기의 논리 상태와 제안 타입을 DB 컬럼이나 구현 완료로 해석하지 않는다.

원본·정보 상태·근거 보존은 [공통 데이터 계약](data-model.md), 기존 분야 의미는 [라벨링 기준](classification.md)을 유지한다. [교육 20건 분석](../records/education-review.md#policy-education-mapping-audit-20260909)은 보존 자료의 설계 사례이며 현재 공식 자격이나 운영 승인 근거가 아니다.

## 1. 실행 경로와 공통 불변 조건

현재 경로와 검증 계약을 구분한다. 아래 차이는 정책 콘텐츠의 검수 생명주기이며 로그인이나 대화 중 권한 확인 절차가 아니다.

| 경로 | 실제 동작과 경계 |
| --- | --- |
| `CATEGORY_BANK_V1` 잠정 추천 | 기존 활성 공개 정책에서 분야·선택한 필요·일부 상세 답변·지역의 문구 관련성을 계산한다. 자격·소득·접수 상태를 확정하지 않고 추가 확인 태그를 제공한다. HUMAN 상태를 만들지 않으며 DB 상태 변경을 뜻하지 않는다. |
| 검증 추천 엔진 | HUMAN 공개 결정과 현재 버전에 맞는 규칙으로 자격·순위·적응형 질문을 계산하는 순수 엔진과 서버 경로가 구현되어 있다. 기본 승인 카탈로그는 비어 있으므로 실정책 검증 추천은 `AWAITING_REVIEW`다. |
| 후속 계약 | 부모·신청자·사건 역할 확장, 실제 정책 근거·검수 연결, 서명 커서와 상세 버전 의존성은 아래 계약에 맞춰 연결할 대상이다. |

잠정 추천의 현행 예외는 2026-09-09 사용자 결정에 따른다. 이후 HUMAN 공개 관문과 비수치 순위 규칙은 **검증 경로**에 적용한다. 잠정 추천 점수를 적격도나 검증 순위의 구현으로 설명하지 않는다.

- 상위 분야는 하나만 선택한다. 거주지는 선택 입력이며 세부 필요는 선택적 복수 선택이다. 필요를 고르지 않으면 필요 순위 요소를 사용하지 않는다.
- 자녀 관련 정책은 등록한 자녀 중 한 명 이상을 선택해 찾는다. 선택 목록은 탐색 범위이며 실제 총자녀 수나 정책상 다자녀 산정 수가 아니다.
- 같은 의미·대상·산정 기준·시점의 가구 질문만 공유한다. 학교·연령·장애 인정·입학 사건은 해당 자녀 ID에 연결한다.
- 질문 중에는 추천 카드를 표시하지 않는다. 질문 종료 또는 결과 보기 선택 후 고유 정책 최대 20개와 앞의 최대 5개를 표시한다. 부족한 수를 채우지 않는다.
- 같은 정책은 카드 하나이며 자녀별 `입력 기준 조건 일치`·`추가 확인 필요`를 구분한다. 가구 태그는 실제 가구 경로가 있을 때만 만든다.
- 모름·건너뛰기·수정을 허용한다. 추천 이용에 로그인이나 영구 프로필 저장을 요구하지 않는다.
- 다른 상위 분야 자동 혼합, 자격 규칙 자동 생성, 자유문 대화·학습 모델, 근거 없는 0~100 적격도 점수는 v1 범위 밖이다.

## 2. 정책·경로·근거의 단위

처리 구조는 **정책 → 지원 경로 → 수혜자·사건 → 조건 묶음·급여 분기**다. 카드 표시 단위와 조건 비교 단위를 분리한다.

2026-09-11 상위 조건 재정제는 `coarse-refinement-20260911.json`의 원문 결합 초안을 같은 템플릿 컴파일러로 처리한다. 지역·나이·장애 여부 자체를 전역 필터로 만들지 않고 경로의 필수 조건, 가구/개인 대상, 과거 기준일과 대체 자격을 보존한다. 예를 들어 장애인·한부모 보험료 지원은 별도 경로이며, 청년 또는 신혼부부의 청년 나이는 신혼부부에게 전파하지 않는다. 제목의 지역이나 선정 배점의 나이는 실행 조건을 만들 근거가 아니다. `UNCONFIRMED` 기준은 질문을 생성하지 않고 초안은 불완전·미검수로 유지한다. 전체 검토 목록에는 장애·대체 경로·거주 기준일·대상 범위별 신호와 중복 제거한 정책 건수를 기록하며, 신호 존재를 규칙으로 자동 변환하지 않는다.

| 단위 | 보존할 정보 | 금지하는 합성 |
| --- | --- | --- |
| 정책 | 내부 ID·출처 ID·표시 내용·공식 링크·원본 버전 | 같은 제목만으로 다른 지역 사업 병합 |
| 지원 경로 | 안정적 ID·실제 서비스·분야·세부 목적·신청/이용 경로 | 통합 신청과 개별 급여 혼합 |
| 수혜자·사건 | 신청자·수혜자·대리인·가구 역할·인물 ID·입학/출산 사건 ID | 부모 조건을 자녀 조건으로 대체 |
| 조건 묶음 | 공통 필수·AND·대체 OR·제외·예외·기준일·완전성 | 다른 자녀의 충족 조건 합산 |
| 급여 분기 | 금액·주기·인원·상한·적용 조건·해당 경로 | 급여 한도를 정책 전체 자격 상한으로 확대 |

한 정책에 복수 경로·분야·목적을 허용하지만 결과는 선택 분야의 실제 경로로 설명한다. 한 경로가 일치해도 다른 급여까지 받을 수 있다고 표시하지 않는다. 기관 수혜 사업은 원본으로 보존하되 가족이 직접 신청하거나 이용할 경로가 없으면 가족 추천에서 제외한다.

상위 분야는 임신·출산, 양육·보육, 돌봄, 의료·건강, 아동 교육, 주거·생활지원이다. 분야는 탐색 범위, 기존 세부 유형은 분류 호환, 세부 목적은 사용자 필요와 실제 제공 지원의 연결이다. 생애 단계·가족 상황은 관련성 정보이며 법적·사업상 조건은 별도 검수 규칙이다.

목적 사전과 분야·세부 유형 대응표는 버전 관리하며 일대일 대응을 가정하지 않는다. 사전에 없는 명확한 목적은 확장 검토로 남긴다. 사전 밖·서비스 범위 밖·근거 부족을 구분하고 미확인을 임의 `other`나 사용자 탈락으로 바꾸지 않는다.

`PublicPolicy`는 표시 문자열·URL 중심이다. `public-data.ts`의 활성 정제값 조회나 `matchesInterests`의 텍스트 매칭은 HUMAN 공개 관문 또는 실행 규칙의 대체가 아니다. `criteria_text`가 비어도 대상·지원내용에서 검수 후보를 찾을 수 있지만 문자열 존재만으로 비교 가능한 규칙이 되지는 않는다. `updated_at`은 신청 가능 시각이나 공식 갱신일이 아니다.

## 3. 생성·검수·공개·갱신

각 단계는 독립 상태와 근거를 가진다. 이전 단계의 통과는 다음 단계의 승인이 아니다.

| 단계 | 산출물과 통과 조건 |
| --- | --- |
| 수집 | 원본 응답·출처·스냅샷 ID/해시·수집 시각·오류/완전성. 일부 응답 실패도 보존한다. |
| 정규화 | 정제값/해시·정제 버전·필드별 원본 경로. 숫자·단위·부정·예외·관계를 보존한다. |
| AI 후보 | 분야·목적·대상·규칙 후보·인용·모델/프롬프트 버전. 검수 목록에 등록하며 실행 규칙으로 사용하지 않는다. |
| 인간 의미 검수 | 경로·분류·목적 판단·근거·검수자/시각. 모호함·충돌은 보류하고 보완 자료를 지정한다. |
| HUMAN 공개 결정 | 현재 버전에 결박한 공개 경로·표시·목적 범위. 공식 근거·표시 품질·가족 이용 가능성을 확인한다. |
| 규칙 승인 | HUMAN 규칙·범위별 완전성·예외·의존성. 현재 승인 범위만 확정 비교에 사용한다. |
| 추천 제공 | 공개 경로·판정 범위·이유·미확인 원인을 같은 유효성 기준으로 서버에서 계산한다. |

원본 제공자 갱신 시각, 내부 수집 시각, 검수 시각은 별개다. 결정에는 스냅샷·원본/정제 해시·정제/분류/목적 사전 버전·적용 범위를 연결한다. 규칙에는 규칙 버전·기준 연도·의존 근거·유효 범위를 더한다. 없는 버전을 만들어 채우지 않는다. 공식 링크는 URL 문법뿐 아니라 공식성·정책 일치·접속·신청 경로를 확인한다.

`AI_ASSISTED`의 `VERIFIED`는 인간 검수로 승격하지 않는다. 공개 결정은 해당 분야·목적·수혜 경로의 의미를 확인해야 한다. 공개 가능은 신청 가능·접수 중·지급 보장이 아니다. 공개 범위는 유효하지만 규칙이 불완전한 경로는 허용된 범위에서 `UNKNOWN`으로 안내할 수 있다. 규칙이 완전해도 공개 결정이 없으면 검증 추천에 넣지 않는다.

| 논리 공개 상태 | 행동 |
| --- | --- |
| 검수 대기 | AI 후보 또는 인간 결정 미완료 상태로 내부 보존 |
| 공개 보류 | 공식 근거·표시·대상·충돌 해결 전 해당 경로 중단, 담당과 해결 조건 기록 |
| 공개 가능 | 현재 근거와 HUMAN 결정이 유효하면 다른 관문·규칙 평가 |
| 재검수 필요 | 관련 의존성 변경·만료 범위 중단 후 재검수 |
| 공개 철회 | 잘못되거나 무효인 공개 범위 즉시 제외, 이력 보존 |

현재 API는 `released-catalog.ts`의 검수 결정 기반 loader를 사용한다. 해당 정책·관련 질문과 전이적 선행 질문·원본 메타데이터의 v2 초안 digest와 공개·규칙·질문 결정, 검수 유효 기간을 검사하고, 동일 ACTIVE 원본의 스냅샷·정제 버전·표시 해시·전체 정제 내용 SHA-256이 일치하는 정책만 남긴다. 원본 변경·만료로 빠진 건수는 자격 탈락과 구분해 응답한다. 검수된 조건 결과와 별도로 미검수·재확인 정책은 사용자 결정에 따라 직접 확인 태그로 표시할 수 있다. 조건 불일치로 탈락한 현행 검수 정책은 이 목록에 다시 넣지 않는다. 원본 조회는 유효 승인 정책이 있을 때 전체 페이지를 한 번 순회하고 동일 지문을 검증한다. 기존 `recommendation-release.ts`의 표시 fingerprint loader는 호환 검증용으로 보존한다. 어느 fingerprint도 승인 자체가 아니며 현재 실제 공개 결정은 0건이다.

`CATEGORY_BANK_V1`은 기본 질문 답변과 추가 규칙 답변을 함께 전달한다. 입력/카탈로그 문맥이 바뀐 추가 답변은 HTTP 409 `recommendation-context-changed`로 반환한다. 화면은 기본 답변을 유지하고 추가 답변·문맥·문항 수를 초기화하여 최신 질문을 다시 요청한다. 통신 실패의 일반 재시도와 구분하며, 사용자에게 기본 입력을 일부러 바꾸도록 요구하지 않는다.

갱신은 의존 범위별로 처리하며 기존 결정을 삭제하지 않는다. 영향이 불명확한 관련 범위는 재검수한다.

| 변경 | 중단 범위와 복구 조건 |
| --- | --- |
| 분야 라벨 근거·사전 무효 | 해당 분야 적용 중단 → 현재 의미 검수·공개 결정 |
| 조건 규칙만 만료·변경 | 확정 비교 중단, 유효한 공개 범위는 UNKNOWN → 현재 HUMAN 규칙 승인 |
| 공개 표시·목적·수혜 경로 근거 변경 | 공개 결정 무효화·해당 노출 중단 → 새 HUMAN 공개 결정 |
| 출처 충돌·정제 의미 손실 | 영향 값·규칙·표시 중단 → 충돌 해결·정제 수정·재검수 |
| 변환·추천 코드 오류 | 운영 담당이 영향 경로 중단·이전 검증 배포 복구 → 현재 근거와 호환되는 공개/규칙 묶음 |

규칙 만료만으로 유효한 공개 라벨을 모두 폐기하지 않는다. 반대로 공개 근거 변경을 규칙 UNKNOWN 처리만으로 넘기지 않는다. 롤백도 현재 근거와 유효해야 하며 옛 승인·신청 기간을 복원해 재개하지 않는다.

## 4. 사실·규칙·역할 타입

실행 타입의 기준은 [types.ts](../../../src/features/policy/recommendation/types.ts)다. 다음은 현재 핵심 구조의 요약이며 생략한 필드는 소스와 대조한다.

```ts
type Truth = "TRUE" | "FALSE" | "UNKNOWN";
type Eligibility = "ELIGIBLE" | "INELIGIBLE" | "UNKNOWN";
type Subject = { kind: "CHILD" | "HOUSEHOLD"; id: string };
type FactKey = {
  attribute: string; subject: Subject; basis: string; reference: string;
};
type FactValue =
  | { kind: "BOOLEAN"; value: boolean }
  | { kind: "CODE"; value: string }
  | { kind: "NUMBER_RANGE"; min: number | null; max: number | null;
      minInclusive: boolean; maxInclusive: boolean; unit: string }
  | { kind: "DATE_RANGE"; earliest: string; latest: string };
type Expression =
  | { kind: "PREDICATE"; ruleId: string }
  | { kind: "ALL" | "ANY"; children: Expression[] }
  | { kind: "NOT"; child: Expression }
  | { kind: "UNRESOLVED" };
type Evaluation<T> = {
  value: T; reasonCodes: string[]; evidenceRefs: string[];
  usedAnswerKeys: FactKey[]; unknowns: Unknown[];
};
```

`Answer`는 `key`·`recordedAt`·선택적 질문 ID/버전·활성 여부와 응답을 가진다. `PROVIDED`는 값과 `USER_DECLARED` 출처를 갖고, 나머지는 `UNASKED / DONT_KNOW / SKIPPED / EXPLICIT_NOT_APPLICABLE`이다. 명시적 아니요는 질문 의미에 맞는 제공 값이며 미선택과 구분한다.

`Predicate`는 FactRef, label, 근거, `HUMAN / FIXTURE / UNREVIEWED`, sourceVersion과 타입이 맞는 연산을 갖는다. 현재 연산은 `EQ / IN_SET / NUMBER_RANGE / DATE_RANGE`, 역할 참조는 `BENEFICIARY / HOUSEHOLD`다. 임의 코드 실행·분류 코드에서 즉석 조건 생성은 허용하지 않는다.

후속 확장에는 `SELF / PARENT` 등 역할, 신청자·수혜자·대리인 관계, 사건 ID와 역할 바인딩, `scopeCompleteness`·`alternativeCoverage`·집계 범위가 필요하다. 현재 CHILD/HOUSEHOLD 타입이 이 계약 전체를 구현했다고 설명하지 않는다. `RESIDES_IN` 같은 연산자도 등록·검증을 거쳐 추가할 제안이다.

논리 계약의 완전성은 `COMPLETE / PARTIAL / UNKNOWN`이다. 현재 엔진은 경로 `complete`, 정책 `completePaths`, 요청 `subjectsComplete`로 제한적으로 표현한다. 급여액·횟수 분기는 자격식과 별도로 평가한다.

확장 버전 문맥은 `releaseRevision / ruleVersion / purposeVersion / taxonomyVersion / questionVersion / rankingVersion`을 묶고 서버 평가 시각 `evaluatedAt`과 `Asia/Seoul` 기준을 공유한다. 현재는 catalog/source/question 버전과 평가 시각을 사용하며 전체 문맥·커서 계약은 후속이다. 사건 reference는 실제 입력된 대상·사건·날짜와 연결하고 미래 사건을 생성하지 않는다.

### 기존 입력의 정규화 계약

- 주민등록 지역은 해당 기준의 사실로만 변환하고 지역 코드·계층에 연결한다. 현재 지역을 과거 기준일 거주나 학교 소재지로 재사용하지 않는다.
- 자녀 ID를 유지하고 출생월은 가능한 날짜 구간으로 표현한다. 연령에서 학교급·학년·재학을 추정하지 않는다. 목록 완전성과 총자녀 수·출생순위는 별도다.
- 소득 구간 양끝 포함 여부·산정 기준·연도·가구 정의를 보존한다. 월급을 기준 중위소득 비율로 환산하지 않으며 기준 누락은 UNKNOWN이다.
- 일반 한부모와 법정 인정, 가구 내 장애와 해당 자녀의 장애 인정은 다른 사실이다. 복수 선택의 미선택은 false가 아니며 명시적 비해당도 질문 범위에만 적용한다.
- 기존 `unknown`·빈 값은 모름/건너뜀/미질문을 추정하지 않는 별도 이관 상태가 필요하다. 원 설계의 `LEGACY_UNSPECIFIED`는 현재 Answer 열거형에 없으므로 수용 가능한 어댑터 계약을 먼저 정한다.
- 분야 변경은 의미가 같은 공통값만 보존한다. 부모 답변·대상·사건 변경으로 적용되지 않는 종속 답변은 비활성화하며 숨겨진 답변을 비교에 넣지 않는다.

## 5. 관문·3값 자격·미확인

공개·분야·서비스 관문을 먼저 적용한다. 자격 계층에서 제외하는 상태는 `INELIGIBLE`뿐이며 공개 철회나 다른 분야의 정책을 반드시 보여야 한다는 뜻은 아니다.

| 관문·상태 | 처리 |
| --- | --- |
| HUMAN 공개 근거 무효·분야 라벨 없음/STALE | 해당 공개/분야 범위 중단·재검수; 사용자 탈락으로 설명하지 않음 |
| 가족 신청·이용 경로 없음 | 가족 추천 범위 제외; 원본 보존 |
| 목적 불일치·미확인 | 순위·설명에 반영; 자격 탈락 아님 |
| 규칙 불완전·오래됨·답변 미확인 | UNKNOWN 유지 |
| 유효 규칙으로 전 판정 범위 불일치 확정 | INELIGIBLE 제외; 명시한 범위만 설명 |

`ELIGIBLE`은 입력 정보 기준의 검수 범위 일치이며 공식 선정 확정이 아니다. 기존 `MATCH / NO_MATCH / NEEDS_CHECK`는 자격 문맥에서 각각 `ELIGIBLE / INELIGIBLE / UNKNOWN`에 대응한다. 순위 feature의 MATCH와 혼동하지 않는다.

| 식 | 3값 계산 |
| --- | --- |
| 원자 비교 | 유효한 검수 근거와 같은 대상·기준의 충분한 값일 때 TRUE/FALSE, 나머지 UNKNOWN |
| ALL(AND) | FALSE가 하나라도 있으면 FALSE, 모두 TRUE면 TRUE, 나머지 UNKNOWN |
| ANY(OR) | TRUE가 하나라도 있으면 TRUE, 모두 FALSE면 FALSE, 나머지 UNKNOWN |
| NOT | TRUE↔FALSE, UNKNOWN 유지 |

식은 같은 경로·수혜자 바인딩의 최종 자격식이다. `기본 조건 AND NOT(제외 AND NOT(예외))`처럼 검수된 관계를 보존한다. 미해결 예외는 UNRESOLVED로 남긴다. 빈 ALL/ANY를 자동 참/거짓으로 만들지 않으며 명시적 제한 없음은 근거를 가진 별도 조건으로 등록한다.

1. 공개 가능한 관련 경로와 일관된 대상·사건 바인딩을 정한다. 두 자녀의 사실을 합치지 않는다.
2. 규칙 버전·검수·근거를 확인하고 식을 평가한다. 사용자 정보 문제와 정책 재검토 원인을 따로 수집한다.
3. 필수조건·예외·범위가 완전하고 TRUE일 때만 해당 경로를 ELIGIBLE로 한다. 부분 규칙의 TRUE는 전체 충족으로 올리지 않는다. 검수된 필수조건 실패와 이를 뒤집을 예외가 해결된 경우의 경로 불일치는 정책 전체 제외와 구분한다. 현재 코드는 불완전한 경로의 TRUE/FALSE를 모두 UNKNOWN으로 보존하며, 이 경로별 불일치 증명의 세분화는 후속 연결 범위다.
4. 정책 전체 INELIGIBLE은 관련 대체 경로·수혜 대상이 빠짐없이 확인되고 모두 실패하며 이를 뒤집을 예외가 해결됐을 때만 허용한다. 비공개 대체 경로의 존재는 내용을 노출하지 않고 배제 판단의 불완전성으로 남긴다.
5. 완전한 경로 하나의 일치는 그 범위만 표시한다. 다른 경로·급여까지 일치로 올리지 않는다. 대표 경로의 상태와 ‘어떤 경로 하나는 일치’ 집계를 구분한다.
6. 선택한 자녀 범위가 완전하면 그 범위만 판정한다. 불완전 목록의 전원 실패를 가족 전체 탈락으로 올리지 않는다. 충돌 답변 중 하나를 임의 선택하지 않는다.

수치·날짜의 가능한 모든 값이 조건을 만족하면 TRUE, 모두 벗어나면 FALSE, 경계에 걸치면 UNKNOWN이다. 대상·산정 기준·단위·시점이 같아야 비교한다. E01형 50% 기준에 ‘80% 이하’ 응답은 UNKNOWN이다. 급여 한도·우선 선정 순위는 승인된 필수조건 근거 없이는 탈락 조건이 아니다.

| 미확인 원인 | 담당·해결 |
| --- | --- |
| USER_MISSING / USER_PRECISION | 필요한 최소 질문, 모름·건너뜀 허용 |
| USER_CONFLICT | 정정 질문; 명시적 모름/건너뜀을 자동 재질문으로 우회하지 않음 |
| POLICY_MISSING·정책 근거 충돌 | 운영 검수자가 공식 자료·우선 근거 보완; 사용자 질문 반복 금지 |
| UNREVIEWED_RULE / STALE_RULE | 영향 규칙 HUMAN 재검수, 유효한 공개 범위만 미확인 안내 |
| INCOMPLETE_PATHS / INCOMPLETE_SUBJECTS | 경로·예외 보완 또는 실제 판정 대상 범위 확인 |

`Unknown`은 ruleId·factKey·resolvableByQuestion을 선택적으로 포함하고 원인은 복수일 수 있다. 정책 충돌의 별도 `POLICY_CONFLICT` 코드는 후속 논리 계약이며 현재 열거형에는 없다. 누락을 0·false·무제한으로 바꾸지 않는다. 값이 알려짐, 명시적 제한 없음, 명시적 비해당, 누락, 미해결을 구분한다.

## 6. 순위·시점·카드

Hard는 HUMAN 검수된 필수·제외·예외, Soft는 선호에 따른 관련성, Ranking은 남은 후보의 표시 순서다. 부족한 Hard를 Soft로 낮추지 않는다. 같은 속성도 정책 근거에 따라 역할이 달라진다.

| 정보 | 검증 경로의 사용 경계 |
| --- | --- |
| 필요·목적 | 명시한 필요와 실제 경로 목적의 관련성, 최우선 feature |
| 거주 지역 | 인물·주민등록/실거주·지역 계층·기준일이 맞는 필수조건; 제공기관 위치로 대체 금지 |
| 이용 지역·방식 | 희망 접근성은 선호, 학교 소재지 같은 필수요건은 별도 Hard |
| 생애 단계·연령·입학 | 목적·이용 시점 관련성; 검수된 연령/사건 제한만 Hard |
| 가구·인정·소득·자녀 수 | 정책 정의에 맞는 Hard 비교; 특정 가구·낮은 소득·지역에 일반 가점 없음 |
| 신청·급여·이용 기간 | 서로 분리; 접수 상태는 결과 보기, 확인된 마감만 제한된 순위 |
| 혜택 규모 | 금액·주기·대상·상한·현물/서비스/융자 차이를 표시; 최대금액·임의 중요도 가점 없음 |

접수의 논리 상태는 `OPEN / CLOSED / UNKNOWN`이며 검증된 신청 일정과 판단 시각이 필요하다. ‘상시’·‘예산 소진 시’나 급여 기간만으로 OPEN을 확정하지 않는다. 확인된 미래 일정의 원 설계 표시명 `SCHEDULED`는 현재 코드에서 `UPCOMING`으로 표현한다.

보기는 `CURRENT / UPCOMING / CLOSED`다. 경로를 먼저 분류한 뒤 보기별 정책 카드 하나를 만든다. 근거 없는 availability는 UNKNOWN으로 보고 CURRENT에 유지한다. 근거 있는 OPEN 경로의 유효 마감이 평가 시각을 지나면 CLOSED로 옮긴다. 서로 다른 보기의 건수 합을 전체 고유 정책 수라고 표시하지 않는다.

접수 종료는 자격 실패와 별개다. 미래 지원은 입력된 예정 사건과 검수된 미래 적용 근거로만 안내한다. 진학·출산·이사·소득 변화를 예측하거나 현재 INELIGIBLE을 미래 통과로 바꾸지 않는다. 다음 모집이 확정되지 않았으면 재개를 약속하지 않는다.

### 사전식 순위와 feature

`calculatePolicyScore`는 `features`와 오름차순 `rank: number[]`를 반환한다. 원 설계의 `RankScore { strategy: LEXICOGRAPHIC_V1, numericScore: null, key }`는 설명용 확장 구조이며 현재 직렬화 필드가 아니다. 같은 입력·시각·버전에는 같은 순서가 나와야 한다.

1. 직접 선택한 필요의 일치.
2. 희망 시점과 실제 이용 시점의 일치. 마감을 이용 시점으로 대신하지 않는다.
3. 해당 역할·사건·기준일의 생애 단계 관련성.
4. 선호한 제공 방식·시간의 일치.
5. 앞의 feature가 같은 경우 CURRENT의 근거 있는 OPEN·유효한 미래 마감 우선, 그 안에서 빠른 마감 순.
6. 앞의 키가 전부 같은 경우에만 자녀·목적 다양성을 적용하고 안정적 정책 ID로 마무리한다.

현재 feature 키는 MATCH/NOT_USED=0, UNKNOWN=1, OTHER=2다. 선호·사실을 사용하지 않는 feature는 후보 전체에 NOT_USED를 적용해 비교에 영향이 없게 한다. 일부 정책의 근거만 없으면 UNKNOWN이며 부분 feature 수로 재정규화하지 않는다. 이는 적격도·확률 점수가 아니다.

| feature | 계산 계약과 현재 구현 |
| --- | --- |
| need | 현재는 목적·근거가 있고 선택 목적과 교집합이면 MATCH, 교집합이 없으면 OTHER. 목적/근거 누락은 UNKNOWN, 선택 없음은 NOT_USED. 목표 계약은 완전한 목적 범위에서 선택 필요가 없음이 확인될 때만 OTHER이며, 목적 매핑이 불완전하면 UNKNOWN이다. 이 완전성 구분은 후속 공개 검수·계산 연결에서 보완한다. |
| timing | 희망/제공 구간의 확인된 관계를 검수 식으로 평가. 단순 신청일은 대체 불가. |
| lifeStage | 목적·권장 이용 시점 근거를 가진 별도 관련성 식. 임의 연령 점수·자격 점수 중복 가산 없음. |
| delivery | 활성 방식 선호를 실제 제공 근거와 비교하는 식. 알려진 불일치 OTHER, 불명확 UNKNOWN. |
| urgency | CURRENT·OPEN·근거·유효 미래 마감이면 `[0, deadline]`, 나머지 `[1, 0]`. UPCOMING에는 현재 마감 시급성 미적용. |

현재 timing/lifeStage/delivery는 관련 활성 PROVIDED 사실이 있으면 feature를 활성화하고 근거 있는 식의 TRUE/FALSE/UNKNOWN을 MATCH/OTHER/UNKNOWN으로 바꾼다. 불확실한 날짜를 임의의 하루로 확정하지 않는다. 자격 UNKNOWN 자체를 감점하거나 뒤로 격리하지 않으며 마감이 더 중요한 필요를 앞지르지 못한다.

### 대표 경로·중복·동점 다양성

실제 경로·수혜자 조합별로 평가하고 비탈락 후보 중 가장 적합한 하나를 대표로 택한다. 경로 동점은 pathId, 다음은 대상 직렬화 값 순이다. 대표 목적은 선택 필요와 일치하는 목적 코드 중 사전순 첫 값, 없으면 경로 목적 코드순 첫 값이다.

대표 조합 후보의 순위·대상·목적이 같은 경우에는 조건 일치가 확인된 대체 경로를 우선한다. 다른 대상·목적이나 더 낮은 관련성의 일치 경로로 대표를 바꾸지 않는다. 카드 최상위 상태·점수·이유·접수 상태는 같은 대표 조합에 속한다. 다른 경로의 높은 점수·ELIGIBLE·OPEN을 합성하지 않는다. 다른 경로는 pathResults와 해당 대상의 태그로 보여준다. 예를 들어 마감된 교복과 OPEN 학습 경로가 있으면 CURRENT에서 교복을 현재 지원 이유로 쓰지 않는다.

동점 다양성은 이미 선택된 카드에서 덜 다뤄진 자녀 경로를 포함한 정책을 먼저 고른다. 현재 구현은 카드가 포함한 자녀들의 표시 횟수 최솟값을 비교하고, 자녀 경로가 없으면 Infinity로 둔다. 다음은 대표 목적의 누적 횟수, 목적 코드, 정책 ID 순이다.

집계에는 실제 CHILD·ELIGIBLE/UNKNOWN 경로만 사용한다. 여러 자녀에 관련된 카드는 각 자녀 횟수를 한 번씩 늘리고 가구 경로를 모든 자녀로 세지 않는다. 자녀별 할당량을 강제하거나 더 높은 순위의 정책을 밀어내지 않는다. 복수 목적도 대표 목적 하나로 센다.

전체 후보에서 정책별 중복 제거·순위·다양성을 끝낸 뒤 최대 20개·Top 5를 정한다. 후보 전체 수와 추천 수는 다르다. 후속 페이지에서도 Top 5를 다시 선정하거나 20개 상한을 넘지 않는다. 변경할 순위 강도·점수화에는 별도 표본과 사용성 근거 및 rankingVersion 변경이 필요하다.

## 7. 질문 등록·효용·종료

질문은 정책마다 복사하지 않는다. 재사용 키는 **속성 + 대상 + 산정 기준 + 기준 시점**이다. 현재 주민등록과 과거 기준일 주민등록, 학교 소재지는 다른 질문이다. 검수된 템플릿·선택지를 등록하고 런타임 LLM이 질문이나 조건을 생성하지 않는다.

현재 QuestionDefinition은 id·version·fact·prompt·whyAsked·burden·값이 있는 options·`{ questionId, equals }` prerequisites를 갖는다. 인스턴스는 의미 키·definitionId/version·factKey·문구·선택지·affectedPolicyIds·burden·utility를 반환한다. 원 설계의 template/params·answerType·allowedPurposes·정책/경로/규칙별 requiredBy는 확장 등록부 계약이다.

날짜·지역·단위는 검수된 규칙에서 가져오고 원문 전체를 템플릿에 넣지 않는다. 질문·이유는 공개 가능한 근거만 사용한다. 새로운 속성·연산자·단위·응답 구조는 먼저 등록부를 검토하며 표현할 수 없는 조건은 정책 검토 과제로 남긴다.

초기 설계의 C01~C10·A01~A06·ED01~ED07 코드와 현행 분야별 질문 사전 코드를 혼용하지 않는다. 실제 문구·선택지·번호는 질문 사전을 따른다. 진단명·상세 병력·상세 주소·증빙 파일은 받지 않는다. 거리 조건도 필요한 정책 기준의 충족 여부만 묻고 모름을 허용한다.

### 후보 생성과 시뮬레이션

1. 공개 가능한 관련 정책의 사용자로 해결 가능한 누락·정밀도·충돌과 미확인 선호를 대상으로 한다. 정책 근거 부족·미검수를 질문으로 전가하지 않는다.
2. 같은 의미를 병합하고 선행조건을 확인한다. 뒤의 유용한 질문을 여는 선행 질문도 후보가 될 수 있다. 선행 DAG의 순환·누락을 금지한다.
3. 충분히 답한 질문은 제외한다. PROVIDED라도 정밀도 부족·충돌이면 정정이 가능하지만 모름·건너뜀·명시적 비해당은 자동 재질문하지 않는다. 문구만 바꿔 우회하지 않는다.
4. 유효 답변별 가상 평가로 경로 자격·사용자 미확인·순위 feature가 변하는지 확인한다. 모든 답변이 무효하거나 정책 원문 부족만 남는 질문은 하지 않는다.

현재 구현은 등록 options를 열거해 가상 답변을 대체·활성화하고 전체 평가를 호출한다. 후속 질문의 독립 부모까지 같은 대상에 바인딩해 prerequisite DAG를 만족시킨다. 형제의 답변으로 다른 자녀의 선행조건을 충족하지 않는다. 정책 경로 불완전성에 가려진 사용자 unknown 변경만으로 효용을 부풀리지 않는다.

```text
focus = need MATCH 정책이 있으면 그 집합,
        없으면 need UNKNOWN 집합, 그것도 없으면 전체 후보
affected(q) = 유효 답변/열리는 후속 질문으로 평가 근거가 변하는 고유 정책 수
cost(q) = 등록 부담 + 필요한 가장 저렴한 후속 경로 부담
utility(q) = focus 안의 affected(q) / cost(q)
```

양수 효용 최대 → UNKNOWN 자격을 해소 가능한 정책 수 → 낮은 부담 → 질문 키 순으로 고른다. 현재 resolved 집계는 시뮬레이션에서 baseline UNKNOWN 카드가 ELIGIBLE이 되거나 사라지는 정책의 합집합이다. focus에 유용한 질문이 없으면 전체 후보에 같은 계산을 한 번 적용한다.

부담 1은 간단한 선택, 2는 날짜·구간, 3은 복수 인물·이력, 4는 소득·인정 정보다. 이는 사용성 가설이며 정확도나 강제 수집 근거가 아니다. 실제 답변 분포가 없으므로 엔트로피·정보이득을 추정했다고 주장하지 않는다. 모름·건너뜀을 가상 긍정/부정으로 더하지 않는다.

숫자·날짜 자유 입력을 확장할 때는 검수된 규칙 경계의 동치 구간, 지역은 해당 집합/바깥 관계로 시뮬레이션할 제안이다. 현재 options 열거가 자동 경계 생성까지 구현한 것은 아니다. 가상 답변은 저장하거나 실제 결과에 섞지 않는다.

### 종료·수정

- 현재 엔진은 QUESTIONING·questionCount<5일 때 다음 질문을 선택한다. RESULTS는 `RESULTS_REQUESTED`, 5개 도달은 `QUESTION_LIMIT`, 유용한 질문 없음은 `NO_USEFUL_QUESTION`이다.
- QUESTIONING의 cards는 빈 배열이다. RESULTS는 최대 20개와 Top 5를 반환하며 nextQuestion은 null이다. 5문항 뒤 계속/마치기와 결과 화면의 답변 수정·더 확인은 UI에서 별도로 연결할 흐름 계약이다.
- 답변 변경은 원래 공개 가능한 전체 후보에서 다시 계산한다. 이전 제외 목록만 갱신하지 않는다. 대상·사건·분야 변경은 종속 사실·질문 효용·커서를 무효화하며 같은 의미의 공통 답변만 재사용한다.
- 모름·건너뜀은 명시적 수정/재개 전까지 유지한다. 질문 없음은 모두 자격 충족을 뜻하지 않으며 사용자 종료·정책 확인만 남음 등을 설명한다.
- 후보가 없으면 검수 범위와 수정 경로를 안내한다. 다른 분야나 키워드로 몰래 확대하지 않고 비공개 정책 상세·내부 검수자 정보를 노출하지 않는다.

## 8. 모듈·API·개인정보·제한

순수 계산은 `src/features/policy/recommendation/`, 공개 조회·HTTP는 서버 어댑터로 나눈다.

| 현재 모듈 | 책임 |
| --- | --- |
| types.ts / facts.ts | 타입·런타임 입력 검증·FactKey·정밀도·답변 대체/활성화 |
| eligibility.ts | evaluatePredicate / evaluateExpression / evaluateEligibility |
| ranking.ts | 필요·시점·생애 단계·방식·마감 feature, calculatePolicyScore / rankPolicies |
| questions.ts | buildQuestionCandidates / simulateQuestionImpact / selectNextQuestion |
| engine.ts | 카탈로그 검증·selectUsablePolicies·evaluateCards·evaluateRecommendation |
| server/recommendation-release.ts | 승인 묶음·현재 공개 표시 fingerprint·관련 질문 연결 |
| server/category-recommendation.ts | 잠정 관련성 추천·완전한 공개 목록 로더 |

원 설계의 publication.ts·features.ts·explanations.ts는 별도 파일 생성 완료로 취급하지 않는다. 설명은 실제 평가 추적과 공개 근거에서 만들고 템플릿 밖 자격·금액을 주장하지 않는다. `calculateRegionScore`·`calculateHouseholdScore` 같은 일반 가점은 검증 경로에 두지 않는다.

`POST /api/policy-recommendations`가 개인화 서버 경로다. URL에 답변을 넣지 않고 `Cache-Control: private, no-store`를 사용한다. 공개 목록 `GET /api/policies`의 offset·공개 캐시를 개인화 요청에 재사용하지 않는다.

현재 순수 엔진 Request는 revision·category·selectedChildren·subjectsComplete·householdId·needs·answers·phase·questionCount·evaluatedAt·view·mode를 갖는다. 서버가 평가 문맥과 PUBLIC 모드를 통제하고 클라이언트의 점수·검수·공개 상태·근거를 신뢰하지 않는다. 질문·속성·값·대상을 서버 등록부와 대조한다.

현재 Result는 revision·catalogVersion·evaluatedAt·mode·cards·top5·candidateCount·nextQuestion·stopReason이다. 상세 상태별 집계·전체 ContextVersion·사건 참조·schemaVersion·서명 커서는 확장 계약이다. 내부 원문 묶음·검수자·불필요한 개인 식별값은 내보내지 않고 공개 가능한 확인 사항만 전달한다.

잠정 요청은 flow=`CATEGORY_BANK_V1`, phase=`RESULTS`, revision·category·needs·childProfiles·선택 residence·bankAnswers를 받는다. 거주지를 입력하면 제공기관의 지역 접두어(없으면 정책명 접두어)로 다른 시·도 정책을 먼저 제외한다. 구·군까지 입력하면 다른 구·군도 제외한다. 중앙기관·지역 미상 정책은 유지하며 본문에 등장하는 학교·연락처 지역은 거주 범위로 해석하지 않는다. 이는 잠정 지역 관련성 필터이며 검수된 자격 판정은 아니다. 분야 관련 후보의 기본점수 10에 선택 필요별 문구 일치 +8, 일부 상세 답변 신호 +3, 학교 지역 신호 +2, 거주 지역 +2를 더한다. 같은 질문/값 신호는 자녀 수만큼 중복 가산하지 않는다. 점수 내림차순·정책 ID로 정렬해 20개를 반환하며 모두 잠정·추가 확인 태그를 단다.

### revision과 후속 서명 커서

답변 변경 시 브라우저 revision을 올리고 이전 요청을 취소한다. 취소 실패 여부와 무관하게 최신 revision의 응답만 적용한다. 오래된 결과를 새 평가처럼 보여주지 않는다.

다음 커서 계약은 **미구현 제안**이다.

- 서버 서명으로 답변의 키 기반 다이제스트·분야·보기·대상/사건·전체 ContextVersion·평가 시각·위치·만료를 묶는다. 원문 답변은 담지 않는다.
- 답변·범위가 바뀌면 첫 페이지부터 계산한다. 공개 철회·관련 버전 변경·접수 시작/종료·자격 기준일 경계를 통과하면 `409 recommendation-context-changed`로 최신 문맥 재평가를 요구한다.
- 기본 수명 15분·페이지 10건은 제안값이다. TTL만으로 철회를 처리하지 않으며 기존 위치를 유지한 채 평가 시각만 바꾸지 않는다.
- 전체 후보에 중복 제거·다양성을 적용한 뒤 페이지를 자른다. 개인화 커서·다이제스트를 공개 캐시·로그에 저장하지 않는다.

### 최소 수집·완전한 조회·계산 비용

답변은 브라우저 메모리에 보관하고 새로고침 시 초기화한다. 서버는 요청 처리에 사용하며 영구 답변·맞춤 결과·프로필 저장은 별도 동의·수정·삭제·사용자 간 접근 차단 계약이 필요하다. 요청/응답 본문·답변 다이제스트를 접근 로그·오류 추적·분석에 기본 수집하지 않는다. 질문 ID·오류 코드·익명 집계 등 허용 이벤트도 실제 답변 없이 별도 명세한다.

공개 정책·규칙·질문 불변 묶음만 재사용하고 개인 계산은 요청별로 분리한다. 전체 대상 조회 실패나 임의 상한의 부분 결과를 전체 건수로 표시하지 않는다. 현재 잠정 로더는 완료된 전체 순회만 60초 캐시하고 동시 조회를 공유하며 페이지/offset 제한 초과는 오류로 처리한다. 승인 로더도 중복·비진행 offset을 거부한다.

초기 설계의 요청 상한은 본문 128KiB·답변 300개·자녀 30명이다. 현재 잠정 파서도 답변 300개·자녀 30명 제한을 검증한다. 구체적 HTTP 상한은 라우트 구현과 대조한다. 현재 질문 시뮬레이션은 후보당 4,096회 초과 시 `question-simulation-limit` 오류다. 제한 초과를 빈 결과나 일부 자녀 계산으로 바꾸지 않는다.

후속 성능 개선은 속성→규칙/정책 역색인, 경계별 분기 병합, 요청 안의 동일 조합 계산 재사용으로 진행한다. 실제 전체 규모의 지연·메모리를 측정하기 전 성능 통과 수치를 만들지 않는다. 계산 오류는 재시도 가능한 상태로 전달하고 이전 결과를 최신으로 유지하지 않는다.

### 검토 대기 표시와 전체 확대 작업

`GuidedRecommendationResponse.method`는 PROVISIONAL/VERIFIED/MIXED다. 카드별 `reviewStatus`는 REVIEWED 또는 CHECK_REQUIRED이며 후자에는 ‘직접 확인 필요’ 태그와 거주 요건·지원 대상·신청 기간을 공식 안내에서 확인하라는 문구를 표시한다. REVIEWED도 사용자 답변이 부족하면 UNKNOWN일 수 있다. 표시 상태는 서버가 계산하며 승인이나 자격 충족을 사용자 요청에서 받지 않는다.

질문 중에는 두 종류 카드 모두 숨긴다. 결과 요청 시 검수 결과를 먼저 배치하고 잠정 관련성 결과로 남은 자리를 채워 총 20개로 자른다. top5는 최종 목록 앞 5개다. 잠정 후보를 자르기 전에 현행 검수 정책 ID 전체를 제외한다. 이후 검수된 정책은 한 번만 나타나며 직접 확인 태그가 해제된다.

전체 작업 목록은 `scripts/policy/audit-recommendation-coverage.ts --input <ACTIVE 원본 JSON> --out-dir <출력 경로>`로 생성한다. 입력은 `checkedAt`, `items:[{policy,source}]`이며 조회 당시 원본 식별자를 보존해야 한다. 중복 ID는 오류로 처리한다. 원본 변화·활성 목록에서 사라진 초안·미작성·분야 후보 중복을 구분하고 대상/선정기준 원문의 조건 신호와 짧은 주변 구절을 작업 목록으로 남긴다. 개월 수는 연령으로 확정하지 않고 보험료·소득인정액·중위소득 신호도 분리한다. 이 목록은 규칙 자동 승인 자료가 아니다.
