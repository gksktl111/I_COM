## 1. 목적과 범위

행정안전부 정책 데이터를 수집·정제하여 사용자 입력에 맞는 육아 지원 정책을 조회할 수 있는 내부 데이터셋을 정의한다.

정책 원본, 화면 표시용 정보, 검색용 분류, 검수된 비교 규칙을 분리한다. AI 설명은 이 데이터셋 이후의 별도 기능이며, 조건 판별에 사용하지 않는다.

MVP는 전국 공통 정책과 선정한 하나의 시군구에 적용되는 정책부터 시작한다. 해당 시군구의 상위 시도 정책도 포함한다. 최초 검수 대상은 출산·육아 관련 정책 20~30개로 제한한다.

## 2. 원본 API와 수집 단위

행정안전부 「대한민국 공공서비스(혜택) 정보」는 중앙부처·지자체·공공기관·교육청 등의 혜택 정보를 제공한다. 포털은 무료·개발 및 운영 자동승인으로 안내한다. 공공데이터포털

| 기능     | 경로                          | 사용 목적                     |
| -------- | ----------------------------- | ----------------------------- |
| 목록     | `/gov24/v3/serviceList`       | 정책 발견 및 변경 후보 확인   |
| 상세     | `/gov24/v3/serviceDetail`     | 설명·신청 정보·자격 원문 확보 |
| 지원조건 | `/gov24/v3/supportConditions` | 검색 분류의 기초 자료 확보    |

기본 주소는 `https://api.odcloud.kr/api`이다. 세 응답은 `서비스ID`로 연결한다. 목록은 이름·분야·수정일시 등의 필터를, 상세와 지원조건은 `cond[서비스ID::EQ]`를 제공한다. 사용자 조건 전체를 전달하는 맞춤 판별 API로 취급하지 않는다. 공식 Swagger 명세

## 3. 데이터 처리 흐름

1. 목록을 페이지 단위로 수집한다.
2. 육아 관련 후보를 선정한다.
3. 후보의 상세와 지원조건을 수집한다.
4. 응답 구조를 검증하고 원본 스냅샷을 보관한다.
5. 화면 표시용 정보와 검색 분류를 정규화한다.
6. 적용 지역과 세부 조건을 원문에 근거해 검수한다.
7. 검수된 버전을 공개하고 사용자 조건과 비교한다.

사용자 조회 시에는 내부 DB를 사용한다. 외부 API 수집을 사용자 요청 경로에 포함하지 않는다.

## 4. 내부 데이터셋 구성

아래 테이블과 필드는 서비스가 정의하는 내부 설계다. 공공 API가 이 형태로 제공한다는 의미는 아니다. DB는 snake_case, TypeScript는 camelCase로 일관되게 변환한다.

| 테이블                    | 책임                                  | 주요 관계             |
| ------------------------- | ------------------------------------- | --------------------- |
| `policy_sources`          | 외부 정책 식별자와 수집 상태          | 정책당 출처 연결      |
| `policy_source_snapshots` | 변경된 원본 응답 이력                 | 출처 1 스냅샷         |
| `policies`                | 화면에 공개하는 정책 기본 정보        | 출처·분류·규칙의 기준 |
| `policy_tags`             | 정책 탐색용 분류                      | 정책 1 태그           |
| `regions`                 | 서비스 내부 지역 코드 사전            | 상위 지역 참조        |
| `policy_rule_sets`        | 특정 원본을 기준으로 검수한 조건 버전 | 정책 1 규칙 버전      |
| `policy_regions`          | 해당 규칙 버전의 적용 지역            | 규칙 버전 1 지역      |
| `policy_condition_groups` | 대체 가능한 지원 경로                 | 규칙 버전 1 그룹      |
| `policy_conditions`       | 비교 가능한 개별 조건                 | 그룹 1 조건           |
| `policy_sync_runs`        | 수집 작업의 성공·실패·진행 상태       | 수집 작업별 기록      |

`regions`는 선택한 지역 코드 체계의 사전을 별도로 준비한다. 행안부 정책 API가 지역 사전까지 제공한다고 가정하지 않는다.

## 5. 원본 데이터셋

### 5.1 policy_sources

| 필드              | 타입                 | 의미                                   |
| ----------------- | -------------------- | -------------------------------------- |
| `id`              | uuid                 | 내부 출처 ID                           |
| `policy_id`       | uuid                 | 연결된 정책                            |
| `provider`        | text                 | MVP 고정값 `GOV24`                     |
| `external_id`     | text                 | 원본 서비스ID, 숫자로 변환하지 않음    |
| `api_version`     | text                 | 수집 API 버전                          |
| `last_seen_at`    | timestamptz          | 목록에서 마지막으로 확인한 시각        |
| `last_success_at` | timestamptz nullable | 필요한 응답 수집이 완료된 시각         |
| `sync_status`     | text                 | `PENDING / SUCCESS / PARTIAL / FAILED` |

`(provider, external_id)`는 UNIQUE로 설정한다. 이름이 같다는 이유로 서로 다른 서비스ID를 합치지 않는다. 외부 ID는 공개된 자격증명과 무관하며 API 인증키는 DB 원본에 저장하지 않는다.

### 5.2 policy_source_snapshots

| 필드                 | 타입           | 의미                                   |
| -------------------- | -------------- | -------------------------------------- |
| `id`, `source_id`    | uuid           | 스냅샷 및 출처                         |
| `list_payload`       | jsonb          | 해당 정책의 목록 항목 원본             |
| `detail_payload`     | jsonb nullable | 상세 항목 원본                         |
| `conditions_payload` | jsonb nullable | 지원조건 항목 원본                     |
| `fetch_metadata`     | jsonb          | 기능별 수집 시각·성공 여부·원본 수정일 |
| `content_hash`       | text           | 정렬된 JSON 기준 변경 비교값           |
| `fetched_at`         | timestamptz    | 스냅샷 생성 시각                       |

변경된 내용은 새 스냅샷으로 남긴다. 수집 실패와 정상적인 빈 응답을 구분한다. 부분 수집도 진단용으로 보관할 수 있지만 공개 버전을 자동 교체하지 않는다.

## 7. 검색 분류 데이터셋

`policy_tags`는 `policy_id`, `category`, `code`, `origin`, `source_snapshot_id`, `review_status`를 갖는다. 같은 정책에 복수 태그를 허용한다.

| 분류      | 내부 코드 예시                                      | 용도        |
| --------- | --------------------------------------------------- | ----------- |
| 육아 주제 | `PREGNANCY`, `CHILDBIRTH`, `CHILDCARE`, `EDUCATION` | 정책 탐색   |
| 가구 특성 | `SINGLE_PARENT`, `MULTICULTURAL`, `MULTI_CHILD`     | 관련성 정렬 |
| 지원 형태 | `CASH`, `VOUCHER`, `SERVICE`, `DISCOUNT`            | 화면 필터   |

원본 지원조건에는 대상연령 시작·종료(`JA0110`, `JA0111`), 임산부(`JA0302`), 출산/입양(`JA0303`), 한부모가정/조손가정(`JA0403`), 다자녀가구(`JA0411`) 등의 분류가 있다. 지원조건 스키마

원본의 결합 분류를 임의로 분해하지 않는다. 예를 들어 한부모/조손 분류는 우선 원본 의미 그대로 보관하고, 원문 검수 후 내부 태그로 연결한다. 원본 코드 사전은 코드·설명·관찰된 값·해석 규칙·API 버전을 함께 관리한다.

태그는 후보 탐색과 정렬에 사용한다. 태그가 없다는 이유로 정책을 자격 미충족으로 처리하지 않는다. 키워드는 후보 발견 수단이며 제목만으로 최종 수집 대상을 확정하지 않는다.

## 8. 지역·신청기간·규칙 버전

### 8.1 policy_rule_sets

| 필드                                             | 타입                        | 의미                                |
| ------------------------------------------------ | --------------------------- | ----------------------------------- |
| `id`, `policy_id`                                | uuid                        | 규칙 버전과 정책                    |
| `source_snapshot_id`                             | uuid                        | 검수한 원본                         |
| `version`                                        | integer                     | 정책 내 버전 번호                   |
| `review_status`                                  | text                        | `DRAFT / REVIEWED / NEEDS_REVIEW`   |
| `coverage`                                       | text                        | `COMPLETE / PARTIAL / UNKNOWN`      |
| `unresolved_notes`                               | text[]                      | 자동 비교하지 못한 기준             |
| `region_scope`                                   | text                        | `NATIONAL / SPECIFIC / UNKNOWN`     |
| `application_period_kind`                        | text                        | `ALWAYS / FIXED / NOTICE / UNKNOWN` |
| `application_start_date`, `application_end_date` | date nullable               | 검수된 접수 기간                    |
| `valid_from`, `valid_to`                         | date nullable               | 규칙 자체의 적용 기간               |
| `reviewed_at`, `reviewed_by`                     | timestamptz / text nullable | 검수 기록                           |

`coverage=COMPLETE`는 정한 비교 범위에서 확인할 기준을 모두 구조화했다는 의미다. 공식 자격 확정을 뜻하지 않는다. 예산 소진·중복 수혜 등 확인하지 못한 기준이 있으면 `PARTIAL`로 남긴다.

### 8.2 regions / policy_regions

`regions`는 내부 ID, 코드 체계, 외부 코드, 이름, 지역 수준, 상위 지역 ID를 갖는다. 코드 체계와 외부 코드 조합은 UNIQUE로 관리한다.

`policy_regions`는 `rule_set_id`, `region_id`, `include_descendants`, `residence_basis`, `evidence_text`를 갖는다. `residence_basis`는 주민등록지·실거주지·기타·미확인을 구분한다.

- `NATIONAL`은 원문에서 전국 적용을 확인했을 때만 지정한다.
- `SPECIFIC`은 하나 이상의 적용 지역 행이 있어야 한다.
- `UNKNOWN` 또는 지역 행 누락을 전국 정책으로 해석하지 않는다.
- 제공기관 소재지를 정책 적용 지역으로 복사하지 않는다.
- 상위 지역 포함 여부는 코드 문자열 접두어 대신 지역 계층으로 판단한다.
- 지역에 따라 다른 조건을 적용하는 복잡한 정책은 MVP에서 추가 확인 대상으로 처리한다.

정책 검색은 사용자가 입력한 거주지를 사용한다. 시설 검색용 GPS 위치로 정책 거주 조건을 확정하지 않는다.

## 9. 비교 조건 데이터셋

### 9.1 조건 그룹

MVP에서는 그룹 내부를 AND, 그룹 사이를 OR로 고정한다. 지역·신청기간은 그룹 평가와 별도로 공통 적용한다.

| 테이블                    | 핵심 필드                                                                                                                                     |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `policy_condition_groups` | `id`, `rule_set_id`, `label`                                                                                                                  |
| `policy_conditions`       | `id`, `group_id`, `subject`, `field`, `operator`, `value`, `unit`, `reference_date_basis`, `evidence_text`, `evidence_field`, `review_status` |

`subject`는 신청자·자녀·가구를 구분한다. `field`별로 허용 연산자·값 타입·단위를 고정하고 서버에서 검증한다. 임의 SQL이나 실행 코드를 조건 값에 저장하지 않는다.

| 조건 필드 예시        | 비교 예시      | 주의점                                |
| --------------------- | -------------- | ------------------------------------- |
| `child_age`           | 개월 범위      | 부모 나이와 분리, 경계 포함 여부 명시 |
| `child_count`         | 2 이상         | 정책에서 세는 자녀의 범위 확인        |
| `family_traits`       | 한부모 포함    | 복수 가구 특성 허용                   |
| `residence_duration`  | 6개월 이상     | 연속 거주·기준일 검수                 |
| `income_median_ratio` | 특정 비율 이하 | 소득인정액 등 산정 기준 확인          |
| `pregnancy_status`    | 해당           | 미입력과 비해당 구분                  |

자녀 나이의 두 경계는 하나의 범위 조건으로 묶어 동일한 자녀에 적용한다. 자녀 관련 조건을 여러 개 묶는 경우에도 같은 자녀가 모두 충족해야 하는지 명시한다. MVP에서 표현할 수 없는 자녀 간 관계는 미해결 기준으로 남긴다.

### 9.2 가상 구조화 예시

아래 내용은 실제 정책이 아닌 설계 설명용이다.

> 특정 구에 거주하고 만 6세 미만 자녀가 있으며, 한부모가구 또는 자녀 2명 이상인 가구.

| 영역      | 구조화 결과                                         |
| --------- | --------------------------------------------------- |
| 적용 지역 | 해당 구를 `policy_regions`에 등록                   |
| 그룹 A    | 자녀 연령 0개월 이상·72개월 미만 AND 한부모 특성    |
| 그룹 B    | 자녀 연령 0개월 이상·72개월 미만 AND 자녀 수 2 이상 |
| 최종 비교 | 지역 일치 AND (그룹 A OR 그룹 B)                    |

원본 분류에 다자녀 표시가 있다는 이유로 자녀 수 2 이상 규칙을 자동 생성하지 않는다. 근거 문장에 있는 숫자를 검수한 후 등록한다.

| -------------- | -------------------------- | ----------------------------------------------- |
| 문자열         | 앞뒤 공백·줄바꿈 형식 정리 | 의미 있는 목록·문단 유지                        |
| HTML           | 안전한 텍스트 변환         | 원본 HTML 직접 렌더링 금지                      |
| 식별자         | 문자열 유지                | 누락·충돌 시 격리                               |
| URL            | http/https 형식 검증       | 복수 주소·비정상 값은 원문 보존                 |
| 일시           | 확인된 형식만 변환         | 원본 시간대 불명확 시 추정 금지                 |
| 빈 값          | 내부 null로 정리           | 제한 없음·false로 변환 금지                     |
| 분류 코드      | 검증된 코드 사전 적용      | 미확인 값은 UNKNOWN                             |
| 금액           | 원문 보존                  | 월별·일회성·자녀별 금액을 단일 숫자로 축약 금지 |
| 지역·연령·소득 | 후보 추출 가능             | 자격 비교에 쓰기 전 근거 검수                   |
| 신청기한       | 원문 보존                  | 상시·기간·공고·예산 소진 조건 구분              |

알 수 없는 새 필드는 원본에 보존한다. 필수 식별자·필드 타입이 깨진 응답은 공개 데이터 반영을 중단하고 오류를 기록한다.

AI 추출은 향후 검수 초안 작성에만 사용할 수 있다. MVP는 수동 검수한 규칙부터 운영하며, 원문 필드와 근거 문장을 모든 조건에 연결한다.

## 11. 사용자 입력과 결과 구조

| 입력        | 내부 표현                           | 처리 원칙                                |
| ----------- | ----------------------------------- | ---------------------------------------- |
| 거주지      | 지역 ID                             | 시도·시군구 연결 검증                    |
| 가구 특성   | 코드 배열 또는 unknown              | 미선택과 명시적 비해당 구분              |
| 자녀        | 자녀별 생년월일 배열                | 서버에서 기준일에 맞춰 계산              |
| 임신 여부   | yes / no / unknown                  | 미입력을 false로 변환하지 않음           |
| 소득        | 산정 기준·입력 수준·값 또는 unknown | 단순 월급을 소득인정액으로 간주하지 않음 |
| 거주 시작일 | 날짜 또는 unknown                   | 필요한 정책에 한해 추가 입력             |

자녀 수 등 파생값은 서버에서 계산한다. 정책별 자녀 수 정의가 다르면 별도 확인한다. 월령은 일수를 30으로 나누지 않고 생년월일·기준일·정책 경계로 계산한다.

각 조건은 `PASS / FAIL / UNKNOWN`을 반환한다. AND는 FAIL이 하나라도 있으면 FAIL, 그 외 UNKNOWN이 있으면 UNKNOWN이다. OR는 PASS가 하나라도 있으면 PASS, 그 외 UNKNOWN이 있으면 UNKNOWN이다. 빈 그룹이나 규칙 누락은 PASS로 처리하지 않는다.

| 정책 결과     | 조건                                             | 화면 안내          |
| ------------- | ------------------------------------------------ | ------------------ |
| `MATCH`       | 유효한 검수 버전·완전한 비교 범위·필수 조건 통과 | 입력한 조건에 부합 |
| `NEEDS_CHECK` | 미입력·미검수·미해결 기준·규칙 노후화            | 추가 확인 필요     |
| `NO_MATCH`    | 유효하고 검수된 필수 조건에 명확히 불일치        | 기본 추천 제외     |

신청 접수 상태는 `OPEN / CLOSED / UNKNOWN`으로 별도 반환한다. 자격 조건이 맞아도 현재 접수 종료일 수 있다. 마감된 정책은 표시 옵션으로 구분하며, 접수 종료를 자격 미충족으로 혼동하지 않는다.

결과에는 `policyId`, `matchStatus`, `applicationStatus`, `matchedReasons`, `unmatchedReasons`, `missingInputs`, `unresolvedConditions`, `sourceUrl`, `reviewedAt`을 일관되게 반환한다.

## 12. 수집·갱신 운영

### 초기 수집

목록을 순회하고 이름·요약·분야 등을 함께 검토해 후보를 고른다. 목록 필터의 실제 코드값과 페이지 크기 상한은 응답 테스트 후 확정한다. 최초 요청량은 목록 페이지 수와 후보별 상세·조건 요청 수를 기준으로 산정한다.

### 갱신

일 1회 변경 확인을 초기 운영안으로 둔다. API의 실제 갱신 보장 주기가 아니라 서비스 운영 설정이다. 호출 한도와 작업 시간을 확인한 뒤 조정한다.

수정일시 필터는 중복 구간을 두고 조회하고, 정책 식별자로 중복을 제거한다. 성공한 작업 범위까지만 다음 수집 기준점을 이동한다. 상세·조건의 변경이 목록 수정일시에 반영된다는 보장이 확인되지 않았으므로, 선정한 정책은 주기적인 전체 재확인도 수행한다.

### 변경 반영

1. 새 스냅샷을 저장하고 기존 원본과 비교한다.
2. 문구·연락처 변경과 자격·지역·기간 변경을 구분한다.
3. 의미가 불명확한 변경은 조건 변경으로 취급한다.
4. 조건 변경 시 활성 규칙을 `NEEDS_REVIEW`로 표시하고 확정적인 MATCH/NO_MATCH에 사용하지 않는다.
5. 새 표시 정보와 규칙 버전을 검수 후 하나의 트랜잭션으로 공개한다.

이전 공개 정보는 재검수 중임을 표시해 유지하거나 숨길 수 있다. 새 원문과 과거 조건을 조용히 혼합하지 않는다. 조회수처럼 판별과 무관한 값의 변화는 조건 재검수 사유에서 제외한다.

### 실패·삭제 의심

부분 실패 시 기존 공개 데이터를 유지한다. 전체 목록 수집 실패나 일시적인 누락만으로 정책을 삭제하지 않는다. 완전한 목록 동기화에서의 누락과 추가 확인을 거쳐 보관 상태로 전환한다.

`policy_sync_runs`에는 작업 ID, 시작·종료 시각, 상태, 진행 위치, 성공·실패 수, 오류 요약을 기록한다. 재시도는 횟수를 제한하고 동일 정책을 중복 생성하지 않도록 한다. 수집 작업은 작은 배치로 나누어 재개할 수 있게 구성한다.

## 13. 애플리케이션 역할과 접근 범위

| 위치                                 | 책임                                 |
| ------------------------------------ | ------------------------------------ |
| `domains/policy/integrations/gov24/` | API 응답 스키마·클라이언트·원본 변환 |
| `domains/policy/services/`           | 정제·동기화·검수 버전 공개           |
| `domains/policy/queries/`            | 공개 정책 및 후보 조회               |
| `domains/recommendation/schemas/`    | 사용자 입력 검증                     |
| `domains/recommendation/services/`   | 순수 조건 비교 및 결과 조립          |
| 예약 작업 진입점                     | 수집 서비스 호출·인증·작업 잠금      |

수집 서비스는 Next.js UI 로직과 분리한다. 예약 작업 호출 경로와 조회 로직은 동일한 도메인 서비스를 재사용한다. 수집 시간 제한과 배치 재개 방식은 배포 환경 확인 후 확정한다.

일반 사용자는 공개 정책과 필요한 공개 조건만 조회한다. 원본 스냅샷, 검수 메모, 수집 로그 및 쓰기 권한은 운영 영역으로 제한한다. 사용자 맞춤 입력은 MVP에서 영구 저장하지 않는 것을 기본으로 한다.

## 14. 구현 전 확인 목록

- [ ] API 활용 신청 및 목록·상세·지원조건 샘플 확보
- [ ] 문자열 조건값과 null·빈 문자열의 의미 확인
- [ ] API 페이지 크기 상한·할당량·실패 응답 확인
- [ ] 선정 정책의 세 응답 연결 및 누락 비율 확인
- [ ] 지역 코드 체계와 시범 지역 확정
- [ ] 연령 주체·기준일·소득 산정 기준 검수
- [ ] 분류 코드와 자격 규칙의 분리 확인
- [ ] 정확한 연령 경계·다자녀별 나이·AND/OR·미입력 사례 확인
- [ ] 원문 변경 시 기존 규칙이 자동 재사용되지 않는지 확인
- [ ] 부분 수집 실패 시 기존 공개 데이터가 보존되는지 확인

## 15. 결정 요약

MVP는 행안부 API 원본을 보관하고, 정책 표시 정보와 검색 분류를 자동 정규화한다. 적용 지역과 실제 자격 비교 규칙은 작은 범위부터 검수해 등록한다. 미확인 조건은 추가 확인 상태로 제공하고, 정책 변경 시 원본과 규칙 버전을 함께 관리한다.
