# 맞춤 추천: 사용자 질문과 정책 정보 대응표

> 확정한 추천 흐름: 자녀 관련 탐색은 한 명 이상을 선택할 수 있다. 공통 가구 질문은 재사용하고 자녀별 사실은 분리한다. 선택한 자녀 수를 실제 총자녀 수나 정책상 다자녀 산정 수로 사용하지 않는다. 질문 종료 후 최대 20개 정책·Top 5와 자녀별 확인 태그를 표시한다. 상세한 선택·정렬·수정 계약은 [적응형 설계](./policy-adaptive-recommendation-design.md)를 따른다. 현재 화면 구현과는 구분한다.


작성일: 2026-09-09 · 상태: 추천 설계 초안 · 범위: 현재 6개 분야

목표는 **지원 분야 → 거주지 → 분야별 상세 정보 → 개인·가구 특성 → 추천 이유가 있는 정책 목록**을 연결하는 것이다. 상위 6개 분야를 유지하고 세부 지원 목적·대상·자격 조건을 별도로 연결한다. 아래 추가 질문·논리 필드·추천 방식은 제안이며 화면, 저장 구조, 비교 알고리즘을 구현했다는 뜻이 아니다.

후속 v1 결정은 [정책 처리 기준](./policy-recommendation-policy-handling.md)과 [적응형 추천 구현 설계](./policy-adaptive-recommendation-design.md)를 따른다. 본 문서의 질문 대응은 재사용하고, 초기 정렬 제안은 구현 설계의 생애 단계·시점·순위·질문 선택 규칙으로 구체화한다.

현재 입력은 [분야별 맞춤 입력](../ui/interest-questions.md), [입력 타입과 질문 표시 규칙](../../src/features/policy/public/types.ts), [질문 컴포넌트](../../src/features/policy/components/PolicyConditionFields.tsx)를 대조했다. 정책 의미·근거·정보 상태는 [공통 데이터 계약](./policy-common-data-contract.md), 분야 경계는 [라벨링 기준](./policy-labeling-standard.md)을 따른다. 수집 데이터의 최신 건수나 조건 구조화 가능 비율은 이번 작업에서 재조회하지 않았다.

## 1. 추천에서 각 정보가 하는 일

| 용도 | 판단 | 결과에 미치는 영향 |
| --- | --- | --- |
| 후보 탐색 | 선택 분야의 유효한 공개 가능 라벨인가? 지역 적용 범위가 맞는가? | 분야가 확정되지 않은 정책은 해당 분야 결과에 자동 포함하지 않음. 지역이 미확인이면 전국 정책으로 간주하거나 지역 불일치로 탈락시키지 않음 |
| 자격 비교 | 해당 수혜자와 지원 경로의 검수된 조건을 충족하는가? | `MATCH`, `NO_MATCH`, `NEEDS_CHECK`를 구분. 사용자 답변이나 정책 근거 부족은 추가 확인 |
| 추천 순위 | 사용자가 직접 선택한 필요·시점·이용 방식에 얼마나 맞는가? | 필요가 맞는 후보를 우선 안내. 선호 불일치를 자격 탈락으로 바꾸지 않음 |
| 설명 | 어떤 답변과 원문 때문에 추천·보류했는가? | 추천 이유, 비교한 조건, 추가 확인 사항, 신청 일정과 공식 출처를 분리해 표시 |

분류 라벨은 자격 규칙이 아니다. 예를 들어 `child_education`은 교육 분야라는 뜻이며, 초등학생만 지원한다거나 소득 제한이 없다는 뜻이 아니다. 자격 비교 결과도 공식 신청 승인이나 지급 보장은 아니다.

## 2. 공통 질문 대응표

‘현재’는 화면에서 입력 가능하다는 뜻이며 추천에 연결됐다는 뜻이 아니다. 현재 분야 선택은 키워드 탐색에 쓰이고 상세 답변은 정책별 비교·세부 필터에 미연결이다. 표의 정책 정보는 필요한 논리 의미이며 새 DB 컬럼 명세가 아니다.

| ID | 사용자 질문 / 현재 필드 | 현재 상태·표시 시점 | 정책에서 필요한 정보 | 용도·미확인 처리 |
| --- | --- | --- | --- | --- |
| C01 | 어떤 지원 분야가 필요한가요? `interests` | 현재 · 1단계, 하나 필수 | 6개 분야 코드, 세부 유형, 지원 경로, 라벨 근거·버전·검수와 공개 가능 여부 | 후보 탐색. 키워드·`VERIFIED` 상태만으로 공개 허용하지 않음 |
| C02 | 주민등록상 시·도와 시·군·구는 어디인가요? `region`, `district` | 현재 · 분야 선택 후, 선택 입력 | 전국/특정 지역/미확인, 지역 코드·계층·버전, 주민등록/실거주 기준, 적용 대상 인물 | 지역 비교. 시·도만 입력했으면 시·군·구 조건은 미확인. 기관 소재지로 추정 금지 |
| C03 | 자녀의 생년월일 또는 출생월을 알려주세요. `children[].id/birth/precision` | 현재 · 임신·출산은 출산 후·양육 중에 표시, 나머지 분야 표시 | 해당 자녀의 연령·월령 범위, 단위·경계·기준일, 같은 자녀를 묶는 식별 관계 | 자격 비교. 출생월의 가능한 날짜가 경계를 걸치면 추가 확인. 자녀 간 조건을 합치지 않음 |
| C04 | 실제 총자녀 수는 몇 명인가요? 모두 입력했나요? `totalChildren`, `childrenComplete` | 현재 · 자녀 정보와 함께 | 정책이 세는 자녀의 정의, 연령·동거 범위, 총수/대상 자녀 수/출생순위 구분 | 자격 비교. 목록 길이를 총자녀 수로, 총수를 특정 자녀의 출생순위로 대체하지 않음 |
| C05 | 해당하는 가족·가구 특성이 있나요? `household` | 현재 · 양육·보육/돌봄/교육/주거·생활 | 맞벌이·한부모·조손·다문화·위탁·장애 관련 조건의 정확한 정의, 대상자·증빙·예외 | 조건 후보 연결. 일반 한부모 응답을 법정 인정으로, 장애 가족 존재를 해당 자녀의 장애로 바꾸지 않음 |
| C06 | 법정 복지 대상 인정을 받았나요? `welfare` | 현재 · 모든 분야 | 수급/차상위/법정 한부모 등 구체적인 인정 종류·대상·유효 시점, 소득 조건의 대체 경로인지 여부 | 사용자 신고에 따른 조건 비교. 응답을 기관 검증 완료로 표시하지 않음. 선택하지 않은 개별 항목을 자동으로 ‘아니요’ 처리하지 않음 |
| C07 | 알고 있는 소득 산정 기준과 구간은 무엇인가요? `incomeBasis`, `income` | 현재 · 모든 분야, 중위소득 선택 시 구간 표시 | 중위소득/소득인정액/보험료 등 기준, 연도·가구 규모·경계·예외 | 자격 비교. 현재 구간만으로 산정 연도·가구 범위 일치를 보장 못 함. 구간이 기준을 걸치면 추가 확인, 월급 자동 환산 금지 |
| C08 | 지금 가장 필요한 지원은 무엇인가요? | **추가 제안** · 분야별 상세 정보의 첫 질문, 선택 입력 | 분야별 세부 지원 목적, 실제 제공 내용, 수혜자·지원 경로 | 추천 순위. 초기에는 우선 필요 하나를 선택. 돌봄·의료·생활의 기존 필요 질문을 활용하고 같은 의미를 중복 질문하지 않음 |
| C09 | 지원이 필요한 시점은 언제인가요? | **추가 제안** · 필요 선택 후, 선택 입력 | 실제 이용·급여 가능 기간, 준비 기간, 신청 기간·접수 상태와 확인 시각 | 추천 순위. 당장/예정 시점/미정 등의 선택지는 표본 검증 후 확정. 마감 임박과 지원을 빨리 받을 수 있다는 사실을 구분 |
| C10 | 누구에게 필요한 지원인가요? | **추가 제안** · 복수 자녀 또는 부모/자녀 경로가 갈리는 경우 | 신청자·수혜자·가구·임신/출산 사건의 관계와 경로 ID | 조건 결합과 설명. 자녀 ID 선택이나 본인/가구 구분을 사용하며 이름은 불필요. 미선택이면 자녀별 결과를 분리하고 서로 섞지 않음 |

현재 화면은 ‘모름 / 건너뛰기’를 여러 항목에서 같은 값으로 저장하고, `household`·`welfare`의 빈 배열도 별도 응답 상태가 없다. 후속 입력 계약은 **알려진 값 / 명시적 아니요·해당 없음 / 모름 / 건너뛰기 / 아직 묻지 않음**을 구분해야 한다. 기존 빈 값에서 이 차이를 복원하거나 추정하지 않는다. 사용자 답변 상태는 정책 원문의 `MISSING`·`UNRESOLVED` 등 정보 상태와 별도로 유지한다.

## 3. 분야별 상세 질문 대응표

모든 분야가 C01~C10의 의미를 공유하되, 현재 숨겨진 질문을 자동으로 공개하거나 저장하는 변경은 이 문서에 포함하지 않는다. ‘조건부 추가’는 후보 정책의 유효한 규칙이 요구할 때만 묻고, 정책 근거가 모호하면 사용자에게 질문을 반복하는 대신 정책을 재검토한다.

| ID · 분야 | 현재 질문·입력 | 보완할 질문 제안 | 정책에서 필요한 정보 | 적용 원칙 |
| --- | --- | --- | --- | --- |
| F01 · 임신·출산 | 가족 상황 `family`, 임신 중 출산 예정 구간 `birthTiming`; `pregnancy`는 관련 내부 상태로 별도 질문이 아님 | 우선 필요: 임신 준비/난임/산전 관리/출산 비용/산후 회복. 조건부로 예정일·출산일 또는 필요한 사건 확인 | 지원 사건·목적, 수혜자, 임신 주수/출산 후 기간/신청 기한과 기준 사건 | 상황과 필요는 추천에 활용. ‘3개월 이내’를 정확한 예정일·주수로 변환하지 않음. 단일 가족 상황으로 다른 자녀나 임신 관련 사실을 부정하지 않음 |
| F02 · 양육·보육 | 자녀별 보육·교육 이용 `children[].care`: 가정/어린이집/유치원/학교 | 우선 필요: 양육비/시설 이용 비용/양육 지원. 시설 종류·이용 시점은 필요한 경우 추가 | 지원 목적, 자녀별 이용 조건, 시설 유형, 연령, 중복 수급·전환·예외 규칙 | 현재 이용 상황과 원하는 지원을 구분. 어린이집 이용만으로 다른 모든 급여와 중복 불가라 추정하지 않음 |
| F03 · 돌봄 | `careTime`: 평일 낮/저녁·야간/주말·공휴일/일정하지 않음. `careType`: 방문/센터/방과 후/긴급·일시 | 기존 시간·유형을 필요 질문으로 재사용. 조건부로 이용 희망 시점과 정책이 요구하는 보호 공백 사유 | 제공 시간·방식·서비스 지역·연령, 보호 공백의 인정 조건, 예약·정원 정보의 확인 상태 | 시간·유형은 우선 선호 비교. 맞벌이만으로 법정 돌봄 요건을 충족한다고 단정하지 않음. 지원 시간 정보가 없으면 불일치가 아님 |
| F04 · 의료·건강 | `healthNeed`: 검진/예방접종/진료·치료/의료비/재활 | 기존 유형을 필요 질문으로 재사용. C10으로 본인·자녀 구분; 임신 관련 경로라면 필요한 사건 질문 연결 | 지원 목적·대상, 연령/사건, 비용 범위, 특정 인정·진단·의뢰 조건과 확인 필요 항목 | 치료 필요 응답을 진단 사실로 바꾸지 않음. 진단명·상세 병력은 현재 수집 범위 밖이며 필요한 공식 확인을 안내 |
| F05 · 아동 교육 | 자녀 정보와 `children[].care`의 ‘학교’ 선택 | 우선 필요: 교육비/학용품·교복/통학/학습. 자녀별 학교급·학년·재학/입학 예정/학교 밖 상태를 필요한 범위에서 추가 | 교육 목적, 학교급·학년·재학 요건, 학교 밖 청소년 경로, 연령·학년도·지역·예외 | 현재 ‘학교’만으로 초·중·고를 구분할 수 없음. 나이에서 학년·재학을 추정하지 않음. 어린이집·유치원 기본 이용은 양육·보육과 경계 유지 |
| F06 · 주거·생활지원 | `housingType`: 자가/전세/월세/공공임대/기타. `livingNeed`: 주거비/이사·주거 마련/공과금·에너지/생활비 | 기존 필요 질문 재사용; 식생활 지원은 정책 표본에 따라 선택지 보완. 조건부로 정책상 가구의 주택 소유·계약 관계 확인 | 지원 목적, 임차/소유 조건의 대상 범위, 가구 정의·자산·소득·지역·기간, 비용·급여 분기 | 월세 거주를 가구 전체 무주택으로 판단하지 않음. 자산 등 미입력 조건은 추가 확인으로 유지 |

상위 분야를 늘리는 대신 세부 목적을 라벨 사전과 대응시킨다. 표의 한국어 선택지 제안은 기존 세부 유형 코드와 자동으로 일대일 대응하지 않으며, 실제 지원 경로와 근거를 검토한 후 매핑한다. 일·가정 양립처럼 기존 분야에 담기 어려운 서비스 관련 정책은 `OUT_OF_TAXONOMY` 검토를 통해 확장 여부를 결정한다.

## 4. 개인·가구 정보의 조건부 추가 질문

다음 정보는 처음부터 모두 받지 않는다. ‘어떤 정책의 어떤 조건 확인에 필요한지’를 설명할 수 있을 때만 질문한다. 프로필 영구 저장·동의·갱신·삭제는 P2의 별도 계약이며 첫 추천 실험의 선행 조건으로 두지 않는다. 상세 주소, 진단명, 증빙 파일은 이 초안의 수집 범위에 넣지 않는다.

| ID | 질문 제안·표시 조건 | 필요한 정책 정보 | 입력·추론 제한 |
| --- | --- | --- | --- |
| A01 | 해당 지역에 언제부터 거주했나요? 실거주 기준이 필요한가요? | 주민등록/실거주 구분, 계속 거주 기간·기준일·대상 인물 | C02와 다른 의미면 별도 질문. 상세 주소 대신 필요한 지역·기간 정밀도만 요청 |
| A02 | 이 소득 구간의 기준 연도와 산정 가구원 수를 아나요? | 동일한 소득 산정 기준·연도·가구 정의 | 모르면 공식 산정 확인으로 남김. 자녀 수를 가구원 수로 대체하지 않음 |
| A03 | 이 자녀의 출생순위나 정책상 대상 자녀 수는 어떻게 되나요? | 출생순위와 자녀 수의 정책별 정의·예외 | 같은 자녀/사건에 연결. 총자녀 수만으로 추정하지 않음 |
| A04 | 정책에서 요구하는 인정 상태가 누구에게 해당하나요? | 특정 가구원·수혜자의 인정 종류, 시점·증빙 기준 | 가구 특성을 개인에게 전파하지 않음. 필요한 인정 여부 수준만 질문, 증빙을 받은 것으로 표시하지 않음 |
| A05 | 같은 목적의 지원을 현재 이용하거나 받고 있나요? | 특정 급여·서비스 간 중복 제한, 적용 기간·예외·대체 경로 | 정책에 명시된 지원만 확인. 복지 대상 인정과 개별 급여 수급을 구분 |
| A06 | 정책에 필요한 신청자·보호자 관계나 연령 조건을 확인할 수 있나요? | 신청자와 수혜자의 관계, 성인 연령·사건 등 해당 규칙 | 자녀 생년월일로 부모 나이를 추정하지 않음. 실제 규칙이 요구하는 최소 정보만 추가 |

질문은 `속성 + 대상 인물 + 산정 기준 + 기준 시점`이 같을 때 재사용하고 필요한 정책·경로·규칙 및 이유(`required_by`)를 연결한다. 질문을 건너뛰어도 추천 탐색은 계속할 수 있어야 한다. 현재 분야에서 숨겨진 답변은 자동 비교에 투입하지 않으며, 필요한 공통 답변을 재사용할 때도 대상·시점·유효성을 확인한다.

## 5. 라벨링·조건 구조화 산출물

추천 알고리즘을 먼저 완성해 원문을 거기에 끼워 맞추지 않는다. 위 질문이 필요로 하는 의미를 정의한 뒤 실제 정책에 그 근거가 있는지 기록한다.

| 산출물 | 정책별로 남길 내용 | 질문과의 연결 |
| --- | --- | --- |
| 분야·세부 목적 라벨 | 분야, 세부 유형, 수혜 대상, 실제 지원 경로, 원문 근거와 현재 유효성 | C01·C08, F01~F06 |
| 자격 규칙 | 대상 인물·사건, 속성·연산자·단위·경계·기준일, AND/OR·제외·예외와 완전성 | C02~C07·C10, 필요한 A01~A06 |
| 제공 조건 | 지원 방식·시간·장소·비용 범위와 급여 분기 | 분야별 필요·선호와 비교. 지원액만으로 전체 순위를 결정하지 않음 |
| 시점·접수 | 적용/신청/이용/급여 기간 각각의 근거, 접수 상태와 판단 시각 | C09. 수집일이 최근이라는 이유로 접수 중이라 판단하지 않음 |
| 설명·검수 | 연결 원문·스냅샷·변환/평가 버전, AI/인간 검수 종류·범위, 공개 가능 여부, 미해결 이유 | 추천 이유와 추가 확인 표시. 분야 검수가 조건 검수를 대신하지 않음 |

정책 값마다 공통 계약의 정보 상태와 근거를 붙인다. 원문에 없으면 `MISSING`, 충돌·해석 보류는 `UNRESOLVED`다. 같은 정책처럼 보여도 출처별 금액·조건을 임의 병합하지 않으며, 원문·규칙 버전이 달라지면 영향받는 비교를 중단하고 재검토한다.

## 6. 첫 추천 방식 제안과 설명

초기에는 가중치 점수나 학습 모델보다 다음과 같은 설명 가능한 순서를 검증한다. 사용자 행동 수집·학습은 이번 범위에 포함하지 않는다.

1. 공개 계약을 통과한 현재 유효한 분야 라벨의 정책을 후보로 가져온다.
2. 같은 수혜자·지원 경로 안에서 검수된 지역·자격 조건을 비교한다. `MATCH`는 비교 범위가 완전하고 필수 조건과 예외를 해결한 경우만 허용한다. 모든 대체 경로의 불일치가 확정된 경우만 `NO_MATCH`로 기본 추천에서 제외하고 이유를 보존한다. 자녀 목록이 불완전하고 수혜 자녀를 지정하지 않았다면, 입력된 자녀가 모두 불일치해도 정책 전체를 `NO_MATCH`로 확정하지 않는다. 나머지는 `NEEDS_CHECK`로 유지한다.
3. 접수 마감이 확인된 정책은 현재 신청 후보와 분리한다. 접수 미확인은 ‘접수 확인 필요’로 남기며, 자격 비교 결과와 별도로 표시한다.
4. 기본 정렬 초안은 **명시한 필요 일치 → 필요한 이용 시점·방식 일치 → 같은 적합도 안에서 확인된 신청 마감이 가까운 순**이다. 미입력·정책 정보 부족은 불일치 점수로 바꾸지 않는다. 필요를 건너뛴 경우 그 정렬 항목을 생략하고 탐색 결과임을 안내한다. 동률은 안정적인 정책 식별자 순으로 정해 페이지 중복·누락을 방지한다.
5. 조건 확인 완료와 추가 확인 필요 상태를 각 카드에 표시한다. 비교 가능한 정보가 많다는 이유만으로 덜 필요한 정책을 무조건 앞세우지 않는다. 정책별 경로 결과를 먼저 구한 뒤 정책 단위로 중복 제거·건수 계산·페이지 처리를 한다.

아래는 동작 설명용 가상 사례이며 실제 정책 자격이나 추천 품질의 검증 결과가 아니다.

| 입력·정책 상황 | 기대 결과·설명 |
| --- | --- |
| 아동 교육, A지역, 자녀의 초등 재학 확인, 통학 지원 필요. 정책의 분야·지역·학교급·통학 지원이 확인됨 | “선택한 통학 지원이며 입력한 지역·학교급 조건에 맞아요.” 소득 기준이 미확인이면 “소득 조건 추가 확인”을 함께 표시하며 전체 자격 충족으로 표현하지 않음 |
| 같은 사용자에게 일반 학습 지원도 있음 | 분야 후보로 유지하되 직접 선택한 통학 지원보다 후순위. 자격 부적합으로 표시하지 않음 |
| 첫째는 연령만, 둘째는 재학 조건만 충족 | 두 자녀의 조건을 결합한 `MATCH` 금지. 자녀별 경로 판정을 유지 |
| 시·군·구를 건너뛰었고 특정 구 주민등록이 필수 | 지역 추가 확인. 임의로 전국 정책 또는 지역 불일치 처리하지 않음 |
| 원문은 중위소득 120% 이하, 사용자 구간은 100% 초과~150% 이하 | 기준 연도·산정 방식 확인과 별개로 구간이 경계를 걸치므로 `NEEDS_CHECK` |
| 같은 필요의 정책 둘 중 하나만 확인된 마감이 가까움 | 시점·방식 적합도도 같은 경우 마감 임박을 우선. 다른 정책의 날짜 누락을 마감 완료로 취급하지 않음 |

## 7. 다음 실행 단위와 완료 기준

첫 검증 분야로 **아동 교육의 보존 정책 20건 매핑을 진행했다.** 현행 ‘학교’ 응답의 한계와 교육·보육·돌봄의 경계를 [실표본 분석](./policy-education-mapping-audit-20260909.md)에 기록했다. 정책 조건·추천 방식의 운영 검수나 구현 완료를 뜻하지 않는다. 다음은 분석에서 확인한 근거 공백을 보완하고 질문·규칙을 구체화하는 단계다.

1. 수집된 교육 후보와 교육 인접·미분류·검토 대상을 포함해 20건 내외의 원문 표본을 선정한다. 이 수는 작업량 기준이며 정확도 입증 표본이 아니다. 교육비·학용품·통학·학습, 전국·지역, 복수 경로·학교 밖 대상·미확인 사례를 가능한 범위에서 포함하고 빠진 범위를 기록한다.
2. 정책·지원 경로별로 질문 ID, 원문 근거, 필요한 규칙, 정보 상태, 현재 입력으로 비교 가능한지, 추가 질문/정책 재검수 필요 여부를 작성한다. 현행 라벨의 공개 기준 확정은 공개 전 선행 조건으로 유지한다.
3. C08의 교육 목적과 학교급·재학 질문의 선택지를 실제 표본에 맞춰 확정한다. 입력에 대응하지 못하는 정책 조건을 생략하지 않는다.
4. 가상 사용자 사례로 필요 일치·지역 미입력·연령/소득 경계·복수 자녀·OR 경로·원문 변경·접수 미확인을 확인한다. 필요와 조건이 맞는 후보가 남는지, 명확한 불일치가 제외되는지, 정보 부족으로 잘못 제외되지 않는지 평가한다.
5. 그 결과를 바탕으로 한 분야의 입력 → 조건 비교 → 순위 → 설명까지 구현한다. 이후 6개 분야로 확대한다. 검수된 범위가 부족하면 분야 탐색과 추가 확인 안내까지만 제공한다.

이 초안의 완료 범위는 **현재 입력 전체와 6개 분야의 대응표, 추가 질문 조건, 정책 정보 요구사항, 추천·미확인 처리 초안 작성**이다. 후속으로 아동 교육 실표본 20건의 AI 보조 설계 매핑을 수행했으며 결과는 위 분석 문서가 기준이다. 공개 기준 확정, 인간 검수, 질문 선택지 확정, 알고리즘 구현·성능 검증은 후속 작업이다.
