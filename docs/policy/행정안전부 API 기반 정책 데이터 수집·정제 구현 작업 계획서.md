# 행정안전부 API 기반 정책 데이터 수집·정제 구현 작업 계획서

작성일: 2026-09-07

상태: 계획 검토용 — 구현 미착수

기술: 기존 Next.js App Router · TypeScript + Supabase PostgreSQL

기준 문서: [행정안전부 API 기반 정책 데이터 정제·구조화 설계서](./행정안전부%20API%20기반%20정책%20데이터%20정제·구조화%20설계서.md)

이 계획은 **공공 API 수집 → 원본 보관 → 표시 정보 정규화 → 변경 감지 → DB 반영**을 구현 대상으로 한다. 설계서는 초안으로 취급하며, 실제 응답 검증 후 데이터 계약과 DB 스키마를 확정한다. 계획 검토 후 아래 단계를 순서대로 구현하고, 각 단계의 완료 기준을 확인한 뒤 다음 단계로 진행한다.

현재 완료한 일은 저장소 구조·구현 상태 확인과 인증이 필요 없는 공식 명세 조회다. 인증키를 사용하는 실제 정책 응답 수집, 패키지 설치, 코드 구현, DB 생성·변경, 예약 작업 등록은 수행하지 않았다. 이 문서에서 제안하는 파일·명령·테이블은 별도 표시가 없으면 향후 산출물이다.

## 2. 확정 사항·수정 사항·미확인 사항

### 2.1 상태를 구분하는 기준

- **확정 — 요구사항/코드**: 사용자 지정 범위 또는 저장소에서 직접 확인한 사실.
- **확정 — 명세**: 현재 공식 문서에 선언된 내용. 실제 응답에서 항상 보장된다는 뜻은 아니다.
- **확정 — 실응답**: 인증된 실제 응답과 재현 근거로 확인한 내용. 현재 이 상태의 항목은 없다.
- **수정 사항**: 이번 범위나 확인 근거에 맞춰 설계 초안을 조정할 내용.
- **미확인**: 실제 응답, 운영 환경 또는 추가 근거가 필요한 내용. 임의의 확정값으로 채우지 않는다.

| -------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |

| 정상적인 조건 0건과 오류                     | HTTP, 응답 외형, 업무 오류 코드, 필터 일치, 반복 조회 결과 확인           | 근거가 없으면 반영 보류. 0건이 허용된 경우에도 ‘지원조건 없음’으로 판정하지 않음     |

| 호출량·요청 제한·오류 응답                   | 활용 계정 설정과 소량 호출 결과 확인                                      | 계정의 실제 한도·초기화 시각·속도 제한은 미확정. 한도 초과를 일부러 유발하지 않음    |
| 상세·지원조건 변경의 목록 수정일시 반영 여부 | 공식 보장 확인 및 시차 표본 재조회                                        | 초기에는 목록의 수정일시만으로 상세·지원조건 재수집을 생략하지 않음                  |
| 시범 지역                                    | README의 서울 지향을 참고해 표본 선정 시 서울시와 한 자치구를 후보로 기록 | 제공기관 소재지를 정책 적용 지역으로 확정하지 않음                                   |
| 배포·예약 실행 기반                          | Supabase 프로젝트, 배포 플랫폼·요금제·함수 실행 제한·네트워크 제한 확인   | 예약 제공자를 확정한 것으로 표시하지 않음                                            |

공식 Swagger에 조건값의 `enum`, 모델 필수 필드 목록, `perPage` 최대값은 선언되어 있지 않았다. 이 부재 역시 실제 허용 범위를 보장하지 않는다. 위 검증 결과를 ‘확정·수정·미확인’ 대조표에 누적한다. [공식 Swagger 명세](https://infuser.odcloud.kr/api/stages/44436/api-docs?1684891964110)

## 3. 이번 구현의 경계

포함하는 것은 표본 선정과 ID 관리, 세 API 수집, 응답 검증, 원본 보관, 텍스트 정규화, 변경 비교, 정책별 DB 반영, 재실행·실패 복구, 실행 기록, 12시간 예약 연결이다.

`지원대상`, `선정기준`, `지원내용`, `신청기한`도 설명 텍스트로 보관한다. 소득·나이·지역·금액·기간을 자동 계산 가능한 자격 조건으로 바꾸지 않는다. 조건 코드 검증은 전달된 값의 형태와 공식 설명을 확인하는 작업이며 정책 자격의 해석·검수와 다르다.

추천 엔진, `MATCH/NO_MATCH` 판정, AI 추출·설명, 사용자 입력 저장, 사용자 화면·조회 API 연결, 관리자 검수 UI, 지역 사전과 규칙 테이블, 검색 태그 생성은 이번 범위에서 제외한다. API 누락에 따른 자동 삭제·자동 공개도 구현하지 않는다.

## 5. 표본 5~10개 검증 방법

### 5.1 선정 원칙

기본 목표는 8개다. 목록에서 임신·출산·양육·보육·아동·돌봄 등의 키워드로 후보를 찾고 서비스명·요약·지원대상·소관기관을 함께 검토한다. 같은 이름도 서비스ID가 다르면 별개로 취급한다.

| 표본 구성 제안          | 목표 수 | 확인 목적                                            |
| ----------------------- | ------- | ---------------------------------------------------- |
| 중앙부처 육아 관련 정책 | 4개     | 아동 급여·보육·돌봄·임신/출산 등 서로 다른 설명 형태 |
| 서울시 등 시도 정책     | 2개     | 중앙 정책과의 필드·기관·신청 방법 차이               |
| 선정한 한 시군구 정책   | 2개     | 지역별 설명, 긴 조건 문장, 신청기한·URL·빈 값 편차   |

위 수와 주제는 선정 기준이며 실재 정책의 이름·ID를 미리 확정한 목록이 아니다. 실제 데이터에 따라 5~10개 안에서 조정하고 선정 이유를 남긴다. 전국 적용 여부와 상세 자격은 기관 구분만으로 판단하지 않는다. 한부모/조손·다자녀 등 복합 분류나 조건 응답이 빈 사례가 관찰되면 표본에 포함하되, 관찰되지 않은 예외는 별도 합성 fixture로 시험한다.

### 5.2 수집 및 대조 절차

1. 실행 환경에서 인증키를 읽고 소량 목록 요청으로 인증·JSON 외형·오류 형태를 확인한다. 로그에는 인증정보를 넣지 않는다.
2. 목록을 페이지 단위로 읽어 후보를 선정한다. 각 정책의 실제 목록 항목과 페이지·조회시각·비밀 없는 필터를 함께 보관한다.
3. 선정 ID마다 상세와 지원조건을 조회한다. 두 응답도 `data` 배열과 페이징을 확인하고, 무조건 `data[0]`만 사용하지 않는다.
4. 요청 ID와 반환 ID의 정확한 일치, 엔드포인트별 행 수, 중복 및 충돌을 기록한다. 다른 ID의 정보가 결합되면 해당 정책을 격리한다.
5. 모든 관찰 필드의 명세 타입·실제 타입·빈 값 종류·빈도·최대 문자열 길이·예시를 집계한다. JSON의 필드 부재와 명시적 `null`을 원본 단계에서 구별한다.
6. 조건 코드는 `코드 / 공식 설명 / 관찰값 / JSON 타입 / 표본 ID / API 버전 / 수집시각 / 의미 확인 상태`로 기록한다. 새로운 코드를 버리거나 Boolean으로 강제 변환하지 않는다.
7. 목록과 상세가 공유하는 필드를 비교하고 충돌·누락·시각 역전·정상 빈 값의 처리를 결정한다. 정제한 문장을 원문과 대조한다.
8. 같은 필터 재조회와 크기가 작은 페이지 순회로 종료 조건·건수·중복을 확인한다. 수정일시 경계·시간대·동일 시각 여러 ID도 가능한 범위에서 확인한다.
9. 동일 ID를 시차를 두고 재조회해 안정성과 변화 여부를 기록한다. 표본에서 변경이 없었다는 이유로 ‘목록 수정일시가 상세·조건 변경을 항상 반영한다’고 확정하지 않는다.

표본 요청 수는 대략 `후보 탐색 목록 페이지 수 + Σ(정책별 상세 페이지 수 + 지원조건 페이지 수) + 재조회/재시도`로 계산한다. 각 상세·조건이 한 페이지인 경우 8개 표본의 두 API 조회는 16회다. 이는 보장된 호출량이나 페이지 상한이 아니다.

## 6. 잠정 데이터 모델과 코드 구성

### 6.1 DB 모델 후보 — 2단계에서 확정

아래는 책임 분리와 검증 항목을 정하기 위한 제안이다. 실제 필드 타입·NULL·연결 건수 검증 전에 마이그레이션을 확정하지 않는다.

| 테이블 후보               | 역할·핵심 필드 제안                                                                                                                                      | 제약·확인 사항                                                                                      |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `policy_sources`          | 출처 ID, `provider`, 문자열 `external_id`, `api_version`, 수집 대상 여부, `last_seen_at`, `last_success_at`, `sync_status`                               | `UNIQUE(provider, external_id)`. 최초 출처만 수집되고 표시 행이 아직 없어도 허용                    |
| `policy_source_snapshots` | `source_id`, `api_version`, 목록·상세·조건의 원본 JSONB, 엔드포인트별 상태/수집시각/페이지 메타데이터, `raw_hash`, `hash_version`, 완전성, 최초 수집시각 | 동일 출처·버전·동일 내용 중복 방지. 원본 배열/필드/값 보존. 부분 원본을 정상 원본으로 취급하지 않음 |
| `policies`                | 출처와 1:1인 내부 표시 데이터, `name` 등 텍스트, `field_sources`, `applied_snapshot_id`, `display_hash`, `normalizer_version`, 내부 갱신시각             | `UNIQUE(source_id)`. 스냅샷과 출처 일치 보장. 첫 성공 전 표시 행은 없어도 됨. 규칙·공개 상태와 독립 |
| `policy_sync_runs`        | 실행 ID, 수동/예약 구분, 범위, 시작·종료, 상태, 체크포인트, 호출·성공·무변경·실패 수, 오류 요약                                                          | `RUNNING/SUCCESS/PARTIAL/FAILED/SKIPPED` 등 내부 상태를 확정. 목록 완료와 전체 반영 완료를 구분     |
| `policy_sync_items`       | 실행별 정책 진행 상태, 기능별 실제 조회시각, 단계별 시도 횟수·오류·다음 재시도, 수집 스냅샷, 반영 전후 스냅샷, 변경 필드, 완료 여부                      | `UNIQUE(run_id, source_id)`. 동일 실행 재개 시 갱신. 이력이 원본 A→B→A 변화와 부분 실패를 추적      |
| `policy_sync_locks`       | 수집기 잠금 키, 소유 실행 ID, 세대 번호, 만료시각, heartbeat                                                                                             | 키별 1개, DB에서 원자적 획득/갱신/해제. 만료된 실행의 뒤늦은 쓰기 차단                              |

수집 식별 정보와 표시 행 사이의 순환 필수 외래키를 만들지 않는다. 초안의 `policy_sources.policy_id`를 그대로 필수화하기보다 `policies.source_id`를 관계 기준으로 제안한다. 실제 FK 방향은 2단계에서 확정한다.

목록의 정책별 원본 항목과 페이지 정보, 상세·지원조건의 전체 해당 `data` 배열 및 응답 메타데이터를 보존한다. 스냅샷의 ‘원본’은 파싱된 JSON 값 기준이며 원래 HTTP 바이트 순서까지 보존한다는 의미는 아니다. 식별자 없는 행·JSON 파싱 실패는 실행에 연결된 격리 기록으로 남기고 표시값 반영에서 제외한다. 오류 본문은 비밀 제거·크기 제한 후 진단에 필요한 범위만 보관한다.

`policy_tags`, `regions`, `policy_rule_sets`, `policy_regions`, `policy_condition_groups`, `policy_conditions`는 이번 마이그레이션에 넣지 않는다. 조건 코드 관찰 사전은 우선 문서/버전 관리 파일로 두며, 해석 규칙용 DB가 필요해지는 후속 단계에서 확장한다.

`field_sources`에는 엔드포인트·원본 필드·스냅샷·fallback 사용 여부를 남긴다. 정상 응답의 `null`/빈 값과 요청 실패를 구분하고, 정상적으로 비워진 값을 과거 값으로 자동 복원하지 않는다. 목록 fallback은 같은 수집 묶음에서만 계약에 따라 허용한다. 상세 실패 시 과거 상세와 최신 목록을 합쳐 정상 버전으로 만들지 않는다.

### 6.3 정규화 원칙

- HTML은 파서 기반으로 텍스트화하고 문단·`br`·목록 경계를 줄바꿈으로 남긴다. 스크립트·스타일은 제거하고 엔티티는 해제한다. 정규식으로 태그만 지우는 구현에 의존하지 않는다.
- 앞뒤 공백과 줄바꿈 형식을 통일하되 목록 번호·단위·부정문·문단을 보존한다. 원본 JSONB는 수정하지 않는다.
- 문자열의 정상 빈 값은 계약에 따라 내부 `null`로 정리하되 누락 원인은 메타데이터에 남긴다. `0`, `false`, 문자열 `"0"`을 같은 빈 값으로 취급하지 않는다.
- ID는 문자열 그대로 식별한다. 숫자 변환, 이름 기준 합치기, 미확인 접두어 제거를 하지 않는다. 필수 ID·필수 표시 필드 타입이 깨지면 해당 정책을 격리한다.
- 조건의 새로운 코드·허용 의미 미확인 값은 원본에 유지하고 관찰 경고를 남긴다. 미확인 의미만으로 정상 텍스트 반영을 막지는 않지만, 응답 구조·연결이 깨진 경우는 반영을 보류한다.

필요한 의존성 후보는 Supabase JS 클라이언트, 런타임 응답 검증 도구, HTML 텍스트 변환 도구, TypeScript 수동 실행·테스트 도구다. 단계별 필요성을 확인해 추가하며 기존 UI 의존성을 교체하지 않는다. 서버 모듈이 클라이언트 barrel export에 포함되지 않게 하고, CLI와 Next.js 진입점에서 같은 로직을 실행할 수 있도록 환경 로딩을 분리한다.

## 7. 변경 감지·실패·중복 실행 처리

### 7.1 정상 반영 단위

초기 동기화는 검증된 ID 집합에 대해 매번 목록을 확인하고 상세·지원조건을 재수집한다. 목록은 실제 지원되는 필터와 페이징으로 수집한 뒤 ID 집합과 대조한다. 관찰한 목록 필터에 서비스ID 조건을 임의로 추가하지 않는다.

반영 단위는 정책 하나다. 목록·상세와 지원조건이 계약에 맞게 수집되고 ID 연결이 유효해야 정상 묶음이다. 조건 0건은 2단계에서 ‘정상 응답의 부재’로 허용하기로 확인한 경우에만 빈 배열로 완료 처리하며, 자격 제한 없음의 의미를 부여하지 않는다. 상세 0건·서로 다른 상세 중복·ID 불일치·판별 불가능한 오류는 반영을 보류한다.

원본 스냅샷 저장을 먼저 완료하고, 표시 필드·`field_sources`·`applied_snapshot_id`·표시 해시·정규화 버전·정책 성공 상태와 `policy_sync_items`의 반영 전후 스냅샷·변경 필드·정책별 완료 기록을 하나의 DB 트랜잭션으로 갱신한다. 반영 전 상태는 같은 트랜잭션에서 확보하며, 무변경 처리와 저장 원본 재처리에도 같은 원칙을 적용한다. 전체 실행의 집계·체크포인트는 커밋된 정책별 완료 기록으로 복구할 수 있게 한다. 외부 HTTP 호출 중에는 DB 트랜잭션을 열어 두지 않는다. Supabase 클라이언트의 여러 `upsert` 호출을 하나의 트랜잭션으로 간주하지 않고 DB 함수/RPC 등 실제 원자적 실행 방식을 사용한다.

세 외부 API가 같은 시점의 버전을 반환한다는 보장은 아직 없다. 기능별 조회시각과 원본 수정일시를 보존하고, 기존 반영본보다 오래된 수정일시나 응답 간 명백한 충돌은 원본 보관 후 반영을 보류한다. 재조회 후에도 해소되지 않으면 검증 보고서에 남긴다. 허용 가능한 수집 시간 차이는 표본 결과로 정하고, 시간대를 모르는 문자열을 임의 비교해 최신 버전을 선택하지 않는다.

DB 함수는 실행 권한을 서버 역할로 제한하고 기본 `SECURITY INVOKER`를 우선 검토한다. 필요한 권한만 부여하고, `SECURITY DEFINER`가 필요할 때는 비공개 위치·고정 `search_path`·스키마 지정·호출 역할을 검토한다. [Supabase DB 함수](https://supabase.com/docs/guides/database/functions), [접근 제어 안내](https://supabase.com/docs/guides/database/postgres/row-level-security)

| 상황                  | 처리                                                                                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 출처를 다시 발견 | `(provider, external_id)` 기준으로 기존 출처 사용. 목록 관찰 시각만 갱신 가능                                                                            |
| 같은 원본 재수집      | JSON 객체 키를 재귀적으로 정렬한 안정적 직렬화에 해시 적용. 동일 원본 스냅샷 재사용                                                                      |

| 표시 필드 변경        | 변경 필드·이전/새 스냅샷을 기록하고 정책별 원자적 반영                                                                                                   |

| 원본 A→B→A            | A 스냅샷을 재사용할 수 있지만 현재 값 B와 비교해 A로 되돌린 반영 이력을 남김. 과거 해시가 존재한다는 이유로 갱신을 생략하지 않음                         |
| 정규화 로직 변경      | `normalizer_version`을 올려 저장된 원본을 재처리. 원본 해시가 같아도 표시값을 재계산                                                                     |
| 무변경 실행           | 정책·스냅샷의 불필요한 중복 생성은 없음. 실행 기록과 최근 관찰/성공시각 갱신은 의도된 동작                                                               |

| 실패 유형                                      | 처리와 복구                                                                                                                                                     |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 일부 정책의 상세 또는 조건 요청 실패           | 받은 원본과 기능별 실패 상태를 진단용으로 보관. 해당 정책의 기존 표시값·반영 스냅샷을 유지하고 실패 대상 기록. 다른 정상 정책은 계속 처리                       |
| 신규 정책의 부분 실패                          | 출처와 부분 원본만 저장 가능. 정상 표시 행을 억지로 생성하지 않음                                                                                               |
| 목록 페이지 실패·건수 불일치                   | 목록 수집 미완료로 기록. 빠진 정책을 삭제·비활성화하지 않음. 범위 완료 기준점 이동 금지                                                                         |
| 타임아웃·일시 네트워크 오류·5xx·일시 속도 제한 | 요청별 타임아웃, 지수 지연+무작위 지연, `Retry-After`가 있으면 준수. 초기 제안은 최초 1회+재시도 최대 3회이며 호출 예산에 포함                                  |
| 일일 한도 소진                                 | 짧은 재시도 반복 중지. 계정의 초기화 시각 또는 다음 수동 실행으로 보류                                                                                          |
| 인증·권한 오류                                 | 동일 키로 반복 시도하지 않고 실행 실패로 종료. 인증값 없는 오류 분류만 기록                                                                                     |
| 잘못된 파라미터·스키마·식별자                  | 같은 요청을 무한 재시도하지 않음. 격리하고 계약/코드 수정 대상으로 기록                                                                                         |
| 원본 저장 실패                                 | 해당 정책 표시 반영 금지. 저장이 복구된 뒤 같은 작업 단위를 재시도                                                                                              |
| 표시 DB 반영 실패                              | 정책 트랜잭션 롤백. 보관된 원본으로 재처리 가능. 성공시각/적용 포인터를 앞서 갱신하지 않음                                                                      |
| 프로세스 중단·실행 제한 도달                   | 완료된 정책은 유지. DB에 남은 미완료 ID·진행 단계에서 재개. 중단 후 원본이 너무 오래되었으면 세 응답을 재수집하고 과거 부분 응답을 새 응답과 임의 결합하지 않음 |

HTTP 200이어도 오류 본문일 수 있으므로 HTTP 상태·JSON 외형·업무 오류를 함께 확인한다. 전체 실행의 `SUCCESS`는 목록 완료 및 대상 정책의 정상 처리/무변경 완료를 뜻한다. 일부 실패는 `PARTIAL`, 필수 선행 요청 실패나 전체 실패는 `FAILED`로 구분한다.

### 7.4 중복 실행과 재개

DB 쓰기가 있는 수동·예약 실행 모두 `GOV24` 수집기 단위의 DB 임대 잠금을 먼저 획득한다. 메모리 변수나 프로세스 내 타이머만으로 실행을 제어하지 않는다. 잠금이 유효하면 두 번째 실행은 `SKIPPED`와 사유를 남기고 수집을 시작하지 않는다.

잠금에는 소유 실행 ID·만료시각·heartbeat·단조 증가 세대 번호를 둔다. 획득·연장·해제는 DB에서 조건부로 처리한다. 잠금 만료 후 새 실행이 시작되면 이전 실행의 뒤늦은 반영을 DB 트랜잭션에서 소유자·세대·유효기간 검증으로 거부한다. HTTP 응답을 기다리는 동안 잠금이 만료되는 경우도 시험한다.

정책 완료와 체크포인트 기록의 경계에서 프로세스가 종료되어도 재개 시 DB의 정책·스냅샷과 함께 커밋된 정책별 완료·변경 이력을 재확인해 중복 없이 처리한다. 변경 가능한 외부 목록에서는 저장한 페이지 번호만 믿지 않고 앞쪽 페이지부터 재확인할 수 있게 한다. 초기 표본은 고정 ID 집합으로 수집하므로 누락 ID를 명시적으로 재조회·조사한다.

초기에는 수정일시 증분 수집을 필수 구현으로 두지 않는다. 이후 도입할 경우 검증된 시간대·경계와 중복 조회 구간을 사용하고, 실패 ID를 반드시 다음 실행에 포함한다. 미완료 범위를 건너뛰어 전역 기준점을 이동하지 않으며 상세·조건의 주기적 전체 재확인을 유지한다.

## 8. 환경변수와 예약 실행 운영

### 8.1 환경변수 관리

| 변수 제안                                              | 용도                                                     | 도입 시점 |
| ------------------------------------------------------ | -------------------------------------------------------- | --------- |
| `GOV24_API_KEY`                                        | 공공 API 인증키. 검증된 전달 방식으로 서버에서만 사용    | 1단계     |
| `SUPABASE_URL`                                         | 개발/운영 Supabase 프로젝트 주소                         | 3단계     |
| `SUPABASE_SECRET_KEY` 또는 `SUPABASE_SERVICE_ROLE_KEY` | 해당 프로젝트가 제공하는 서버용 인증 방식 중 하나를 선택 | 3단계     |
| `POLICY_SYNC_CRON_SECRET`                              | 스케줄러의 내부 동기화 호출 인증                         | 7단계     |
| `POLICY_SYNC_ENABLED`                                  | 동기화 실행을 중지할 운영 스위치                         | 5~7단계   |

필요한 API 인증키는 로컬 `.env.local`과 배포 환경변수에서 읽는다. 키의 실제 값은 대화, 콘솔, 요청 URL 로그, 응답 오류, fixture, 문서, SQL 마이그레이션, Git에 넣지 않는다. 누락 시에는 변수 이름만 안내한다. 요청·응답 객체 전체를 로그에 직렬화하지 않으며 인증 헤더·쿼리값·오류에 반사된 키를 제거한다.

환경변수 예시는 값이 비어 있는 `.env.example`로 만들고 `.gitignore`에 그 파일만 예외로 추가한다. 실제 `.env*`의 무시 규칙은 유지한다. 수집 키와 Supabase 서버 키에 `NEXT_PUBLIC_`를 붙이지 않는다. CLI에서도 명시적인 환경 로딩을 사용한다. Next.js는 `NEXT_PUBLIC_` 값을 브라우저 번들에 포함하며, Next.js 외부 실행에는 `@next/env`를 사용할 수 있다. [Next.js 환경변수 안내](https://nextjs.org/docs/app/guides/environment-variables)

### 8.2 예약 제공자 선택과 실행 시간

기본 후보는 Supabase Cron의 HTTP 호출로 배포된 Next.js 내부 수집 진입점을 실행하는 구성이다. Supabase Cron은 SQL/DB 함수와 HTTP 요청을 예약할 수 있다. 실제 프로젝트의 확장 사용 가능 여부와 HTTP 응답 제한을 확인한 뒤 선택한다. [Supabase Cron](https://supabase.com/docs/guides/cron)

Supabase Cron을 선택하면 호출 토큰은 스케줄러 측 Vault에 보관하고 Next.js에서는 동일 토큰을 환경변수로 검증한다. 행안부·Supabase API 키는 수집 프로세스의 환경변수에만 두고 예약 SQL에 넣지 않는다. Vault의 평문 조회 권한도 제한한다. [Supabase Vault](https://supabase.com/docs/guides/database/vault)

배포 플랫폼의 자체 예약 기능을 선택할 수도 있지만 12시간 간격 지원을 확인한다. 현재 공식 안내에서 Vercel Hobby Cron은 하루 1회 제한이므로 이를 전제로 12시간 실행을 약속하지 않는다. 실제 배포 플랫폼·요금제는 아직 확인되지 않았다. [Vercel Cron 제한](https://vercel.com/docs/cron-jobs/usage-and-pricing)

기본 제안 스케줄 `0 0,12 * * *`는 UTC 00:00/12:00, 한국 시각 09:00/21:00에 해당한다. 12시간은 서비스 실행 설정이며 공공 API의 갱신 보장 주기를 뜻하지 않는다.

6단계에서 재시도를 포함한 실행 시간과 요청 수를 측정한다. 함수 실행 한도와 스케줄러 HTTP 한도 중 더 짧은 한도 안에서 여유 있게 종료되어야 한다. 맞지 않으면 영속적인 배치/worker에서 동일 수집 코드를 실행하고 완료 상태를 DB로 추적하도록 7단계 설계를 조정한다. HTTP 응답 후 미완료 Promise만 남기는 방식은 사용하지 않는다.

초기 하루 호출량은 대략 `2 × (목록 조회 페이지 수 + 선정 정책별 상세·조건 페이지 수 합계) + 재시도 예산`이다. 목록 검색 범위·페이지 크기·동시성은 실제 계정 한도에 맞춰 확정한다. 실행별 건수·최종 성공시각·오류·처리시간을 기록하고 최근 24시간 성공이 없거나 실패가 지속될 때 운영자가 확인할 절차를 둔다.

## 9. 핵심 검증 시나리오와 최종 완료 기준

| 시나리오                          | 기대 결과                                                                                    |
| --------------------------------- | -------------------------------------------------------------------------------------------- |
| 실제 표본 최초 수동 수집          | 5~10개 정책의 세 응답 연결과 원본·표시값·출처를 추적 가능. 예외는 사유가 명시됨              |
| `--dry-run` 실행                  | DB 잠금·실행 기록을 포함해 쓰기 없음. 비교 결과는 참고용으로 표시하고 API 호출 예산 적용 |
| 동일 fixture 연속 실행            | 출처·정책·스냅샷 중복 없음. 실행 이력과 관찰시각만 필요한 만큼 증가                          |
| 지원내용 텍스트만 변경            | 원본과 표시 해시의 변화를 감지하고 해당 정책만 원자적 갱신                                   |
| 조회수·객체 키 순서·수집시각 변경 | 조회수 차이는 원본 이력에 남고 표시값은 유지. 키 순서·수집시각만으로 원본 변경 오판하지 않음 |
| 조건 코드만 변경                  | 조건 원본 diff와 최신 근거 기록. 자격 규칙·추천 결과 생성 없음                               |
| 정상 빈 값·필드 누락·타입 오류    | 확정 계약대로 구분. 정상 삭제된 문자열을 과거 값으로 복원하지 않고 타입 위반은 격리          |
| 상세/조건 0건·복수 건·ID 불일치   | 계약에 맞는 정상 부재만 허용. 미확인 관계와 충돌 데이터는 기존 표시값을 덮지 않음            |
| 일부 정책 API 실패, 일부 성공     | 실패 정책의 기존 표시값·스냅샷 유지, 정상 정책만 갱신, 실행 `PARTIAL`                        |
| 목록 중간 페이지 실패·일시 누락   | 정책 삭제 없음, 완료 기준점 이동 없음, 재개 가능                                             |
| DB 반영 중 실패                   | 표시 필드·출처·포인터·상태·변경 이력·정책별 완료 기록이 함께 롤백. 보관 원본으로 재처리 가능                            |
| A→B→A 원복                        | 현재 표시값도 A로 복귀하고 변화 이력이 남음                                                  |
| 두 실행 동시 시작·잠금 만료       | 한 실행만 처리. 새 소유자 이후 이전 실행의 쓰기 거부                                         |
| 반영 직후 프로세스 종료·재개      | 완료 정책과 변경 이력이 함께 남고, 집계/체크포인트 복구 후 미완료 정책만 계속 처리                                        |
| 429/5xx/타임아웃·인증 오류        | 일시 오류만 제한적으로 재시도, 한도 소진·인증 오류는 반복 중단                               |
| 정규화 버전 변경                  | 원본 API 재수집 없이 저장 스냅샷으로 재정규화·비교 가능                                      |
| 비밀 보호·접근 제어               | 로그·fixture·커밋 대상·오류에 키 없음. 일반 사용자의 원본/로그/RPC 접근 거부                 |
| 실제 예약 2회                     | 12시간 간격 호출과 수집 작업 완료를 확인. 수동 실행과 중복되어도 데이터 일관성 유지          |

초기 구현 완료는 표본의 실제 데이터 계약이 문서화되고, 해당 계약에 따라 원본과 표시 데이터가 안전하게 저장되며, 반복·변경·실패·재개·동시 실행 검증과 실제 예약 2회 확인까지 끝난 상태다. 해결되지 않은 응답 문제는 영향과 처리 방식을 명시하며, API를 호출하지 않은 결과나 합성 fixture를 실응답 검증 완료로 표시하지 않는다.

구현 시작 전 준비할 것은 API 활용 권한과 환경변수다. 개발용 Supabase 대상은 3단계 전, 배포·스케줄러 선택은 7단계 전에 확정한다. 첫 구현 단위는 **1단계의 안전한 수동 탐색 도구와 실제 표본 검증 보고서**이며, 그 결과를 바탕으로 2단계에서 DB 스키마를 확정한다.


## 10. 사용자 준비 사항과 구현 담당 범위

Supabase 프로젝트는 사용자 안내 기준으로 생성 완료다. 실제 연결 성공·스키마·권한 확인은 아직 수행하지 않았으며, 다음 준비를 단계별로 진행한다.

| 시점 | 사용자 준비 사항 | 구현 시 처리할 사항 |
| ---- | ---------------- | ------------------- |
| 1단계 전 | 공공데이터포털의 해당 API 활용 승인과 인증키를 준비하고 로컬 `.env.local`에 `GOV24_API_KEY`로 설정 | 인증 전달 방식 검증, 안전한 탐색 도구와 실제 표본 보고서 작성 |
| 3단계 전 | 생성한 Supabase 프로젝트 URL/참조 ID와 개발·검증용 여부 확인. `.env.local`에 `SUPABASE_URL`, `SUPABASE_SECRET_KEY` 설정 | 대상·접근 확인, 서버 클라이언트·마이그레이션·테이블·권한·RPC 구현 |
| 3단계 DB 적용 전 | 선택한 관리 도구로 해당 프로젝트에 접근 가능하게 준비. MCP를 사용하면 대상 프로젝트 접근 권한 확인 | 실제 도구 연결과 마이그레이션 적용 권한 검증. CLI/직접 DB 연결을 선택할 경우에만 추가 인증 설정 안내 |
| 7단계 전 | 배포 플랫폼·요금제와 운영 대상 결정 | 실행 한도 확인, 예약 토큰 생성·안전한 저장, 12시간 예약 등록 및 실제 2회 완료 검증 |

새 프로젝트의 서버 수집기는 Secret key를 우선 사용한다. MCP 관리 연결과 애플리케이션 실행용 환경변수는 별도이며, MCP 연결만으로 실행 환경에 키가 설정되지는 않는다. 키는 대화에 붙여넣지 않고 로컬 또는 배포 환경변수에 저장한다. [Supabase API 키 안내](https://supabase.com/docs/guides/getting-started/api-keys)

테이블·RLS·DB 함수·Cron을 사용자가 미리 만들 필요는 없다. 실제 표본으로 계약을 확정한 뒤 구현 단계에서 준비한다. 현재 첫 단계 착수에 필요한 것은 행안부 API 활용 권한과 인증키이며, Supabase 연결 정보는 3단계 전까지 준비하면 된다.
