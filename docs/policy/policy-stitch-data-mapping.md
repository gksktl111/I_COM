# Stitch 화면과 정책 데이터 요구사항 대조

검토일: 2026-09-08 · [아이콤 Stitch 프로젝트](https://stitch.withgoogle.com/projects/11573763693905046904)

프로젝트의 최신화 화면 5개를 MCP로 조회하고 HTML의 입력·출력 내용을 확인했다. 화면의 정책명·지원 금액·날짜·건수는 디자인 예시로 취급하며, 실제 정책이나 검증된 데이터로 사용하지 않는다. 본 문서는 화면과 데이터 요구사항의 차이를 확인하는 참고 자료다. 사용자 요청에 따라 실제 정책 데이터의 정확성을 우선하고 필요한 입력을 디자인에 반영한다. [입력 화면 요구사항](./policy-input-design-brief.md)을 우선 참고한다.

## 2. 입력 구조의 보완

| 화면에서 확인한 요소 | 데이터 요구사항과 차이 | 반영 기준 |
| --- | --- | --- |
| 거주지 시도·시군구 필수 선택 | 초안은 모든 입력을 강제하지 않는 제안 | 정책 비교에 필요한 주민등록상 거주 지역을 명확히 질문. 필수 여부는 화면 예시만으로 확정하지 않고 미입력 상태를 보존 |
| 임신 준비 중·임신 중·자녀 양육 중 복수 선택 | 임신 예/아니요/미입력과 생애 단계가 혼합됨 | 생애 단계는 복수 선택, 임신 여부는 독립된 3상태. 준비 중을 임신 예로, 미선택을 아니요로 변환하지 않음 |
| 자녀별 생년월 또는 개월 수 | 정확한 생일·기준일이 없을 수 있음 | 입력 정밀도와 기준일 보존. 출생일·출생월·입력 시점 월령을 구분하고 경계가 불확실하면 추가 확인 |
| 자녀 추가, 다자녀 체크 | 총자녀 수와 정책별 다자녀 정의는 다름 | 등록 자녀 수를 파생하되 실제 총자녀 수와 목록 완전성 확인. 다자녀 체크만으로 2명 이상 확정 규칙 생성 금지 |
| 맞벌이·한부모/조손·다문화·저소득 등 | 최초 입력은 한부모/조손 결합, 수정 모달은 한부모만 표시; 장애인 등록 가구도 모달에만 존재 | 최초 입력과 수정 모달에 같은 코드·값·선택지를 사용. 결합 항목을 단일 세부 특성으로 해석하지 않음 |
| 소득 관련 체크박스 | 독립 소득 구간 입력 없음 | 사용자 요구인 소득 구간을 추가할 설계 필요. 저소득/차상위 여부와 중위소득 구간을 별도 값으로 취급 |

임신 주수·출산일·거주 기간·양육공백 등은 실제 정책에서 필요한 경우에만 추가 질문으로 연결한다. 한 화면에 모든 예외 입력을 일괄 추가하지 않는다.

## 3. 결과·상세·둘러보기 데이터 매핑

| 화면 요소 | 현재 저장 데이터 | 추가 구조·처리 |
| --- | --- | --- |
| 정책명·요약·대상·내용·기관 | 표시 필드 존재 | 원문 요약의 대표성 검수, 미확보 값 안내 |
| 추천 이유·추가 확인·조건별 체크 | 설명 원문만 있음 | 조건별 PASS/FAIL/UNKNOWN, 비교 대상·근거·누락 입력, 규칙 버전 |
| 자격 충족도 정렬·100% 일치 문구 | 점수·확률 근거 없음 | 확정 가능 판정과 추가 확인 구분. 검수하지 않은 조건을 충족으로 표현하지 않음 |
| 처리기간·지급일 | 별도 정규화 필드 없음 | 신청기한과 분리한 원문·단위·기준 사건. 정보 없으면 생성하지 않음 |
| D-day·접수 중 필터 | 신청기한 텍스트만 있음 | 검수된 시작·마감 시각·시간대, 접수 상태, 확인 시점. 예산 소진 등 미확인 상태 별도 |
| 지원금액 높은순·본인부담 도표 | 금액 포함 원문만 있음 | 현금/융자/감면, 월/연/일회, 자녀당/가구당, 지원금/본인부담을 분리. 비교 가능한 동일 기준이 없으면 정렬 제공 보류 |
| 생애 주기·지원 형태·키워드 | 서비스분야·지원유형은 원본에 있음 | 출처별 코드 매핑과 복수 태그. 가족 특성과 생애 주기를 논리적으로 구분 |
| 전국(중앙부처)·지역 필터 | 기관명·대상 원문 | 중앙부처 분류와 전국 적용을 분리. 적용 지역 검수 필요 |
| 최근 등록·등록 건수·접수중 건수 | 원본 등록일 및 내부 저장 기록 | 외부 등록일/내부 최초 수집/공개일 의미 선택. 실제 공개 범위 집계만 표시 |
| 공식 검증 완료·최종 검증일 | 수집 시점은 존재, 내용 검수 기록 없음 | 수집일을 검수일로 대체하지 않음. 공식 기관 검증과 내부 검수 주체를 구분 |
| 신청·공고 PDF·서류 발급 링크 | 출처·일부 신청 URL, 서류 텍스트 | 역할별 링크·문서 출처·검수 상태 필요. 문서나 절차 자동 생성 금지 |
| 지정 시설·정원 여유·우선 예약 | 정책 수집 데이터에서 미확보 | 시설 데이터와 검증된 정책-시설 연결, 별도 예약·정원 출처가 있을 때만 표시 |
| 보관함·회원 프로필·알림·FAQ | 이번 수집 범위 밖 | 각각 별도 사용자 기능·공식 근거 데이터 계약으로 설계 |

## 4. 화면 흐름에 맞춘 논리 구조

구체적인 DB 테이블을 바로 늘리기보다 다음 책임을 분리하여 데이터 계약을 구성한다.

1. **사용자 검색 조건:** 거주지, 생애 단계, 임신 여부, 가구 특성, 자녀별 입력과 정밀도, 소득 기준·구간. 최초 입력과 수정 모달이 같은 구조를 사용한다.
2. **정책 탐색 정보:** 제목·요약·기관·분류·적용 지역·일정·출처. 둘러보기와 추천 목록에서 재사용한다.
3. **조건 근거와 규칙:** 인물·하위 서비스·급여 분기·신청 절차의 범위, 단위·기준일·관계·미해결 기준·검수 버전.
4. **비교 결과:** 판정, 이유, 누락 입력, 추가 확인, 사용한 원본·규칙 버전. 상세에서도 같은 비교 결과를 사용한다.
5. **정책 상세 보조 정보:** 지급·처리 일정, 비용 구성, 서류·문서·절차·시설 연결. 원본이 제공하는 범위만 구조화한다.

로딩 화면은 내부 저장 정책과 입력 조건의 비교 상태를 표현한다. ‘외부 API 실시간 대조’, ‘오늘 04:00 동기화’, ‘공식 검증 완료’ 등은 실제 구현·관측 근거가 있을 때만 사용한다. 현재는 Gov24 표본 수동 수집 상태이며 디자인에 언급된 복지로·서울시 API 연계와 예약 동기화는 완료되지 않았다.

## 5. 다음 작업 기준

[8개 정책 적합성 보고서](./policy-data-fitness.md)의 공통 계약 보완안에 위 화면 입력·출력 요구사항을 함께 적용한다. 다음 API는 화면에 필요한 데이터가 무엇인지 먼저 매핑한 뒤 표본으로 검증한다. 디자인의 샘플 정책·금액·문구를 수집 데이터의 정답이나 자격 규칙으로 복사하지 않는다.

본 대조는 문서 보완이다. Stitch 원본 화면, 서비스 UI, DB 스키마는 변경하지 않았다. 지역 입력 필수 여부·선택지 통합·소득 입력 방식·금액 정렬의 공개 범위는 UI 구현 전 구체화할 사항이다.
