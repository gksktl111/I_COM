## 1. 다음 착수: 기존 답변과 정책 조건 연결

**사용자 결정: 질문을 먼저 늘리기보다, 현재 수집한 정책의 조건을 정리해 기존 답변과 연결한다.** 현재 UI는 테스트 가능한 상태이며 추천 정확도는 별도 검증이 필요하다. 실제 추천은 문구 관련도 기반이고, 입력받은 모든 정보가 점수·자격 판단에 사용되는 것은 아니다.

1. **정책 조건 구조화 및 기존 답변 연결:** 교육 E03·E04 표본부터 공식 근거·예외를 보완하고 지역, 대상 자녀, 학교급, 지원 목적을 정책별 조건에 연결한다. 대상·산정 기준·기준 시점과 원문 버전을 명시하고 자격 조건과 순위 요소를 구분한다. 임신 주차·출생연도 등 미반영 입력도 목록으로 관리한다.
2. **판단에 필요한 추가 질문만 상세화:** 현재 후보 정책의 판단이나 순위가 달라지는 정보만 묻는다. 입학 연도·학교 소재지·정책별 소득 산정 기준 등을 조건부로 추가하되, 정책 원문 공백을 사용자 질문으로 해결하려 하지 않는다.
3. **가족 상황별 추천 비교 검증:** 지역·자녀 수·학교급·필요 시점을 달리한 사례에서 상위 5개와 최대 20개 목록을 비교한다. 어떤 답변·규칙 때문에 순위가 바뀌었는지 설명하고, 관련 없는 정책의 상위 노출·자녀 간 답변 혼용·입력 수정 후 잘못된 재사용을 확인한다.

완료 기준: 정책 → 근거 → 조건 → 질문/답변 → 판단·추천 이유가 추적되고, `UNKNOWN`은 후보에 유지하며 명확한 `INELIGIBLE`만 제외한다. 기존 문구 관련도 방식과 개선 결과를 같은 사례로 비교한 기록을 남긴 뒤 확인된 양식을 다른 분야에 확장한다. 질문 개수 자체를 개선 성과로 보지 않는다.

### 현재 연결 상태와 후속 검수

6개 분야의 [기본 상세 질문 사전](./policy/policy-category-question-bank.md)과 [기계 판독용 JSON](./fixtures/policy-recommendation/category-question-bank-v1.json)을 작성했다. 공통 1개·분야 전용 23개이며 조건부 질문·응답 상태·대상·기준·시점·활용을 정의했다. 24개 질문을 실제 UI와 서버 요청에 연결했다. 조건부 질문과 자녀별 답변을 수집하고 실제 공개 정책을 관련도 순으로 최대 20개 제공한다. 다음은 질문 답변과 근거가 확인된 정책 규칙의 연결이다.

추천 엔진·합성 정책 테스트 UI 연결 완료: [구현 범위·실행 안내](./policy/policy-recommendation-engine.md). 합성 E03·E04로 자녀별 자격·Top 5·추가 질문·수정 흐름을 검증했다. `/policy/match/test`에서 직접 질문·결과를 테스트할 수 있다. 정식 /policy/match는 거주지·분야 → 분야별 상세 입력·추가 질문 → 결과 순서이며 서버 API와 연결됐다. 검수된 자격 규칙 카탈로그와 별도로 실제 정책의 잠정 추천을 제공하며 결과 상단 확인 안내와 추가 확인 태그를 표시한다. 실제 정책 목록 상세는 모달이다. 다음은 [실제 공식 근거·검수 공백](./policy/policy-recommendation-release-review.md)을 보완하고 검수 규칙·인간 공개 결정을 등록하는 작업이며 합성 정책을 공개 데이터로 사용하지 않는다.

사용자 결정: 첫 화면은 거주지·6개 지원 분야를 받고 다음에 분야별 상세 정보를 받는다. 엔진의 첫 검증·공개 검토 표본만 E03·E04이며 UI 시작 범위를 교복·입학준비로 제한하지 않는다. 2단계 자녀 정보는 기본 1명의 성별·출생연도를 입력하고 추가·삭제하는 방식이다. 자녀 관련 탐색은 입력한 한 명 이상을 함께 추천한다. 가구 사실과 자녀별 사실을 분리하며 다자녀 자격은 정책별 산정 기준으로 확인한다. 질문 종료 후 최대 20개 고유 정책을 표시하고 Top 5를 강조한다. 자녀별 조건 일치·추가 확인 태그와 동률 내 자녀 편중 완화를 구현한다. 현재 교육 UI의 세부 필요는 선택적 복수 선택이며, 개별 질문은 단일 선택·해제 후 다음 버튼으로 확정한다. 상세 계약과 회귀 사례는 적응형 설계 문서가 기준이다.

추천 v1의 [정책 처리 결정](./policy/policy-recommendation-policy-handling.md)과 [적응형 질문·추천 구현 설계](./policy/policy-adaptive-recommendation-design.md)를 작성했다. 공개 가능한 경로, 인간 공개 결정과 규칙 검수의 분리, 자격 삼상태, 필요 중심 정렬, 동적 질문 선택·중단·수정, API·검증 순서를 정했다. 이는 P1-1의 설계 기준이며 실제 인간 검수·공개 상태 구현·승인은 미완료다. 다음 착수는 교육 E03·E04의 공식 근거·예외 보완과 공개/조건 검수 범위 확정, 서버 공개 묶음에 근거와 유효 버전을 연결하는 작업이다.

2026-09-09 추천 방향 보완: 목표는 지원 분야·거주지·분야별 상세 정보·개인 및 가구 특성을 연결한 맞춤 추천이다. ## 3. 자격 조건 비교

정책의 연령·자녀·거주·소득 조건을 원문 근거와 함께 구조화한다. 여러 지원 경로의 조건을 섞지 않으며, 미확인·검토 필요·조건 불충족을 구분한다. 분야 검색이 지급 대상 판정으로 오해되지 않도록 결과 설명을 연결한다.

완료 기준: 정책별 비교 가능한 조건과 비교 불가 사유가 보존되고, 입력 누락·경계 연령·지역/소득 기준·복합 사업 사례를 검증한다. 사람의 공식 자격 확인을 대체한다고 표시하지 않는다. P1 공개 계약과 [공통 데이터 계약](./policy/policy-common-data-contract.md)을 먼저 확인한다.

## 4. 커뮤니티·공지의 실제 동작 연결

- **게시글·댓글**: 저장 구조·권한·작성/수정/삭제·조회/검색/페이지를 구현한 뒤 공개 목록과 상세 시안을 연결한다. 작성자와 타 사용자·관리자 접근 차이를 검증한다.
- **신고·제재·금칙어**: 접수 → 근거 확인 → 조치 → 이력 저장을 연결한다. 중복 접수·동시 처리·재처리·권한 없는 조치를 검증한다. 제재 종류·기간·해제 절차는 구현 전에 운영 기준으로 정한다.
- **공지 게시·알림**: 현재 DB 초안 저장과 보관만 구현됐다. 실제 사용자 노출 또는 발송 채널을 먼저 결정하고 실패·중복 발송·수신 설정을 처리한다. 헤더의 알림 아이콘만으로 수신함이 구현됐다고 보지 않는다.

완료 기준: 준비 중 표시를 제거하는 각 기능에 실제 저장·권한·오류 처리 검증이 있고, 관리자 조치 결과와 공개 화면이 일치한다. 커뮤니티는 P2 사용자 인증에 의존한다. 현재 [관리자 UI 구조](./admin-console.md)를 유지한다.

| 수집 작업 실행기              | 정기 실행·호출 할당량·중단/재개·실패 알림·중복 실행을 운영 환경에 연결. 기존 계획의 실제 12시간 간격 2회 성공을 확인하고 웹의 작은 배치와 장시간 작업을 구분 |

## 다음 작업 시작 순서

1. [문서 안내](./README.md)와 담당 기준 문서를 읽고 현재 코드·환경을 확인한다.
2. 맞춤 추천은 위 1절의 **기존 답변 연결 → 필요한 추가 질문 → 가족 상황별 비교 검증** 순서로 진행한다. [아동 교육 실표본 분석](./policy/policy-education-mapping-audit-20260909.md)의 근거 공백·질문 보완안부터 검토해 P1-1·P1-2와 조건 비교를 연결한다. 커뮤니티를 우선 출시한다면 P2-1부터 진행한다.
3. 선택한 항목의 완료 기준과 실제 변경 범위를 정하고 기존 디자인을 유지하며 구현한다.
4. 검증한 범위·미검증 범위와 결과를 담당 문서에 기록하고 이 목록의 상태를 갱신한다.
